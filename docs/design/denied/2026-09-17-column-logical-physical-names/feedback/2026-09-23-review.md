# Review, 2026-09-23

A read of the proposal against `main` at `de2e1ac9`. "Measured" means the
function in question was run on that commit's source; no deployment was
queried.

## Claims that did not hold

- **The fusion example.** `safe_ident` maps each character outside
  `[a-zA-Z0-9_]` to `_`, so it keeps the character count: `분류` becomes `__`
  and `중요도` becomes `___`. They do not collide. `분류` and `모델` do, both
  `__`, and are the pair a gate would need.
- **#470 as the precedent.** #470 stores nothing; it derives the physical
  table name from the logical one on every call. This proposal would store a
  value that cannot be derived again (it hashes the table id), which is a
  different kind of change.
- **"Existing rows are grammatical by construction."** The column rule
  arrived in 0.3.6 as a validation-only change. Columns created before it may
  have a physical name of `lower(safe_ident(name))` rather than `name`, so a
  `pg_name = name` backfill can be wrong; it needs checking against
  `pg_attribute`, not assuming.
- **RoleSync.** Grants are per table; nothing in role synchronisation refers
  to columns. The gate that includes it is testing something this change does
  not touch.
- **The long-header gate.** Twenty-one Hangul syllables are exactly 63 bytes
  and fit. The bound is crossed at twenty-two.

## What the proposal does not cover

- **The row API.** Request bodies, filters, ordering, `on_conflict` and
  response keys are keyed by the registry name, and the row-query grammar
  accepts only `^[a-z][a-z0-9_]*`. Whether a logical name or a physical one is
  used there is not decided, and headers such as `TriviaQA(비과학 문헌)`
  collide with query-string syntax.
- **The other surfaces.** Foreign-key `references.column`, `akb_vault_info`
  (which lists `pg_attribute` names), the fuzzy error hints, publications, the
  SDK's filter serializer and its generated row types, and the frontend's
  table dialogs and query state.
- **`akb_sql`.** Nothing lets SQL refer to a column by its logical name. The
  rewriter handles table names only; rewriting columns means binding every
  reference to its table through aliases and subqueries, and a wrong binding
  answers from another column without an error.

## What would break

- **Application fingerprints.** The canonical column form accepts a fixed set
  of fields and raises on any other. Adding `pg_name` to every stored column
  makes the fingerprint of every application-owned table fail (measured).
- **Idempotent create.** The physical name hashes the table id, and a create
  request mints a new id each time, so an `if_not_exists` replay of an
  identical request reports `mismatches: ["columns"]` (measured).
- **Silent misbinding.** `safe_ident` maps rather than refuses: `a b` becomes
  `a_b` (measured). A call site left unconverted would read or write another
  column, and the `IF NOT EXISTS` / `IF EXISTS` DDL would skip over the wrong
  name without an error.

## What the logical name would need and does not have

A length bound, a rule for NUL (which JSONB rejects), control and
bidirectional characters, and NFC applied on every path. REST normalises to
NFC; MCP passes the payload through as sent.

## What was underestimated

The interim workaround. A column's `description` is already stored and
already part of the table's search chunk (measured: `- col_1: text — 분류`),
so a header kept there is searchable today. What it lacked was visibility to
the agent that has to write SQL, which is what the decision above adds.
