# Round 00 — 8개 차원 코드 감사

8개 에이전트가 병렬로 코드베이스를 감사했다. 각 발견은 `file:line`과
**중복 시 분류**(BREAKS_CORRECTNESS / WASTEFUL / ALREADY_SAFE)를 달았다.

## Background worker tier — multi-process / multi-replica safety of every worker started by lifecycle.start_workers()

`start_workers()` (backend/app/services/lifecycle.py:115-188) unconditionally starts 11 background loops inside the API process; `app/main.py:40-41` is the ONLY entrypoint that calls it, and there is no gate of any kind. The `app.worker_main` module and the `AKB_DISABLE_WORKERS` env var named in the lifecycle docstring (lifecycle.py:3) DO NOT EXIST anywhere in the repository — I grepped every .py/.yaml/.sh/.md/Dockerfile and the single hit is the docstring itself. The PG-outbox workers are the good news: embed_worker, delete_worker, s3_delete_worker, metadata_worker, events_publisher and external_git_poller all claim with `FOR UPDATE SKIP LOCKED` + a lease push, and `sparse_encoder.recompute_stats` uses `pg_try_advisory_lock` — those six are genuinely multi-process safe today. The bad news is concentrated in four places that have no cross-process coordination at all: the audit hash-chain (a per-file monotonic `_seq` + SHA-256 chain held in process memory), the RoleSync reconciler (unsynchronized CREATE/DROP ROLE DDL computed from two non-atomic catalog reads), the write-lane + git per-vault `threading.Lock` pair that worker git writes rely on, and the startup `cleanup_stale_locks()` self-heal. Splitting a worker tier out is therefore not a matter of "flip a flag" — the flag does not exist, the tokenizer ProcessPool is a SERVING dependency accidentally started behind the worker path, and three workers need real leader election or a redesign before a second process may exist.

**`app.worker_main` and `AKB_DISABLE_WORKERS` do not exist — the docstring documents a kill-switch that was never built** — `backend/app/services/lifecycle.py:3` [high/BREAKS_CORRECTNESS]

lifecycle.py:3-4 states "Both `app.main` (when AKB_DISABLE_WORKERS is unset) and `app.worker_main` import these so the start/stop order stays consistent across entrypoints." I verified this is false. `grep -rn "worker_main|DISABLE_WORKERS|disable_workers"` across the whole repo (excluding .git/node_modules/__pycache__) returns exactly ONE hit: that docstring line. `ls backend/app` shows no `worker_main.py`. `grep -rn "start_workers"` shows the only production caller is `backend/app/main.py:41`, inside the FastAPI lifespan, with no conditional. `backend/app/config.py` has no `disable_workers` field and `model_config = ConfigDict(extra="forbid")` (config.py:74-76) means adding it to app.yaml would hard-fail boot. So there is no supported way to run the API without the workers, and no supported way to run the workers without the API.

*실패 시나리오*: An operator reads lifecycle.py:3, believes an opt-out exists, sets `replicas: 3` in deploy/k8s/backend.yaml (or `--workers 4` on the uvicorn CMD at backend/Dockerfile:17) expecting to set AKB_DISABLE_WORKERS on the extra pods. The env var is silently ignored (nothing reads it). All 11 workers now run in every process, triggering findings #2, #3, #4, #5 and #6 below simultaneously.

*수정 스케치*: Either delete the false docstring, or actually implement it: add `settings.workers_enabled` (config.py) + `if settings.workers_enabled: start_workers()` in main.py:41, and add `backend/app/worker_main.py` that calls `init_storage()` + `start_workers()` with no HTTP surface. Note that `sparse_encoder.start_tokenizer_pool()` (lifecycle.py:135) must move OUT of the worker gate — see finding #10.

**audit_log hash chain assumes ONE writer per file — two processes fork the chain and destroy verify_chain()** — `backend/app/services/audit_log.py:83` [blocker/BREAKS_CORRECTNESS]

`_seq` and `_prev` are plain module globals (audit_log.py:83-86) guarded only by a `threading.Lock`. `_write_one` (audit_log.py:254-283) increments `_seq`, computes `h = _chain(_prev, core)`, and appends to `_file_for(day)` = `{audit.log_dir}/akb-audit-{YYYY-MM-DD}.jsonl` (audit_log.py:113-114) — a path derived purely from config + date, with NO process/pod discriminator. `_reseed` (audit_log.py:160-186) reads the whole file at startup to continue the chain, so it is explicitly built on the assumption that exactly one writer ever touches that file. `settings.audit.log_dir` defaults to `/data/audit` (config.py:42) and config/app.yaml:156 sets it. The module docstring (audit_log.py:20-26) sells the chain as the property that lets the SIEM "prove no line was dropped or altered" — that proof is what breaks.

*실패 시나리오*: Two processes with a shared /data/audit (an RWX volume, or `--workers 2` in one pod where the container filesystem is shared): both reseed to seq=N,prev=H at start, then both append. Process A writes seq=N+1 chained on H; process B also writes seq=N+1 chained on H. The file now has duplicate seq numbers and two divergent chains interleaved. `verify_chain()` (audit_log.py:138-154) walks linearly and fails at the first line whose `h != _chain(prev, core)` — i.e. it reports the audit trail as TAMPERED at roughly the second line of the day, forever. A compliance SIEM cannot distinguish this from real tampering.

*수정 스케치*: Make the filename process-unique (`akb-audit-{day}-{pod_name}-{pid}.jsonl`) so each writer owns its own chain and the SIEM verifies N independent chains — this is the cheap correct fix and also fixes finding #3. Alternatively make audit a genuinely singleton sidecar/tier. Do NOT try to share one file with a PG advisory lock: the chain state is in memory, not in PG.

**audit uploader races on the same WORM bucket key and the same local prune, from every process** — `backend/app/services/audit_log.py:373` [high/BREAKS_CORRECTNESS]

`_bucket_key(day, filename)` (audit_log.py:373-374) is `audit/{day}/{filename}` — again no process discriminator. `_process_uploads_sync` (audit_log.py:468-495) lists completed files, checks a filesystem sidecar marker `{dir}/.uploaded-{day}` (audit_log.py:475-476), and on success writes the marker and later `path.unlink()`s the data file AND the marker (audit_log.py:486-494). Check-then-act on a plain filesystem path is not atomic across processes. Separately: the k8s manifest does NOT mount anything at /data/audit — deploy/k8s/backend.yaml:101-111 mounts only /etc/akb/app.yaml, /etc/akb/secret.yaml and /data/vaults (from the RWO `akb-vaultdata` PVC, backend.yaml:160-163). config.py:41-42 explicitly warns "In k8s mount a PVC here — a pod-local emptyDir loses un-uploaded lines on restart." So the shipped manifest already writes audit to ephemeral container storage.

*실패 시나리오*: Case A (separate pods, per-pod /data/audit as shipped): pod-1 and pod-2 each hold a *different* day-file with the same name and both PUT to key `audit/2026-07-27/akb-audit-2026-07-27.jsonl`. On a plain bucket the second PUT overwrites the first — pod-1's entire day of audit is silently lost. On the Object-Lock/WORM bucket the docstring recommends (audit_log.py:24-26), the second PUT is REJECTED, so pod-2 logs "upload failed (kept locally)" (audit_log.py:482-484) every hour forever and never prunes — a slow local disk fill on ephemeral storage. Case B (shared RWX dir): both processes see marker absent, both upload, both then `unlink` the file and the marker; the loser's `unlink(missing_ok=True)` succeeds silently, and if the marker is unlinked between the other's check and its own upload, the file is deleted with no confirmed upload.

*수정 스케치*: Same fix as #2 — make the filename (and therefore the bucket key) process-unique. Additionally replace the marker-file check-then-act with an atomic `os.rename`/`O_EXCL` create, or move the uploader behind a `pg_try_advisory_lock` so exactly one process uploads per tick.

**RoleSync.reconcile_from_catalog issues unsynchronized CREATE/DROP ROLE DDL from two non-atomic catalog reads** — `backend/app/services/role_sync.py:642` [high/BREAKS_CORRECTNESS]

`reconcile_from_catalog` (role_sync.py:642-685) acquires a pool connection at line 667 but wraps NOTHING in `conn.transaction()` — every statement runs in its own autocommit snapshot. `_reconcile_user_roles` (role_sync.py:687-716) then does two separate reads: `SELECT id FROM users` at line 690 → `wanted`, and `SELECT rolname FROM pg_roles WHERE rolname LIKE 'akb_user_%'` at lines 694-696 → `existing`; anything in `existing - wanted` is DROPped at lines 711-714. `_reconcile_vault_roles` (role_sync.py:718-771) has the identical shape (`SELECT id, owner_id FROM vaults` at 730, `pg_roles` at 737-739, DROP at 766-770), as does `_reconcile_token_roles`. It is started per-process from `start_workers` via `get_role_sync().start_reconcile_timer(...)` (lifecycle.py:183-186) on a bare `asyncio.sleep` loop (role_sync.py:701-718 region, `_reconcile_loop`) with no jitter and no leader election, PLUS one unconditional run at boot (lifecycle.py:109).

*실패 시나리오*: Two processes, reconcile timers unsynchronized. Process B executes `SELECT id FROM users` at T0. A new user signs up at T1 and `on_user_create` (role_sync.py:373-383, called from the API path) does `CREATE ROLE akb_user_<uid>`. Process B executes its `pg_roles` read at T2 > T1, sees `akb_user_<uid>`, computes it as `existing - wanted` = orphan, and `DROP ROLE akb_user_<uid>`. The user's PG role is gone; every `akb_sql` call for that user fails its `SET LOCAL ROLE` (which role_sync.py:401-405 documents as intentionally fail-closed) until the next reconcile happens to rebuild it. The same window drops `akb_vault_*` roles for a vault created between the two reads, and `akb_token_*` for a PAT minted between them. Note this race is latent in the single process today; a second process multiplies the number of unsynchronized read-then-DDL windows and removes the accidental serialization of a single asyncio loop.

*수정 스케치*: Wrap the whole reconcile in a `pg_advisory_xact_lock` (the codebase already uses this pattern in publication_service.py:1289 and document_repo.py:33) so exactly one process reconciles at a time, AND wrap `wanted`/`existing` in one REPEATABLE READ transaction (or add a `created_at > now() - interval '5 min'` grace filter on the orphan set) so a role created after the catalog snapshot is never classified as an orphan.

**Worker git writes serialize only on a process-local threading.Lock; write_lane admission is also process-local** — `backend/app/services/write_lane.py:31` [blocker/BREAKS_CORRECTNESS]

write_lane.py:31-33 states outright: "The per-vault `threading.Lock` in git_service stays as the last-line correctness guard (worker paths — external_git poller, vault seeding — commit without passing this lane)". That lock is `_VAULT_LOCKS: dict[str, threading.Lock]` guarded by `_VAULT_LOCKS_GUARD` (git_service.py:41-52) — in-process only. The lane's own primitives are equally process-local: `_vault_gates: dict[str, asyncio.Lock]` (write_lane.py:75), `_global_slots: asyncio.Semaphore` (write_lane.py:80, sized `settings.write_lane_concurrency` = 8, config.py:498), `_waiters` int (write_lane.py:85), and `_commit_pool: ThreadPoolExecutor` (write_lane.py:94). `ExternalGitService` calls `self.git.clone_mirror` / `cleanup_vault_dirs` / `fetch_remote` directly (external_git_service.py:123-138) with no lane. All of /data/vaults is a single shared mount (deploy/k8s/backend.yaml:110-111).

*실패 시나리오*: Two processes sharing /data/vaults (uvicorn `--workers 2`, or two pods on an RWX volume). Process A's external_git_poller runs `fetch_remote("gnu", ...)` holding A's `_vault_lock("gnu")`. Process B's API request runs an `akb_put` commit into the same `gnu` worktree holding B's *different* `_vault_lock("gnu")` object. Both git processes write `<bare>/worktrees/gnu/index.lock`; the loser fails with "Unable to create index.lock: File exists", or worse both proceed against a half-written index and the worktree diverges from the bare ref. Global write concurrency also becomes N×8 instead of 8, so the PG-pool/executor starvation the lane was built to prevent (write_lane.py:12-22) returns at N× scale.

*수정 스케치*: Replace `_VAULT_LOCKS` with `pg_advisory_lock(hashtext(vault_name))` held for the duration of the git mutation (the codebase already has this idiom), and route ALL worker git writes through `write_lane`/`run_git_write` rather than calling GitService directly. Until then, /data/vaults must stay single-writer — which means the worker tier and the API tier cannot both commit git.

**external_git_poller takes a fixed 3600s lease with no renewal — a slow reconcile is re-claimed mid-flight** — `backend/app/services/external_git_poller.py:32` [high/BREAKS_CORRECTNESS]

`_claim_one` (external_git_poller.py:32-59) does the right thing structurally — `FOR UPDATE OF veg SKIP LOCKED` + push `next_attempt_at = NOW() + external_git_claim_lookahead_secs` — but the lease is a one-shot push of `settings.external_git_claim_lookahead_secs`, default 3600 (config.py:114), and there is no heartbeat/renewal anywhere in `_process_once` (external_git_poller.py:62-86). The docstring at external_git_poller.py:36-37 acknowledges the risk ("The interval has to exceed the longest realistic initial bootstrap — a 1GB mirror clone can easily run past the default 10m") but the mitigation is just a bigger constant. `reconcile` is heavy: initial `clone_mirror` over the network, `ls_tree`, then a `cat_blob` + per-file DB write loop (external_git_service.py:123-138, 187, 266, 300).

*실패 시나리오*: A large mirror's initial bootstrap clone plus per-file import exceeds 3600s. At T=3600 the row becomes due again; process B's poller claims the SAME vault and starts a second `reconcile(vault_id, vault_name)`. Both call into GitService on the same on-disk bare repo — and if `last_synced_sha IS NULL` (still true, because the first reconcile hasn't recorded success yet) BOTH take the "untrusted → re-clone" branch at external_git_service.py:127-134, meaning process B calls `cleanup_vault_dirs(vault_name)` — deleting the repo directory out from under process A's in-flight clone. Only the process-local `_vault_lock` stands between them, and it does not span processes (finding #5).

*수정 스케치*: Convert the claim into a renewable lease: store `claimed_by`/`claimed_at`, heartbeat `next_attempt_at` forward every ~60s from the running reconcile, and only allow re-claim when the heartbeat is stale. Or hold a session-scoped `pg_advisory_lock(vault_id)` for the whole reconcile so a peer physically cannot enter.

**init_storage's stale-git-lock self-heal can delete a lock held live by another process** — `backend/app/services/lifecycle.py:78` [medium/BREAKS_CORRECTNESS]

`init_storage` calls `GitService().cleanup_stale_locks()` unconditionally at every process boot (lifecycle.py:78-83). `cleanup_stale_locks` (git_service.py:206-236) removes `index.lock` files older than `max_age_seconds=60.0`. Its own safety argument is explicitly single-process: git_service.py:229-234 says "Safe under concurrency: the only write paths that touch a worktree's index hold `_vault_lock(vault_name)` per-vault, so startup self-heal — which runs before workers — cannot remove a lock held by a live operation." Both halves of that argument are process-local: `_vault_lock` doesn't span processes, and "runs before workers" only orders things within the booting process.

*실패 시나리오*: Rolling restart of a multi-process/multi-replica deployment. Process A is 70 seconds into a large `clone_mirror` or a bulk `delete_paths_bulk` on vault `gnu`, holding a legitimate live `index.lock`. Process B boots, its `init_storage` runs `cleanup_stale_locks()`, sees the lock is >60s old, and deletes it. Process A's git operation now has no lock; a third concurrent writer can enter the same index, and git may abort A's operation with a lock-ownership error or leave a partially-written index.

*수정 스케치*: Gate the self-heal on a `pg_try_advisory_lock` and only run it when the process can prove it is the only one up (e.g. an init container / migration job that runs before any serving pod), or raise the age threshold well above `git_write_timeout_secs` (30.0, config.py:512) *and* record lock ownership (pid/pod) in a sidecar so foreign live locks are skipped.

**PG-outbox workers correctly claim with FOR UPDATE SKIP LOCKED — these six are multi-process safe** — `backend/app/services/_backfill.py:6` [info/ALREADY_SAFE]

Verified each claim query individually. embed_worker `_claim_batch` (embed_worker.py:60-81): `FOR UPDATE SKIP LOCKED` + push `vector_next_attempt_at = NOW() + 10 minutes`, claim committed in its own tiny transaction (embed_worker.py:124-126) before the embedding API call, and a `SELECT 1 FROM chunks WHERE id=$1 FOR UPDATE` re-check before upsert (embed_worker.py:220-229) closes the vanished-chunk race. delete_worker `_claim_delete_batch` (delete_worker.py:45-66) and `_reap_abandoned_chunks_once` (delete_worker.py:226-264, `FOR UPDATE SKIP LOCKED` inside the CTE plus a `WHERE NOT EXISTS` outbox-dedupe at lines 251-254). s3_delete_worker `_claim_batch` (s3_delete_worker.py:54-75) — and S3 delete is idempotent anyway (s3_delete_worker.py:116-120 treats NotFound as success). metadata_worker `_claim_batch` (metadata_worker.py:60-83) plus a compare-and-swap on `expected_blob` in `mark_llm_metadata_filled` (metadata_worker.py:189-197) that drops a stale LLM result. events_publisher `_claim_batch` (events_publisher.py:89-111). external_git_poller `_claim_one` (external_git_poller.py:39-58) — structurally correct, but see finding #6 for its lease duration. `BackfillRunner` itself already documents and supports sibling tasks coordinating at the DB layer (_backfill.py:44-47).

*실패 시나리오*: With N processes each running these loops, rows are partitioned by SKIP LOCKED: no duplicate embedding calls, no duplicate LLM spend, no duplicate XADD (beyond the inherent at-least-once on a crash between XADD and mark), no duplicate S3 deletes. Throughput scales; correctness holds.

*수정 스케치*: No change needed. These six are the ones you can move to a worker tier as-is.

**sparse_encoder.recompute_stats already leader-elects via pg_try_advisory_lock** — `backend/app/services/sparse_encoder.py:585` [info/ALREADY_SAFE]

`recompute_stats` holds one connection for the whole call and takes `pg_try_advisory_lock(987654321)` (sparse_encoder.py:564, 585-599); a loser returns `{"skipped": True}` immediately rather than blocking, and the lock is released in a `finally` (sparse_encoder.py:685-688). The docstring at sparse_encoder.py:574-578 states the exact multi-replica rationale ("two replicas would each spend minutes tokenizing the corpus and then race on the final UPDATE"). The unconditional bootstrap recompute fired at startup (sparse_encoder.py:756-758, `_bootstrap_recompute`) is covered by the same lock. This is the only worker in the tier that does real leader election, and it is the model the others should follow.

*실패 시나리오*: N processes boot simultaneously; one wins the advisory lock and rebuilds bm25_vocab.df + bm25_stats, the other N-1 log "BM25 recompute skipped" and cost one round-trip each. Correct.

*수정 스케치*: None. Reuse this pattern for role_sync (#4) and the audit uploader (#3).

**Kiwi tokenizer ProcessPool is a SERVING dependency started behind the worker path — splitting tiers will break query encoding** — `backend/app/services/lifecycle.py:135` [medium/WASTEFUL]

`sparse_encoder.start_tokenizer_pool()` is called from `start_workers()` (lifecycle.py:135). But `tokenize()` (sparse_encoder.py:302-329) is on the SEARCH hot path via `encode_query` (sparse_encoder.py:518-558), not just the indexing path. The function's own docstring says so: "This is a SERVING dependency (query encode_query) as well as a worker dependency, so if API and indexing-worker tiers are ever split it must be started on the always-run path, not behind a worker gate" (sparse_encoder.py:277-279); lifecycle.py:132-134 repeats the warning. Cost side: the pool spawns `max(2, min(4, os.cpu_count() or 2))` processes (sparse_encoder.py:284), each running `_init_tokenizer_worker` to load a full Kiwi model (sparse_encoder.py:267-270). Also `_token_cache` (sparse_encoder.py:250-251, 2048 entries) and `_stats_cache` (sparse_encoder.py:386-387) are per-process.

*실패 시나리오*: Someone implements the worker gate from finding #1 and puts `start_tokenizer_pool()` behind it. The API tier now has `_tokenizer_pool is None`, so `tokenize()` silently falls through to `asyncio.to_thread` (sparse_encoder.py:322-324) — the exact GIL-serialization path that caused the documented 503 flapping incident (sparse_encoder.py:255-263). No error, no log; just the old outage under search load. Cost side without a split: N processes × up to 4 spawned interpreters each holding a Kiwi model, against a 4Gi memory limit (deploy/k8s/backend.yaml:118-119); I have not measured the per-model resident size, so I cannot state whether 4 processes × 4 workers fits.

*수정 스케치*: Move `start_tokenizer_pool()` (and `stop_tokenizer_pool()`) out of start_workers/stop_workers into `init_storage`/`shutdown_storage` NOW, before any tier split, so the invariant is structural rather than a comment. Size the pool from a config knob so a worker tier and an API tier can be tuned separately.

**Per-process asyncpg pool of 30 connections × N processes will exhaust PG max_connections** — `backend/app/config.py:92` [high/WASTEFUL]

`pg_pool_max_size: int = 30` (config.py:92), read per-process in `_pool_sizes` (backend/app/db/postgres.py:33-40) and passed to `asyncpg.create_pool` (postgres.py:51-52). Every worker in the tier acquires from this same per-process pool. Several hold a connection across external I/O: events_publisher `_process_once` holds ONE connection across an entire 64-row batch of Redis XADD round-trips (events_publisher.py:184-227, BATCH_SIZE=64 at line 39); embed_worker holds a connection per chunk across `store.upsert_one` (embed_worker.py:209-243), which for the qdrant/seahorse drivers is a network call; `recompute_stats` holds `lock_conn` for the entire corpus scan + tokenize, which its own comment calls "minutes of CPU" (sparse_encoder.py:585-631, 711-712); vault_backfill holds a connection across a 5000-row UPDATE (vault_backfill.py:129-149, `_BATCH = 5000` at line 39).

*실패 시나리오*: 4 replicas (or `--workers 4`) → 4 × 30 = 120 connection slots demanded against a PostgreSQL server whose default `max_connections` is 100. Pods that boot later fail `init_db()` with "remaining connection slots are reserved", or serving requests start timing out on pool acquire under indexing load. Nothing in the code caps the aggregate.

*수정 스케치*: Size `pg_pool_max_size` as `total_budget / n_processes` and set it explicitly per tier (a worker tier needs fewer serving conns and vice versa), or put PgBouncer in front. Separately, release the connection around the Redis batch in events_publisher._process_once rather than holding it for 64 network round-trips.

**Process-local monotonic rate limiters make every periodic sweep/reap run N times per interval** — `backend/app/services/delete_worker.py:39` [low/WASTEFUL]

Four independent `time.monotonic()`-based gates live in module globals and therefore reset per process: delete_worker `_last_sweep_at` (delete_worker.py:39, checked at 170-174, SWEEP_INTERVAL_SECONDS=3600) and `_last_reap_at` (delete_worker.py:209, checked at 217-222, REAP_INTERVAL_SECONDS=3600); s3_delete_worker `_last_sweep_at` (s3_delete_worker.py:35, checked at 141-145); events_publisher `_last_sweep_at` (events_publisher.py:47, checked at 236-240). The underlying statements are bulk `DELETE ... WHERE processed_at < NOW() - interval` (delete_worker.py:178-187, s3_delete_worker.py:150-157, events_publisher.py:245-251) — idempotent, so this is cost not corruption. The reap (delete_worker.py:226-264) additionally uses FOR UPDATE SKIP LOCKED so concurrent reapers get disjoint sets.

*실패 시나리오*: With N processes, each of the four bulk DELETEs fires N times per hour instead of once, all unsynchronized (no jitter). On a large `events` table (7-day retention, events_publisher.py:45) that is N concurrent large deletes competing for the same pages, producing lock contention and bloat churn for zero additional benefit. Result is correct; the cost is N×.

*수정 스케치*: Move the cadence gate into PG — either a `sweep_state` table with a timestamp checked in the same statement, or wrap each sweep in `pg_try_advisory_lock` so only the winner runs the DELETE.

**vault_backfill's `_ready` latch is per-process, so search silently uses different filter paths in different processes** — `backend/app/services/vault_backfill.py:42` [low/WASTEFUL]

`_ready` is a module global (vault_backfill.py:42) read on the search hot path via `is_ready()` (vault_backfill.py:45-48) to decide whether the pgvector vault-filter path is safe. It is set independently in each process by `_process_once` (vault_backfill.py:74-126). The batch UPDATE itself (vault_backfill.py:129-148) has NO `FOR UPDATE SKIP LOCKED` — two processes select overlapping `vault_id IS NULL` rows and one blocks on row locks until the other commits, then re-updates the same rows with the same value. The module comment at vault_backfill.py:154-155 already reasons about this ("the batch UPDATE is idempotent on NULL, so a rolling-deploy overlap is harmless") — that reasoning holds.

*실패 시나리오*: During the one-time backfill with N processes: process A finishes its EXISTS probe (vault_backfill.py:114-123) and latches `_ready = True`; process B is one tick behind and still has `_ready = False`. Identical search requests now take different code paths depending on which process the load balancer picks — A uses the vault filter, B uses the source-id path. Both are documented as correct (the source-id path is the safe fallback, vault_backfill.py:10-12), so this is behavioural inconsistency and duplicated 5000-row UPDATE work, not wrong results. Contention cost: two 5000-row UPDATEs serializing on the same rows while each holds a pool connection.

*수정 스케치*: Add `FOR UPDATE SKIP LOCKED` to the batch CTE so concurrent backfillers take disjoint slices, and treat the readiness latch as eventually-consistent (it already is) — or gate the whole worker behind `pg_try_advisory_lock` since it is a one-time migration.

## MCP transport, auth, and API-layer statefulness (the sticky-session question)

The MCP Streamable-HTTP transport is a hard blocker for horizontal scale-out: `backend/mcp_server/http_app.py` keeps every live MCP session — the transport object, the `asyncio.Task` running the server loop, and the resolved user — in three process-local module dicts (`_transports`, `_server_tasks`, `_session_users`, lines 52-55), and the vendored SDK hard-404s any request whose `mcp-session-id` header does not match the transport instance that minted it (`mcp/server/streamable_http.py:845-851`). Nothing in `deploy/k8s/backend.yaml` or `deploy/k8s/ingress.yaml` configures session affinity, so raising `replicas` above 1 today would break MCP for every client that is not lucky enough to be re-routed to the same pod. Auth itself is in far better shape and is essentially replica-ready: AKB JWTs are stateless HS256 over a shared `jwt_secret`, PATs are hashed rows in `tokens`, public share/view-grant tokens are HMACs, and — notably — the OIDC CSRF `state`, PKCE verifier, and one-time exchange codes were deliberately moved into the `oidc_transients` PG table with atomic `DELETE … RETURNING` consumption, explicitly "so the redirect round-trip works across multiple backend replicas" (`keycloak_oidc.py:22-25, 78-95`). Agent sessions (`/api/v1/agent-sessions`) hold no memory state at all — everything lands in PG collections/documents plus git, with `ON CONFLICT DO NOTHING` on the session collection. The remaining non-MCP blockers are the publication password-brute-force limiter, which is an in-memory dict whose own docstring states it relies on AKB being single-replica, and the Node proxy's blind retry-on-404/ECONNRESET path, which will silently duplicate mutating tool calls once requests can be re-routed mid-flight.

**MCP session state (transport + server task + user) lives in process-local dicts — no shared store, no affinity** — `backend/mcp_server/http_app.py:52` [blocker/BREAKS_CORRECTNESS]

`_transports: dict[str, StreamableHTTPServerTransport]`, `_server_tasks: dict[str, asyncio.Task]` and `_session_users: dict[str, object]` (http_app.py:52-55) are module globals. A session is created on POST when the incoming `mcp-session-id` is absent OR unknown to this process (http_app.py:141-151): the `else` branch mints a *fresh* `uuid4`, builds a new `StreamableHTTPServerTransport(mcp_session_id=<new uuid>)`, and then delegates the ORIGINAL request to it. The vendored SDK then rejects that request: `_validate_session` compares the header value against `self.mcp_session_id` and returns HTTP 404 'Not Found: Invalid or expired session ID' (/Users/kwoo2/.pyenv/versions/3.11.9/lib/python3.11/site-packages/mcp/server/streamable_http.py:826-851, reached via `_validate_request_headers` at :503). There is no Redis/PG session store and no `event_store` passed to the transport (http_app.py:145-148), so there is also no resumability fallback. This is the single hardest blocker in this dimension.

*실패 시나리오*: With replicas=2 behind the existing round-robin Service: client POSTs `initialize` → pod A creates session S and returns `mcp-session-id: S`. The next `tools/call` is routed to pod B. B does not have S in `_transports`, so it mints session S' and hands the request to S''s transport, which 404s on the mismatched header. The agent's tool call fails. Every subsequent call has a ~50% chance of failing, and each failure leaves a permanent orphan transport+task on B.

*수정 스케치*: Either (a) make the transport genuinely stateless per request — reject unknown session IDs with 404 and let the client re-initialize, plus put `is_json_response_enabled` sessions behind a shared store; or (b) pin `/mcp` with sticky sessions (nginx `upstream-hash-by` on the `mcp-session-id` header / `sessionAffinity: ClientIP`) as an explicit, documented prerequisite before any replica increase. (a) is the only option that survives pod restarts.

**No session affinity configured on the backend Service or the /mcp ingress path** — `deploy/k8s/backend.yaml:179` [blocker/BREAKS_CORRECTNESS]

The backend `Service` (backend.yaml:179-190) has no `sessionAffinity` field (defaults to `None` = round-robin across endpoints), and `deploy/k8s/ingress.yaml` routes `/mcp` (prefix) to that Service with only `proxy-body-size` and `proxy-read-timeout` annotations — no `nginx.ingress.kubernetes.io/affinity`, no `upstream-hash-by`. So the in-memory session design of finding #1 is currently held together only by `replicas: 1`. I found no doc in `docs/` mentioning sticky sessions or session affinity (grep for sticky|sessionAffinity|multi-replica returned nothing), so this is an undocumented, unguarded coupling between a k8s manifest constant and application correctness.

*실패 시나리오*: An operator (or an HPA) raising `replicas` to 2 to relieve the known single-event-loop saturation would immediately break all remote MCP clients (claude.ai connectors, Claude Code over HTTP) with intermittent 404s, while REST/frontend traffic keeps working — a confusing partial outage that looks like an MCP bug rather than a scaling misconfiguration.

*수정 스케치*: Until #1 is fixed, add a hard guard: a startup assertion or an admission/policy check that refuses to run with replicas>1 while `/mcp` is mounted, plus a comment in backend.yaml next to `replicas: 1` stating the MCP session-affinity dependency.

**MCP sessions are never reaped — one POST permanently pins a transport and an asyncio.Task** — `backend/mcp_server/http_app.py:63` [high/WASTEFUL]

`_ensure_server_running` (http_app.py:63-82) spawns `asyncio.create_task(run())`; `run()` only unwinds when `transport.connect()`'s streams close, which only happens via `transport.terminate()` on an explicit HTTP DELETE (http_app.py:127-138) or an exception in the server loop. There is no TTL, no idle reaper, and no cap on the number of concurrent sessions per process. Each entry holds a `StreamableHTTPServerTransport` (2 anyio memory object streams + a task group + a `ServerSession`, SDK streamable_http.py:970-990). Clients that disconnect without DELETE (browser tab close, agent crash, network drop) leak forever. Worse, a POST that carries no session header but is not an `initialize` also creates a session before being rejected with 400 'Missing session ID' — so one throwaway request per orphan.

*실패 시나리오*: Any holder of a valid PAT loops `POST /mcp` with a non-initialize body and no `mcp-session-id`: each request creates a permanent transport + task in `_transports`/`_server_tasks` and returns 400. Memory and task count grow without bound until the pod OOMs or the event loop degrades — the same class of symptom as the 2026-06 503 flapping incident. Under multi-replica routing this also becomes self-inflicted: every mis-routed request from finding #1 leaves one orphan on the wrong pod.

*수정 스케치*: Record `last_seen` per session, reap idle sessions on a periodic task (and on server-loop exit), cap sessions per process and per user, and only create the transport when the message actually is an `initialize` request.

**Node proxy blind-retries the original request after any 404 / connection reset — duplicates mutating tool calls** — `packages/akb-mcp-client/lib/proxy.mjs:688` [high/BREAKS_CORRECTNESS]

`_forward` (proxy.mjs:678-720) classifies any error whose message contains 'session', 'Session', '404', 'ECONNREFUSED', 'ECONNRESET' or 'socket hang up' as a session error, resets `this.sessionId`/`_initialized`, re-runs `initialize`, and `continue`s the loop — replaying the *same* JSON-RPC message (including `akb_put`, `akb_update`, `akb_delete`, `akb_sql`) up to 2 extra times. `_http` rejects on any `statusCode >= 400` with a message containing the status code (proxy.mjs:655-657), so the 404 from finding #1 lands squarely in this branch. There is no idempotency key on the MCP wire protocol and `akb_put` is create-only: on a path collision it appends a `-{shortid}` suffix rather than failing (document_service.py:430-436, 462), so a replayed create silently produces a second document instead of erroring.

*실패 시나리오*: Rolling update or LB re-route: proxy sends `akb_put` to pod A; A commits the document to PG+git; the connection is reset before the response is read (pod draining / keep-alive socket reaped). The proxy sees 'socket hang up', re-initializes against pod B, and replays `akb_put` → a second document at `<slug>-a1b2c3d4`. The agent sees one success and never learns a duplicate exists. Same shape applies to `akb_sql` INSERTs, which have no collision suffix at all.

*수정 스케치*: Only retry when the method is provably safe (read tools) or when the failure is a pre-write transport error (ECONNREFUSED before bytes were sent). For write tools, surface the error and let the agent decide, or add a client-generated idempotency key the backend can de-duplicate on.

**Publication password brute-force lockout is an in-memory dict that explicitly assumes single-replica** — `backend/app/services/publication_rate_limit.py:40` [high/BREAKS_CORRECTNESS]

`_by_ip: dict[tuple[str,str], _E]` and `_by_slug: dict[str, _E]` (publication_rate_limit.py:40-41) are module globals. The module docstring states the assumption outright (lines 1-8): 'The backend runs single-replica (one process, one event loop), so a module-global dict is authoritative without cross-process coordination.' It is the only throttle on public-publication password attempts, invoked at `backend/app/api/routes/public.py:451` (`pub_rl.reserve`) and :485 (`pub_rl.release`). Budgets are `_FREE_IP = 5` per (slug, ip) and `_FREE_SLUG = 30` per slug (lines 25-26). Redis is deliberately not used ('Redis is optional here … we deliberately do NOT depend on it').

*실패 시나리오*: With N replicas behind the round-robin Service, an attacker gets N × 5 free attempts per IP and N × 30 per slug before any backoff, and each backoff window only applies to the one replica that issued it — rotating requests across the LB means the attacker effectively never sees a lockout. The security control silently degrades by a factor of N with zero log signal. The defense reduces to bcrypt cost alone.

*수정 스케치*: Move the counters to PG (a small `publication_auth_attempts` table with an upsert + decay window) or to Redis when configured, and keep the in-memory map only as a per-process fast path. Update the docstring, which is currently load-bearing documentation of a constraint nothing enforces.

**DELETE /mcp on the wrong replica reports success while the real session survives elsewhere** — `backend/mcp_server/http_app.py:127` [medium/BREAKS_CORRECTNESS]

The DELETE branch (http_app.py:127-138) only tears down the session if `session_id in _transports` on THIS process, but returns `JSONResponse({"terminated": True})` unconditionally (lines 136-137) regardless of whether anything was found. The authenticated user is also never checked against `_session_users[session_id]` before termination — any valid token holder who learns a session id can terminate someone else's session on the replica that owns it (today a single process, so the id is the only thing standing between them).

*실패 시나리오*: Multi-replica: client sends DELETE to close its session; the request lands on pod B, which owns nothing, returns 200 {'terminated': true}, and the live session + task on pod A leaks forever. The client believes it cleaned up. Feeds directly into the unbounded-leak of finding #3.

*수정 스케치*: Return 404 when the session is unknown to this process, and verify the caller's resolved user matches `_session_users[session_id]` before terminating.

**MCP GET (server→client SSE stream) hard-404s on any replica that does not own the session, with no resumability** — `backend/mcp_server/http_app.py:158` [medium/BREAKS_CORRECTNESS]

The GET branch (http_app.py:158-165) returns `{'error': 'Invalid session'}` 404 whenever the session id is missing from this process's `_transports`. Unlike the POST branch there is no re-create fallback at all. The transport is constructed without an `event_store` (http_app.py:145-148 passes only `mcp_session_id` and `is_json_response_enabled=True`), so the SDK's `Last-Event-ID` replay path is unavailable — a dropped GET stream cannot be resumed, only restarted from a fresh initialize. Note the bundled Node proxy never opens this GET (it is POST-only, proxy.mjs:733-741), so the exposure is limited to spec-complete clients (claude.ai / ChatGPT web connectors, Claude Code remote-MCP).

*실패 시나리오*: A web connector opens the long-lived GET stream; the LB routes it to a pod other than the one holding the session (or the owning pod is rolled) → immediate 404, no server-initiated notifications, and no way to resume — the client must re-run the whole initialize handshake and any server-side progress notifications for in-flight requests are lost.

*수정 스케치*: Fix as part of #1. If sticky sessions are chosen as the interim answer, the affinity key must be the `mcp-session-id` header (not client IP), because GET and POST for one session must reach the same pod.

**Session bootstrap races a fixed 50 ms sleep; losing the race raises an unhandled ValueError → 500** — `backend/mcp_server/http_app.py:81` [medium/BREAKS_CORRECTNESS]

`_ensure_server_running` creates the server task then does `await asyncio.sleep(0.05)` (http_app.py:81-82) as the only barrier before `transport.handle_request` is called at line 155. If the task has not yet reached `transport.connect()` (which is what assigns `_read_stream_writer`, SDK streamable_http.py:983), `_handle_post_request` executes `raise ValueError('No read stream writer available. Ensure connect() is called first.')` (SDK streamable_http.py:446-448). Nothing in `MCPApp.__call__` catches it, so it escapes as an unhandled ASGI exception. This is not replica-count-dependent, but it fires on every cold process, and 50 ms is exactly the kind of margin the known Kiwi/GIL event-loop stall erases.

*실패 시나리오*: During a pod's first seconds (or any event-loop stall >50 ms — the documented 2026-06 incident class), a client's `initialize` POST hits the 500 path instead of getting a session. With N replicas, N cold starts per deploy each get their own window; the Node proxy's retry classifier does NOT treat '500' as a session error (proxy.mjs:688-694), so the failure propagates to the agent as a hard error.

*수정 스케치*: Replace the sleep with an `asyncio.Event` the `run()` coroutine sets immediately after `transport.connect()` yields, and `await` it (with a timeout) before delegating; wrap `handle_request` in a try/except that maps the ValueError to a clean 503.

**Every PAT-authenticated request performs an UPDATE on the same tokens row** — `backend/app/services/auth_service.py:1161` [medium/WASTEFUL]

`_resolve_pat` collapses fetch+touch into `UPDATE tokens t SET last_used_at = NOW() … RETURNING …` (auth_service.py:1161-1174). It is deliberate (the comment explains it closes a revoke race), but it means every single authenticated request — REST and MCP alike — takes a row-exclusive lock on one `tokens` row and writes WAL. Today the single event loop naturally serializes these; across processes they become genuine cross-backend row-lock contention on the hottest row for any shared agent PAT.

*실패 시나리오*: With N replicas and one agent PAT driving high MCP traffic, concurrent requests on different pods block each other on the same `tokens` row lock. Throughput on that credential is capped by PG row-lock round-trips regardless of how many replicas are added, and the write amplification (1 UPDATE + WAL per API call) hits the same PVC-backed Postgres.

*수정 스케치*: Throttle the touch: only UPDATE when `last_used_at < NOW() - interval '1 minute'` (a WHERE clause on the same statement keeps the revoke-race property for the read while skipping most writes), or move `last_used_at` to a best-effort async write.

**Each MCP tool call resolves the bearer token twice (two DB round trips, two last_used_at writes)** — `backend/mcp_server/server.py:114` [low/WASTEFUL]

`MCPApp.__call__` already calls `resolve_token(auth_header)` for the auth gate (http_app.py:115) and stores the result in `_session_users` (line 150). But `_session_users`/`get_session_user` (http_app.py:58-60) is dead code — grep across backend/ and packages/ finds the definition and zero call sites. Instead, `call_tool` re-resolves from scratch on every dispatch via `_get_user()` (server.py:114-136, invoked at server.py:1391), which pulls the Authorization header off `server.request_context.request` and calls `resolve_token` again. So each MCP tool call costs two full token resolutions — and, for PATs, two of the row-locking UPDATEs from the previous finding.

*실패 시나리오*: At N replicas the wasted PG load scales linearly with total MCP traffic: 2× auth queries and 2× `tokens` row writes per tool call, all landing on the single Postgres that is already the shared bottleneck. Also a latent correctness smell: the per-session cached user (`_session_users`) and the per-request re-resolved user can diverge (e.g. token revoked mid-session), and only the re-resolved one is authoritative.

*수정 스케치*: Either delete `_session_users`/`get_session_user` as dead code and keep the per-request resolve as the single authority (documented as intentional so revocation takes effect immediately), or pass the already-resolved user through the request scope. Do not cache it per session without a revocation check.

**Keycloak JWKS and its httpx client are cached per-process with no TTL or shared refresh** — `backend/app/services/keycloak_oidc.py:102` [low/WASTEFUL]

`KeycloakOIDC` is a lazy module-level singleton (keycloak_oidc.py:366-374) holding `self._jwks` (line 102) and a dedicated `httpx.AsyncClient` (lines 106-115). `_fetch_jwks` caches indefinitely and only refetches on `force=True` (lines 221-233), which happens on a `kid` miss during ID-token verification (lines 263-264) and access-token verification (lines 328-331). Correctness is preserved across replicas — key rotation self-heals per process — but the cost and the connection pool are duplicated N times.

*실패 시나리오*: On a Keycloak key rotation with N replicas and heavy MCP-OAuth traffic, every replica independently discovers the kid miss and force-refetches, and there is no in-process single-flight guard either — concurrent verifications on one replica can each trigger their own force fetch, producing a burst of JWKS requests at the IdP proportional to N × concurrency rather than N.

*수정 스케치*: Add a short TTL plus an asyncio.Lock single-flight around `_fetch_jwks(force=True)`. Cross-replica sharing is not required.

**OIDC CSRF state, PKCE verifier, and one-time exchange codes are stored in Postgres with atomic single-use consumption** — `backend/app/services/keycloak_oidc.py:78` [info/ALREADY_SAFE]

This was clearly designed for multi-replica already. `_store_issue` (keycloak_oidc.py:62-75) inserts into the `oidc_transients` table with a TTL; `_store_consume` (lines 78-94) is a single `DELETE … WHERE key=$1 AND kind=$2 AND expires_at > NOW() RETURNING payload`, which makes redemption atomic and exactly-once even under concurrent callbacks from different pods. `begin_login` stores the `state` + `code_verifier` there (lines 154-176), `consume_state` reads it (178-180), and `issue_exchange_code`/`redeem_exchange_code` (380-394) do the same for the post-login one-time code. The module docstring states the intent explicitly at lines 22-25 ('persisted in the `oidc_transients` table so the redirect round-trip works across multiple backend replicas'). No in-memory nonce/PKCE/code store exists anywhere in this path.

*실패 시나리오*: None. The login redirect can begin on pod A and complete on pod B; a replayed `state` or exchange `code` returns 0 rows on the second attempt and is rejected (auth.py:291-294 → 'invalid_state'; auth.py:347-351 → 400).

**Tokens are stateless: HS256 JWT + hashed PAT rows + HMAC share tokens, all keyed on the shared jwt_secret** — `backend/app/services/auth_service.py:112` [info/ALREADY_SAFE]

AKB session tokens are self-contained HS256 JWTs signed with `settings.jwt_secret` (create_jwt at auth_service.py:112-133, decode at 136-141), verifiable by any replica. ## Git worktree + storage as the hard scaling blocker (multi-process / multi-pod duplication of backend/app/services/git_service.py)

On-disk layout is one **bare** repo per vault at `/data/vaults/{vault}.git` (git_service.py:76-78, :178) plus **one shared persistent linked worktree** per vault at `/data/vaults/_worktrees/{vault}` (git_service.py:73-74, :79-80, :131-169). Every read op goes to the bare repo's object store with **no lock at all** (`_get_repo`, git_service.py:82-86; read_file :494, vault_log :847, file_diff :929, cat_blob :483, ls_tree :436); every write op mutates the single shared worktree under a **process-local `threading.Lock`** (`_VAULT_LOCKS`, git_service.py:43-53). That lock is the only thing making AKB's write operation atomic, because each AKB write is a 5-6 command git sequence (`reset --hard` → `add`/`rm`/`mv` → `write-tree` → `rev-parse HEAD` → `commit-tree -p HEAD` → `update-ref HEAD`, git_service.py:589-602, :113-129) and git's own `index.lock` is held **per-command, not per-sequence** — so even a perfectly POSIX filesystem gives zero protection between the commands. Duplicating this code into a second process (uvicorn `--workers 2`, or a second pod on an RWX volume) is therefore not a scaling step but a silent-corruption step: interleaved `reset --hard` discards another writer's staged blob, `write-tree` commits a foreign writer's staged files under the wrong message, and `update-ref HEAD` (git_service.py:128) has **no `--old-value` compare-and-swap**, so it unconditionally overwrites a peer's just-created commit and orphans it. The loss is initially invisible because reads are pinned to `documents.current_commit` (document_service.py:597) and unreachable objects still resolve — until git's default `gc --auto` (triggered by the `fetch` on mirror vaults, git_service.py:395; no `gc.auto` override anywhere in the repo) prunes them weeks later. A PG advisory lock or an OS flock *can* replace `_VAULT_LOCKS`, but only if it also covers the four unlocked/partially-locked paths (`cleanup_stale_locks` at lifecycle.py:79, `_ensure_worktree`'s prune-retry at git_service.py:151-167, `cleanup_vault_dirs`' rmtree vs. lock-free readers at git_service.py:307-310, and `fetch_remote`'s out-of-lock network fetch at git_service.py:392-398) — and even then the ref update still needs CAS. The volume itself is `ReadWriteOnce` with `strategy: Recreate` (deploy/k8s/backend.yaml:78, :85-86, :172-173), so multi-pod is physically blocked today; moving to NFS-like semantics breaks git's `O_CREAT|O_EXCL` lockfile atomicity first (silently, both nodes "win" `index.lock`), then attribute-cache staleness on refs/loose objects. Separately, git and Postgres can already diverge on crash in a single process: `put`/`update` commit to git *before* the enclosing PG transaction commits (document_service.py:491 vs :516; :850 vs :858) with no reconciler for that direction.

**One shared worktree + a 6-command non-atomic git sequence guarded only by a process-local threading.Lock** — `backend/app/services/git_service.py:579` [blocker/BREAKS_CORRECTNESS]

`commit_file` (:579-602), `delete_file` (:613-632), `move_file` (:652-679) and `delete_paths_bulk` (:711-739) all take `_vault_lock(vault_name)` — a **process-local** `threading.Lock` from the module dict `_VAULT_LOCKS` (:43-53) — then operate on the SINGLE shared worktree path `<storage>/_worktrees/<vault>` (:79-80, :131-169). Inside that lock each write runs an independent sequence of git subprocesses: `reset --hard HEAD` (:589), `add`/`rm`/`mv` (:595/:625/:672), then `_stage_and_commit` → `write-tree` (:113), `rev-parse --verify HEAD` (:116), `commit-tree -p HEAD` (:120), `update-ref HEAD` (:128). Git's own `index.lock` is acquired and released by EACH of those commands individually — it never spans the sequence. Note also that `write-tree` (:113) serializes the WHOLE index, not just the caller's path, so a peer's staged file is silently swept into this writer's commit and commit message. The path-level PG advisory lock (`acquire_path_lock`, backend/app/repositories/document_repo.py:15-36) does NOT help: it is keyed on `(vault_id, path)`, so two writers to two DIFFERENT paths in the SAME vault hold different advisory locks and both enter the same worktree.

*실패 시나리오*: Two backend processes (uvicorn --workers 2, or two pods on an RWX volume). Process A: akb_put of docs/a.md → `reset --hard HEAD`, writes a.md, `git add a.md`. Process B (different path, so a different PG advisory lock) starts one millisecond later: `reset --hard HEAD` — which resets index AND working tree to HEAD, discarding A's staged a.md and deleting the file. A then runs `write-tree` and gets a tree WITHOUT a.md, `commit-tree`, `update-ref`, and returns a real commit sha. document_service.py:516 writes `documents.current_commit = <that sha>` and PG commits. akb_get for docs/a.md then calls read_file(vault, 'docs/a.md', current_commit) (document_service.py:597) → the blob is not in that tree → returns None → the API 404s ('Document file not found') for a document PG says exists, and the user's content is gone with no error ever logged. The symmetric case (A's `git add` lands between B's `add` and B's `write-tree`) publishes A's private draft inside B's commit under B's commit message and author.

*수정 스케치*: Replace `_vault_lock` with a cross-process lock held for the ENTIRE sequence: either `pg_advisory_lock(hashtext('akb:git:'||vault))` on a dedicated connection acquired in `write_lane(vault)` before dispatching to the commit executor, or `flock(LOCK_EX)` on `<storage>/<vault>.git/akb-write.lock` taken inside GitService (flock fences better — it dies with the process). Every mutator must take it, including the ungated worker paths. Longer term, drop the shared worktree entirely: build the tree with `git hash-object -w` + `git update-index --cacheinfo` against a per-request temporary index (`GIT_INDEX_FILE`), which needs no working tree and no cross-process worktree state at all.

**`update-ref HEAD` performs no compare-and-swap — a concurrent commit is silently orphaned** — `backend/app/services/git_service.py:128` [blocker/BREAKS_CORRECTNESS]

`_stage_and_commit` reads the parent with `rev_parse --verify HEAD` (:116), builds the commit with `commit-tree ... -p HEAD` (:120), then advances the branch with `work_repo.git.update_ref("HEAD", commit_sha)` (:128). There is no `--old-value <sha>` argument, so this is an unconditional write, not a CAS. This is a distinct defect from the worktree race: it stays broken even if each pod is given its own private worktree, because all worktrees and the bare repo share one `refs/heads/<branch>`. No `gc.auto` override exists anywhere in the repo (verified: no `gc.auto`/`GIT_CONFIG`/`gitconfig` in backend/ or deploy/), so git's default auto-gc applies, and `fetch_remote` (:395) runs `git fetch` — a porcelain command that triggers `gc --auto` — on every mirror vault sync.

*실패 시나리오*: Processes A and B both resolve `HEAD` = C0. A commits C1 and runs `update-ref HEAD C1`. B commits C2 (parent C0) and runs `update-ref HEAD C2`. The branch now points at C2; C1 is unreachable. A's document row still has `current_commit = C1`, and because reads are commit-pinned (document_service.py:597 reads `read_file(vault, path, row['current_commit'])`) the doc STILL READS CORRECTLY — the corruption is completely invisible. Meanwhile `akb_activity` / `vault_log` (git_service.py:847) and `akb_history` walk from HEAD and show A's edit as never having happened, and the next `reset --hard HEAD` deletes A's file from the worktree so a later akb_delete of it degrades to DB-only cleanup (document_service.py:1331-1335). Then, up to two weeks later, a mirror-vault `git fetch` fires `gc --auto`, C1 and its blob are pruned, and every read of A's document starts returning 404 — with no event, log line, or correlation to the write that actually lost it.

*수정 스케치*: `update_ref('HEAD', commit_sha, old_head_sha)` (GitPython maps positional args to `git update-ref <ref> <newvalue> <oldvalue>`), capturing `old_head_sha` from the same `rev-parse` used for `-p`. On mismatch, raise a retryable conflict so the write lane can re-run the whole reset/stage/commit sequence. This is the minimum required for ANY multi-writer topology and is cheap enough to add today.

**`cleanup_stale_locks()` runs unlocked at every process start and will delete a live peer's index.lock** — `backend/app/services/git_service.py:206` [high/BREAKS_CORRECTNESS]

`cleanup_stale_locks` (:206-275) iterates EVERY `<storage>/*.git` dir and unlinks `index.lock` files older than 60s (:263-266), and it takes no vault lock at all. Its own docstring (:229-234) states the safety argument explicitly: 'the only write paths that touch a worktree's index hold `_vault_lock(vault_name)` per-vault, so startup self-heal — which runs before workers — cannot remove a lock held by a live operation.' That argument is *entirely* process-local and is void the moment a second process exists. It is called on every boot from `init_storage` (backend/app/services/lifecycle.py:78-83), i.e. on every pod start, rollout, restart, and crash-loop iteration. The 60s age threshold is the only remaining defense; the write-path bound is `git_write_timeout_secs = 30.0` (backend/app/config.py:512), which is under 60s but only by 2x, and that bound is a `kill_after_timeout` that does not apply to a process blocked in uninterruptible I/O on a stalled network filesystem.

*실패 시나리오*: Pod-2 starts (rollout, HPA scale-up, or OOM-restart) while pod-1 is mid-`git add` on vault X whose index.lock is >60s old because the CephFS MDS is stalled (the exact incident class already recorded for this deployment). Pod-2's `init_storage` unlinks pod-1's LIVE index.lock. Pod-1's git command finishes and renames its temp index over `index`; a second writer that meanwhile created its own index.lock and wrote its own index gets its write silently overwritten. The resulting index is one writer's view with the other's rename layered on top — the classic 'both git processes think they own the index' corruption, which surfaces later as a `write-tree` producing a tree missing files, or `git status` reporting phantom deletions of files that are present on disk.

*수정 스케치*: Gate the sweep behind the same cross-process vault lock the write path takes (try-lock, skip the vault if held), or move it out of per-pod startup entirely into a leader-elected/one-shot init container. At minimum, key the removable set on locks whose owning PID is provably dead rather than on wall-clock age.

**`_ensure_worktree`'s `worktree prune` retry can delete a peer's in-flight worktree registration** — `backend/app/services/git_service.py:151` [high/BREAKS_CORRECTNESS]

`_ensure_worktree` checks `if (wt / '.git').exists(): return wt` (:140-141), then runs `git worktree add <wt> <branch>` (:151). On a GitError containing 'already registered' it runs `git worktree prune` and retries the add (:159-167). `git worktree add` is not atomic: it writes `<bare>/worktrees/<name>/` metadata, then creates the worktree directory and its `.git` gitdir-pointer file. `git worktree prune` reaps registrations whose worktree directory/gitdir pointer is missing — which is exactly the transient state a concurrent `worktree add` is in. The comment at :153-158 correctly identifies the SIGKILL/OOM origin of stale registrations, but the recovery is unsafe once two processes can call it concurrently.

*실패 시나리오*: Two pods take their (process-local, therefore non-excluding) vault locks and both call `_ensure_worktree` for a vault whose worktree does not yet exist. Pod-1 wins the add and is between writing `<bare>/worktrees/<vault>/` and creating `<wt>/.git`. Pod-2's add fails with 'already registered', so pod-2 runs `git worktree prune`, which sees pod-1's registration with no valid gitdir and deletes `<bare>/worktrees/<vault>/`. Pod-1 finishes and returns a worktree whose administrative directory no longer exists; its subsequent `reset --hard`/`add` fail with 'fatal: not a git repository' or corrupt the bare's worktree bookkeeping, and every write to that vault 500s until an operator manually runs `worktree prune` + `rm -rf`.

*수정 스케치*: Hold the cross-process vault lock across the whole `_ensure_worktree` body (it already documents 'Callers must hold the vault lock' at :136 — that must become a cross-process lock), and never call `worktree prune` while another process could be mid-add. Or eliminate the worktree (temporary-index approach) so there is no registration to race on.

**`cleanup_vault_dirs` rmtree's the bare repo while lock-free readers hold it open** — `backend/app/services/git_service.py:307` [high/BREAKS_CORRECTNESS]

`cleanup_vault_dirs` takes `_vault_lock(vault_name)` and `shutil.rmtree`s both `<storage>/<vault>.git` and `<storage>/_worktrees/<vault>` (:307-310). Its docstring (:298-304) explicitly justifies the lock as protecting against a racing `clone_mirror`/`fetch`/`commit`. But NO read path takes that lock: `read_file` (:494), `list_files` (:515), `ls_tree` (:436), `cat_blob` (:483), `file_log` (:813), `vault_log` (:847), `file_diff` (:929), `diff` (:983) and `last_commit_for_path` (:454) all go straight through `_get_repo` (:82-86) with no lock. Callers include `document_service.get` (:597), the activity routes (backend/app/api/routes/activity.py:73, :193), and `resource_integrity.repair_resource_hashes` (backend/app/services/resource_integrity.py:99). It is invoked from three places: vault delete (backend/app/services/access_service.py:1628), create-vault rollback (backend/app/services/document_service.py:1879), and — the dangerous one — the mirror self-heal path `external_git_service.py:133-134`, which rmtree's and immediately re-clones a vault that is otherwise fully live and serving reads.

*실패 시나리오*: Even in ONE process this is unguarded for readers; with two processes it also races writers. Concretely: pod-1's external_git poller decides vault X's bare is 'untrusted' (external_git_service.py:127-134) and rmtree's `<storage>/X.git` while pod-2 is streaming a blob for an `akb_get` — the reader gets an IOError/`BadObject` mid-stream and the request 500s. Worse, pod-2's write lane is concurrently committing to X's worktree (pod-1's `_vault_lock` does not exclude pod-2): pod-2's `update-ref` writes into a directory tree that is being deleted, producing a half-deleted bare with a ref pointing at objects that no longer exist. The subsequent `clone_mirror` at :134 then re-populates the directory, and `vault_exists()` reports True forever after, so the self-heal never fires again on the now-genuinely-corrupt repo.

*수정 스케치*: Take the cross-process vault lock on the read path too (a shared/read flock is enough — readers exclude only the rmtree, not each other), and make destructive cleanup a rename-then-delete: `os.rename('<vault>.git', '<vault>.git.deleting-<uuid>')` under the exclusive lock, then rmtree the renamed dir out of band. Renaming is atomic and leaves already-open file descriptors valid on POSIX.

**`fetch_remote` runs the network fetch outside the vault lock; the external-git re-clone path can rmtree underneath it** — `backend/app/services/git_service.py:392` [medium/BREAKS_CORRECTNESS]

`fetch_remote` deliberately performs `git fetch` into `refs/akb/fetch-tmp/<branch>` OUTSIDE the lock (:392-398, justified at :376-383 as 'idempotent and append-only; safe to race'), acquiring `_vault_lock` only for the ref move (:403-410). The append-only argument holds for object writes between two fetchers, but it does not hold against `cleanup_vault_dirs` (:277-310), which deletes the whole bare directory. Within one process the poller is the only fetcher and it holds a SKIP LOCKED claim, so no overlap occurs. Across processes, the claim's exclusion window is time-based (`external_git_claim_lookahead_secs = 3600`, backend/app/config.py:114) rather than a held lock, and `cleanup_vault_dirs` is reachable from delete-vault and create-rollback on any pod at any time.

*실패 시나리오*: Pod-1 is 4 minutes into a 900s bootstrap `clone_mirror` (git_service.py:349-356) or a 300s `fetch_remote` for mirror vault M. An admin issues akb_delete_vault for M against pod-2, which runs the PG cascade and then `run_git_write(GitService().cleanup_vault_dirs, ...)` (access_service.py:1628). Pod-2's `_vault_lock` is a different lock object from pod-1's, so the rmtree proceeds while pod-1's git child process is writing packfiles into the directory being deleted. Result: partially written pack/tmp files left in a recreated directory (clone_mirror recreates it at :346-356), a bare repo that `is_healthy_repo` may or may not catch, and — if a same-named vault is recreated — `init_vault` raising FileExistsError (:176-177) against the leftovers.

*수정 스케치*: Same cross-process lock as the other findings, but taken in SHARED mode for `fetch_remote`'s network phase (allowing concurrent readers/fetchers) and EXCLUSIVE for `cleanup_vault_dirs`. Additionally make the external-git claim hold a `pg_advisory_lock` for the duration of reconcile rather than relying on a 3600s lookahead push-out.

**Write-lane admission control is entirely process-local — capacity and backpressure become N× lies** — `backend/app/services/write_lane.py:75` [high/WASTEFUL]

**RWO PVC + `strategy: Recreate` makes >1 replica physically impossible; NFS-like RWX would break git's lockfile atomicity first** — `deploy/k8s/backend.yaml:172` [blocker/BREAKS_CORRECTNESS]

`akb-vaultdata` is `accessModes: [ReadWriteOnce]` (:172-173), mounted at `/data/vaults` (:111), matching `git_storage_path: /data/vaults` (deploy/k8s/backend.yaml ConfigMap; backend/app/config.py:103). `replicas: 1` (:78) and `strategy: Recreate` (:85-86) exist specifically because RWO cannot multi-attach (comment at :79-84). backend/Dockerfile:17 is `CMD ["uvicorn", "app.main:app", ...]` with no `--workers`, so even in-pod there is exactly one process. What git requires from the filesystem: (a) `O_CREAT|O_EXCL` create of `index.lock`, `<ref>.lock`, `packed-refs.lock` must be atomic and mutually exclusive ACROSS NODES; (b) `rename()` over an existing file must be atomic (index, refs, packfiles); (c) the index's cached stat data (dev/ino/ctime/mtime) must be stable and consistent per file; (d) close-to-open consistency for loose objects and refs.

*실패 시나리오*: Switching to NFS RWX breaks (a) first and silently: on NFSv3, O_EXCL create is not reliably atomic (the classic link()-count workaround), so two nodes both 'acquire' `index.lock` and both proceed to rewrite `index` — with no error on either side. Second to break is (c): st_dev/st_ino differ per client mount and attribute caching (acregmin/acregmax, default up to 60s) makes the index's stat cache useless, so `reset --hard` and `add` re-stat and re-read everything (slow) and git's 'racily clean' heuristics can mis-classify a file as unchanged when it was just rewritten. Third is (d): a reader on node B can get a cached negative dentry for a loose object node A just wrote, surfacing as a spurious `BadObject`/'object not found' 500 on an akb_get. CephFS is materially better (real cross-client flock/fcntl, strong consistency, no attribute-cache staleness) and would satisfy (a)-(d) — but it still does NOT fix findings 1 or 2, because git's per-command index.lock never spans AKB's multi-command write sequence and `update-ref` has no CAS. Filesystem choice is necessary but not sufficient.

*수정 스케치*: Do not attempt RWX/NFS. If multi-pod is the goal, the correct decomposition is: keep the volume single-writer and make git writes go through a single dedicated git-writer Deployment (replicas:1, owning the PVC) that the API replicas call; or eliminate the shared working tree with a temporary-index/`hash-object` write path plus `update-ref --old-value` CAS, and put the vault write lock in Postgres. Either way, `update-ref` CAS (finding 2) is a prerequisite, not an optimization.

## search / vector / indexing pipeline under multiple processes

The core queue mechanics are genuinely multi-process-safe: `chunks` is the queue, `embed_worker._claim_batch` claims with `FOR UPDATE SKIP LOCKED` + a 10-minute lease (embed_worker.py:60-81), the pre-upsert `SELECT 1 ... FOR UPDATE` re-check (embed_worker.py:220-229) closes the upsert-vs-delete race with a PG row lock rather than a process-local one, the delete outbox uses the same claim shape (delete_worker.py:45-66), `recompute_stats` is guarded by `pg_try_advisory_lock` (sparse_encoder.py:585-599), and pgvector's `ensure_collection` uses `pg_advisory_xact_lock` + an atomic index swap (pgvector.py:274-277). Duplicating the process does not corrupt that path. What does break is everything that lives in Python module globals: `sparse_encoder._stats_cache` (60s TTL, invalidated only in the winning process) is baked into *persisted* document weights by `encode_document`, so two processes indexing chunks of the same corpus during a stats transition write non-comparable saturated-TF values; `vault_backfill._ready` is a per-process latch that selects between two search code paths whose archived-document semantics actually differ, so the same query returns different result sets on different replicas; and `index_table_metadata` / `index_file_metadata` replace a source's whole chunk set on a bare autocommit connection with no lock and no transaction, which both violates the outbox-atomicity invariant that `_drop_source_chunks_with_outbox` documents and lets two processes interleave into duplicate stale chunk sets. `indexing_concurrency=1` is not a correctness constraint — it is a budget knob whose documented rationale (embedding-API rate limit, PG pool) is per-process and silently becomes replicas x N with no global admission control. The eager-`ensure_collection`-at-startup mitigation is per-process and therefore not a mitigation at all cross-process; it only survives because pgvector (the shipped driver) holds a real advisory lock, while qdrant/seahorse have no cross-process guard by their own admission in base.py:184-198. Structurally, there is no way to run an API-only replica: `start_workers()` is unconditional in main.py:41, and the `AKB_DISABLE_WORKERS` / `app.worker_main` split that lifecycle.py:3 claims exists does not exist in the tree.

**Table/file chunk reindex replaces the whole chunk set with no transaction and no lock** — `backend/app/services/table_service.py:538` [blocker/BREAKS_CORRECTNESS]

`index_table_metadata` (table_service.py:538-544) and `index_file_metadata` (file_service.py:646-652) and `delete_table_index` (table_service.py:549-551) acquire a bare `pool.acquire()` connection with NO `conn.transaction()` wrapper, then call `write_source_chunks` / `delete_table_chunks`, which call `_drop_source_chunks_with_outbox` (index_service.py:476-492). That helper's docstring is explicit: "The outbox enqueue and the PG DELETE MUST commit atomically ... Any failure in enqueue now raises and rolls back the caller's transaction." At these three call sites there is no caller transaction, so asyncpg runs each `execute` in its own implicit transaction — the outbox INSERTs commit independently of the chunks DELETE, and each of the N per-chunk INSERTs in write_source_chunks (index_service.py:570-582) commits independently. Separately, both call sites are invoked OUTSIDE the DDL transaction that protects the table (table_service.py:750-762 comment: "Outside the create transaction on purpose"; table_service.py:1476-1489 is dedented out of the `async with` block), and neither takes the `pg_advisory_xact_lock` that documents get via `acquire_path_lock` (document_repo.py:32-36). So there is no cross-process serialization on (source_type, source_id) for tables and files at all.

*실패 시나리오*: Two `akb_alter_table` calls for table T land on replica A and replica B. Both finish their DDL, then both call index_table_metadata concurrently. A: SELECT chunk ids -> sees {C0}; INSERT outbox(C0) [commits]; DELETE chunks C0 [commits]; INSERT chunk A1 [commits]. B's SELECT lands in the window after A's DELETE and before A's INSERT: it sees zero rows, enqueues nothing, deletes nothing, and INSERTs chunk B1. The chunks table now holds BOTH A1 and B1 for table T, carrying two different schema snapshots. embed_worker indexes both into the vector store as two distinct chunk_ids. Search dedups by (source_type, source_id) (search_service.py:415-424), so whichever ranks higher wins — the user can be shown the pre-ALTER schema indefinitely, and the stale chunk permanently inflates BM25 df. Second failure: the outbox INSERT commits, the chunks DELETE then fails (deadlock, statement timeout, conn drop). Outbox rows now point at chunk ids that still exist and are still marked vector_indexed_at NOT NULL; delete_worker drains them and removes LIVE points from the vector store (delete_worker.py:107-112), silently making that table or file unsearchable with no error anywhere.

*수정 스케치*: Wrap both helpers in `async with conn.transaction():`, and take `pg_advisory_xact_lock` keyed on (vault_id, source_id) as the first statement — the same pattern documents already use via document_repo.acquire_path_lock. Better: move the reindex INSIDE the create/alter transaction that already holds the table lock, or push it onto the chunks queue as a job rather than doing it inline.

The two branches are NOT semantically equivalent. The source-id branch appends `d.status != 'archived'` when `include_archived` is False (search_service.py:319-320, comment: "Default-hide archived documents from discovery"). The vault branch (search_service.py:237-253) only resolves accessible vault ids and passes them to the driver, which filters on `vault_id` alone (pgvector.py:625-627); `_hydrate_hits` (search_service.py:568+) joins `documents` with no status predicate. Archiving a document does not delete its chunks — `document_service.update` only rewrites chunks when `req.content is not None` (document_service.py:870-886) — so archived docs keep live, indexed chunks. `vault_path_eligible` (search_service.py:90-106) does not consider `include_archived` at all. In a single process this is a latent bug; with N processes it becomes nondeterministic, because each process latches `_ready` independently on its own 60s `vault_backfill` tick (vault_backfill.py:156).

*실패 시나리오*: Rolling restart of 3 replicas. Replica A's vault_backfill tick has fired and latched `_ready=True`; replicas B and C have not yet. A user runs the same `akb_search("deprecation plan", vault="eng")` three times. The request that lands on A returns archived documents mixed into the results; the requests that land on B and C do not. Refreshing the page changes the result set with no user-visible cause, and there is no `degraded` flag (search_service.py:458-459) because neither path failed.

*수정 스케치*: Two separate fixes. (1) Add `include_archived` to `vault_path_eligible`'s inputs so an archived-hiding search is never eligible for the vault path — or add an archived filter to the vault path's hydration. (2) Move readiness out of process memory: store the latch in PG (a row in a small settings/flags table) so every replica reads the same value, or gate on `vault_backfill_pending() == 0` read fresh with a short shared cache.

**BM25 corpus stats are a process-local 60s cache and are BAKED INTO persisted document weights** — `backend/app/services/sparse_encoder.py:387` [high/BREAKS_CORRECTNESS]

`_stats_cache` is a module global with a 60s TTL (sparse_encoder.py:386-406). `_invalidate_stats_cache()` (line 409-411) is called only inside `recompute_stats` (line 676) — i.e. only in the ONE process that won the advisory lock at line 586-588. Every other process keeps serving its stale tuple until its own TTL expires. Two consumers matter. (a) Query side: `encode_query` reads `total_docs` from the cache to compute IDF (line 544-557), and has a hard branch at line 546-547 returning uniform 1.0 weights when `total_docs <= 0`. On the seahorse drivers the cached `(total_docs, avgdl, k1, b)` is shipped verbatim to Coral as the server-side BM25 parameters (seahorse_db.py:542-562; seahorse_db_grpc.py:393-429), so the whole BM25 formula is parameterized by per-process state. (b) Document side — the durable one: `encode_document` reads `avgdl`, `k1`, `b` from the same cache (line 487-493) and bakes them into the saturated TF that is WRITTEN to the vector store (line 500-514, `dl_norm = 1 - b + b*(dl/avgdl)`). Those weights are persisted, not recomputed at query time.

*실패 시나리오*: A bulk import moves total_docs from 100k to 400k and avgdl from 180 to 420; the recompute runs in replica A, which invalidates only its own cache. For the next 60s replicas B and C encode incoming chunks with avgdl=180 while A encodes with avgdl=420. Every chunk indexed in that window by B/C carries a saturated-TF roughly 2x the value an A-indexed chunk of identical text gets, and those numbers sit in `akb_vectors.chunks.sparse_weights` forever — the sparse leg now systematically over-ranks whichever replica happened to index a document. Query-side, in the same window a search hitting A and the same search hitting B produce different IDF vectors and can return different top-10 orderings. Worst case: a freshly-started replica whose bootstrap recompute lost the advisory lock (sparse_encoder.py:590-599 returns skipped) and whose first `load_stats()` hit a table with total_docs=0 serves uniform-1.0 query weights (line 546-547) — BM25 collapses to raw term presence on that one replica, with no degraded flag.

*수정 스케치*: Key the cache on a version/`updated_at` column read cheaply (or a PG NOTIFY on recompute) so every process invalidates together. For the doc-encode path specifically, either drop the cache entirely for `encode_document` (one extra indexed single-row read per chunk batch, not per chunk) or record the (avgdl,k1,b) generation on the chunk row so a stats change can trigger a re-encode instead of silently mixing conventions.

**indexing_concurrency is a per-process knob whose documented budget rationale assumes a single process** — `backend/app/config.py:484` [high/WASTEFUL]

The comment at config.py:480-484 states the reason for the default of 1: "Workers coordinate via FOR UPDATE SKIP LOCKED, so N can be raised until the embedding API's rate limit or PG pool budget caps it. 1 keeps the legacy single-task behavior; 4-8 is the typical production knob." So the default is conservatism, not a correctness constraint — and the claim about SKIP LOCKED is accurate (embed_worker.py:60-81) and survives multi-process unchanged. What does NOT survive is the budget reasoning. `BackfillRunner` spawns `concurrency` sibling asyncio tasks inside ONE process (_backfill.py:69-71), and `embed_worker._runner` reads the setting at import time (embed_worker.py:263-267). Every replica runs its own runner because `start_workers()` is unconditional (main.py:41, lifecycle.py:115-116). The only outbound cap is `httpx.Limits(max_connections=100)` in the shared client (http_pool.py:26) — also per-process. `write_lane`'s admission semaphore is a process-local `asyncio.Semaphore` (write_lane.py:80, 105-108) and does not cover the embed path at all. There is no PG-side or Redis-side global concurrency counter anywhere in the embedding path.

*실패 시나리오*: An operator reads the config comment, sets indexing_concurrency: 8 for the documented '4-8 typical production' value, then scales the Deployment to 4 replicas to fix the event-loop stall. Effective embedding concurrency is now 32 in-flight batches of up to 32 inputs each (index_service.py:434-439) = up to 1024 concurrent inputs against an endpoint sized for 8 batches. The gateway starts returning 429; in `platform_hard` governance mode 429 is classified transient (index_service.py:370-374), so the whole batch is returned as empty embeddings, every row takes a `_mark_failure` retry increment (embed_worker.py:98-115), and after 8 retries (BACKOFF_SECS, _backfill.py:23-24) the chunks are 'abandoned' and eventually reaped (delete_worker.py:212-268) — documents silently drop out of dense search. No single process can observe or throttle the aggregate.

*수정 스케치*: Either document the knob as per-process and give operators a replicas x concurrency worksheet, or move admission to a shared resource: a PG advisory-lock pool (N numbered keys, try-lock to acquire a slot) or a Redis token bucket in front of `generate_embeddings`. At minimum, log effective concurrency and the replica identity at startup so the aggregate is discoverable.

**ensure_collection eager-init at startup is a per-process mitigation and does not serialize N processes** — `backend/app/services/lifecycle.py:87` [medium/WASTEFUL]

The mitigation comment (lifecycle.py:87-92) is scoped to one process: "N concurrent embed_workers all racing to be the first caller of ensure_collection can exhaust the main PG pool ... Doing it once here, single-threaded, sidesteps the cold-start contention." That reasoning is about a single process's connection pool, so it does not transfer. With N processes, the eager init runs in N processes at the SAME instant (Recreate strategy, deploy/k8s/backend.yaml:85-86, brings all pods up together) — which is the worst case for the race, not a mitigation. What actually saves the shipped configuration is pgvector's `pg_advisory_xact_lock` (pgvector.py:274-277), which is genuinely cross-process and auto-releases on rollback so a cancelled CREATE INDEX cannot strand it. The real remaining races: (1) `CREATE EXTENSION IF NOT EXISTS vector` at pgvector.py:269 executes in AUTOCOMMIT, BEFORE the transaction that takes the advisory lock — and the class's own comment at pgvector.py:124-129 says exactly this kind of IF-NOT-EXISTS DDL "are not race-safe at the catalog level"; the same applies to `_bootstrap_extension` (pgvector.py:167-178) on the separate-DSN path. (2) Non-pgvector drivers have NO cross-process guard whatsoever: qdrant uses only `_ensured_collection` + `collection_exists()` (qdrant.py:76-130), seahorse_db uses an `asyncio.Lock` + GET/POST catalog (seahorse_db.py:145-200), seahorse_cloud likewise (seahorse_cloud.py:171-200). base.py:184-198 already flags all three as unaudited, and base.py:164-166 already states the requirement: "Concurrent callers serialize, in-process AND cross-process."

*실패 시나리오*: Fresh database, 3 pods start simultaneously under Recreate. All three run `CREATE EXTENSION IF NOT EXISTS vector` in autocommit at pgvector.py:269 within milliseconds of each other. Two get `duplicate key value violates unique constraint "pg_extension_name_index"` -> asyncpg.PostgresError -> `VectorStoreUnavailable("schema setup failed: ...")` (pgvector.py:284-285). lifecycle.py:96-97 swallows it as a warning, so those pods boot with `_ensured_collection=False` and every subsequent upsert/search re-enters ensure_collection until one attempt lands cleanly. On the qdrant driver the shape is worse: all three see `collection_exists()==False`, all three POST create_collection, the losers get a 409 raised through `_qdrant_errors` and never latch `_ensured_collection`, so every `upsert_one`/`hybrid_search` (qdrant.py:153,185,231,253) pays a full collection_exists round-trip forever.

*수정 스케치*: Move `CREATE EXTENSION IF NOT EXISTS vector` inside the advisory-lock transaction (it is transactional DDL in PG), or wrap it in a retry that treats duplicate-key as success. For qdrant/seahorse, take a PG advisory lock in the service layer around `store.ensure_collection()` since main PG is already a hard dependency, and latch `_ensured_collection` on a 409/AlreadyExists response rather than raising.

**delete_worker's sweep and abandoned-chunk reap are rate-limited by process-local monotonic clocks** — `backend/app/services/delete_worker.py:209` [medium/WASTEFUL]

`_last_sweep_at` (delete_worker.py:170-173) and `_last_reap_at` (delete_worker.py:209, 217-221) are module globals compared against `time.monotonic()`. `time.monotonic()` has no shared epoch across processes, and both start at 0.0 in a freshly imported module, so the documented rate limits (`SWEEP_INTERVAL_SECONDS`, `REAP_INTERVAL_SECONDS = 3600.0`) are per-process, not global. `_reap_abandoned_chunks_once` scans `chunks` filtered on `vector_indexed_at IS NULL AND vector_retry_count >= $1` with `FOR UPDATE SKIP LOCKED` plus a NOT EXISTS anti-join against `vector_delete_outbox` (delete_worker.py:226-264). `_process_once` calls both on every 10s idle tick (delete_worker.py:274-288, IDLE_INTERVAL_SECS in _backfill.py:30). The work itself is safe — SKIP LOCKED plus the NOT EXISTS guard (whose comment at delete_worker.py:240-247 already anticipates concurrent enqueues) prevents duplicate outbox rows — so this is cost, not corruption.

*실패 시나리오*: With 4 replicas, the hourly reap becomes 4 scans per hour instead of 1, and the outbox sweep likewise. Worse, immediately after a Recreate rollout all 4 processes have `_last_reap_at == 0.0`, so all 4 fire the reap scan on their very first 10s tick — four simultaneous FOR UPDATE SKIP LOCKED scans of the chunks table against a cold buffer cache, at exactly the moment the pods are also running the bootstrap BM25 recompute and draining the indexing backlog. That is the same class of load spike that produced the original probe-timeout 503 flapping.

*수정 스케치*: Replace the in-memory clock with a PG-side gate: `pg_try_advisory_lock` on a reap key plus a `last_run_at` row, so only one process runs it per interval globally and losers exit immediately. Also stagger the first tick with a small random jitter so a simultaneous cold start does not synchronize.

**Kiwi tokenizer ProcessPool sizes off os.cpu_count(), multiplying model copies per replica** — `backend/app/services/sparse_encoder.py:284` [medium/WASTEFUL]

`start_tokenizer_pool` (sparse_encoder.py:273-290) computes `n = max(2, min(4, os.cpu_count() or 2))` and spawns that many child interpreters with `initializer=_init_tokenizer_worker`, which loads the full Kiwi model in each child (sparse_encoder.py:267-270). `os.cpu_count()` reports the NODE's CPU count, not the container's cgroup quota, so on any node with >= 4 CPUs every pod spawns 4 children regardless of its own budget. lifecycle.py:135 starts the pool unconditionally in every process. The pod memory limit is 4Gi (deploy/k8s/backend.yaml:119-120) and there is deliberately no CPU limit (deploy/k8s/backend.yaml:116-118: "No CPU limit on purpose ... Cluster has ~98% CPU headroom; revisit if other tenants land on the same node"). `_token_cache` (sparse_encoder.py:250-251, 2048 entries) also lives once per parent process, so hit rates do not compound across replicas.

*실패 시나리오*: Scale to 4 replicas co-scheduled on one node: 4 uvicorn parents + 16 Kiwi child processes, each holding a full copy of the Kiwi model, against a per-pod 4Gi limit and a node with no CPU limits to throttle any of them. If all 4 pods start together (Recreate) they each fire `_bootstrap_recompute` (sparse_encoder.py:757-758); three lose the advisory lock and exit cheaply, but the winner tokenizes the entire corpus through its own 4-worker pool while the other 12 children sit resident. The explicit caveat in the deploy comment — 'revisit if other tenants land on the same node' — is exactly the situation multi-replica creates, and nothing in the code notices.

*수정 스케치*: Read the cgroup CPU quota (or a new `tokenizer_pool_workers` setting) instead of `os.cpu_count()`, and set a per-pod CPU limit once replicas > 1 so the no-limit assumption stops holding. Long term this argues for splitting the tokenizer/indexer into its own Deployment rather than replicating it inside every API pod.

**No API-only mode: start_workers() is unconditional and the documented worker split does not exist** — `backend/app/services/lifecycle.py:3` [medium/WASTEFUL]

The module docstring claims "Both `app.main` (when AKB_DISABLE_WORKERS is unset) and `app.worker_main` import these so the start/stop order stays consistent across entrypoints." Neither exists. `find . -name 'worker_main*'` returns nothing, and grepping `AKB_DISABLE_WORKERS` across the entire repo (excluding .git/node_modules/__pycache__) matches only this docstring line. `main.py:37-41` calls `start_workers()` unconditionally inside the lifespan. So every process that serves HTTP also runs embed_worker, delete_worker, external_git_poller, vault_backfill, the BM25 stats refresher, the Kiwi ProcessPool, the git commit pool, s3_delete_worker, metadata_worker, events_publisher, the audit uploader and the role_sync reconcile timer (lifecycle.py:115-188). Note the related design intent that IS honored: sparse_encoder.py:277-279 warns the tokenizer pool "is a SERVING dependency ... so if API and indexing-worker tiers are ever split it must be started on the always-run path, not behind a worker gate" — the split it anticipates has no implementation.

*실패 시나리오*: Scaling to 3 replicas to fix the single-event-loop stall triples every background worker rather than sharding them: 3 BM25 stats refreshers, 3 abandoned-chunk reapers, 3 outbox sweepers, 3 role_sync reconcile timers, 3 audit uploaders, 3x the tokenizer memory. The queue-claiming workers are safe (SKIP LOCKED) so nothing corrupts, but there is no configuration that lets an operator run 4 API pods and 1 worker pod — the only lever is replica count, which moves all of it at once.

*수정 스케치*: Implement what the docstring already describes: an `AKB_DISABLE_WORKERS` (or `settings.run_workers`) gate around `start_workers()` in main.py, plus an `app.worker_main` entrypoint that runs init_storage + start_workers with no HTTP server. Keep `sparse_encoder.start_tokenizer_pool()` and `write_lane.start_commit_pool()` on the always-run path per the existing comment.

**recompute_stats zeroes the entire bm25_vocab table inside its transaction, blocking every concurrent encoder** — `backend/app/services/sparse_encoder.py:649` [low/WASTEFUL]

Inside the advisory-lock-held transaction, `recompute_stats` executes `UPDATE bm25_vocab SET df = 0, updated_at = NOW()` over every row (sparse_encoder.py:649), then a second full unnest-driven UPDATE (lines 652-661). Both take row locks on the whole vocab table until commit. Concurrently, `get_or_create_term_ids` (sparse_encoder.py:352-362) runs `INSERT ... ON CONFLICT (term) DO UPDATE SET updated_at = bm25_vocab.updated_at` — a DO UPDATE, which requires a row lock on every existing matched term, so it blocks behind the recompute rather than skipping. Every `encode_document` call goes through it (line 470), and each blocked caller is holding a pool connection acquired at line 344.

*실패 시나리오*: Corpus with ~500k vocab terms; the two full-table UPDATEs take several seconds. During that window, with 4 replicas each running indexing_concurrency=8, up to 32 embed_worker tasks call get_or_create_term_ids and all block on vocab row locks, each pinning a PG pool connection (pg_pool_max_size is per-process, so 8 of each process's budget). Any request-path write needing a connection queues behind them. This is invisible in the indexing stats because the rows are still claimed and leased — they just make no progress until the recompute commits.

*수정 스케치*: Change the no-op ON CONFLICT to `DO NOTHING` plus a follow-up SELECT for the existing ids (a DO NOTHING conflict does not take the row lock), which removes the interaction entirely. Alternatively write df into a side table that is swapped by rename, so the hot path never contends with the recompute.

**/health reports per-process vault_backfill readiness through a load-balanced Service** — `backend/app/main.py:352` [low/WASTEFUL]

`vs_info["vault_backfill"] = await vault_backfill.pending_stats()` (main.py:352) returns `{"ready": is_ready(), "applicable": ..., "vault_filter_supported": ...}` (vault_backfill.py:161-179), and `ready` is the process-local `_ready` global (vault_backfill.py:42-48). `null_remaining` comes from a real PG count so it is consistent, but `ready` is not. With one replica this is the truth; with N it is one replica's opinion, selected by whichever pod the Service routed the probe to.

*실패 시나리오*: An operator polls /health during a rollout to confirm the vault-filter path activated. Successive polls return ready:true, ready:false, ready:true depending on which pod answered, while null_remaining consistently reads 0. The operator cannot distinguish 'backfill incomplete' from 'some replicas have not ticked yet', and the metric that actually predicts search behavior (which path a given query will take) is unobservable from outside the pod.

*수정 스케치*: Report readiness derived from the shared source (`vault_backfill_pending() == 0`) rather than the local latch, or include the pod/process identity in the payload so the value is interpretable.

**Indexing queue claim, lease, and the upsert-vs-delete guard are genuinely cross-process safe** — `backend/app/services/embed_worker.py:60` [info/ALREADY_SAFE]

Recording this explicitly so it is not re-litigated. `_claim_batch` (embed_worker.py:60-81) selects pending chunks with `FOR UPDATE SKIP LOCKED` and pushes `vector_next_attempt_at` out 10 minutes in the same statement, giving a DB-enforced lease that peer processes honor. The embedding API call happens outside any transaction (embed_worker.py:130-176), so no locks are held across the network round-trip. The critical cross-process guard is embed_worker.py:220-229: before upserting, the worker re-reads `SELECT 1 FROM chunks WHERE id = $1 FOR UPDATE` — a PG row lock, not a process-local one — so a concurrent `_drop_source_chunks_with_outbox` in another process either serializes behind it (its DELETE then enqueues the outbox row that cleans up the point) or has already committed (the worker sees nothing and skips, leaving no orphan). `_mark_success`/`upsert_one` commit in one transaction with pgvector joining the caller's conn (embed_worker.py:209-243, pgvector.py:193-209). delete_worker's claim uses the identical SKIP LOCKED shape (delete_worker.py:45-66). `recompute_stats` holds `pg_try_advisory_lock` for the whole scan and write with losers bailing cheaply (sparse_encoder.py:585-599, 686-688). pgvector's `ensure_collection` uses `pg_advisory_xact_lock` with an atomic build->drop->rename index swap (pgvector.py:274-277, 399-419). Document writes serialize on `pg_advisory_xact_lock(hashtext(vault_id), hashtext(path))` (document_repo.py:32-36) via `_path_lock` (document_service.py:314-343). Duplicating the process does not break any of these.

*실패 시나리오*: With 4 processes each running 8 embed_worker tasks (32 concurrent claimers), no two claim the same chunk row, no chunk is embedded twice, and a document deleted mid-embed cannot leave an orphaned vector-store point — verified by the SKIP LOCKED claim plus the FOR UPDATE existence re-check, both DB-side.

*수정 스케치*: No change needed. Worth preserving as the reference pattern the table/file reindex path should be brought up to.

## Process-local mutable state that would diverge across processes/pods (backend/app, backend/mcp_server)

There is no `functools.lru_cache`/`@cache` anywhere in backend/app or backend/mcp_server (verified by grep), so the divergence surface is entirely hand-rolled module globals — I enumerated all 41 `global` statements plus every module-level mutable container. The codebase splits cleanly into three groups: (a) state that is already cross-process correct because it lives in PG (`oidc_transients` DELETE…RETURNING, all six outbox workers' `FOR UPDATE SKIP LOCKED` claims, `pg_advisory_xact_lock` on `(vault_id, path)`, the BM25 recompute `pg_try_advisory_lock`, pgvector's `ensure_collection` advisory lock); (b) harmless per-process handles (http client, boto clients, vector-store singleton, readiness cache, template registry); and (c) a small set of globals that are load-bearing correctness or security primitives and are documented as safe *only because* AKB runs one process — `git_service._VAULT_LOCKS`, `document_service._CREATE_LOCKS`, `publication_rate_limit._by_ip/_by_slug`, `write_lane._vault_gates/_global_slots`, `mcp_server.http_app._transports/_session_users`, and the `audit_log` hash chain. The audit chain is the sharpest case: `_seq`/`_prev` are per-process, so two writers appending to one file make `verify_chain` fail on the *second* line, and if each pod instead keeps its own `/data/audit` (the k8s manifest mounts no volume there), the uploader's fixed bucket key `audit/{day}/akb-audit-{day}.jsonl` makes every pod overwrite the others' day file. Three findings are outright data-destroying (git ref lost-update, create_vault rollback deleting the winner's repo, audit overwrite); two are security-control weakening (rate-limit budget × N, RBAC reconcile races). Note also that `lifecycle.py`'s docstring references an `app.worker_main` entrypoint and an `AKB_DISABLE_WORKERS` env var that do not exist in the repo — `start_workers()` is unconditional in `main.py:39-41`, so every process runs every worker.

## Postgres layer under multiple processes (pool, migrations, RoleSync, advisory locks, read-modify-write)

The Postgres layer is bimodal: the *request-path* write sequences are genuinely well-hardened for multi-process (PG transaction advisory locks on doc paths, publications, table migrations, account provisioning, BM25 recompute, pgvector schema; FOR UPDATE SKIP LOCKED on all six queue workers), so document/table/file writes and worker claims would survive N processes essentially unchanged. The *startup and control-plane* paths are the opposite: `init_db()` runs `init.sql` plus the migration ledger on every boot with NO advisory lock and no serialization of any kind (backend/app/db/postgres.py:80-224), and the migration body is not atomic with its ledger row, so N pods booting together can double-apply a data migration or crash the boot on a catalog unique violation. `RoleSync.reconcile_from_catalog()` is a lock-free, non-transactional, unconditional read-modify-write over `pg_roles`/`pg_auth_members` that both (a) can drop the PG role of a user/vault/token created between its two reads and (b) re-issues three ACCESS EXCLUSIVE-taking GRANTs on *every* `vt_*` table on every pass — N processes multiply both. Connection budget is the hard wall: 30 conns/process against `max_connections=200` with no PgBouncer anywhere in `deploy/` means the shipped k8s Postgres is exhausted at N=7 processes, and the failure is a boot crash, not degradation. Finally `document_service.create_vault` explicitly documents that its `rm -rf` rollback is "sound only because `_create_lock(name)` excludes concurrent same-name creates" — a process-local asyncio.Lock, so a second process racing the same vault name deletes the winner's git repo.

**init_db()/_apply_migrations() run on every boot with no advisory lock — N pods race the schema** — `backend/app/db/postgres.py:96` [blocker/BREAKS_CORRECTNESS]

`init_db` unconditionally executes the whole of `init.sql` (postgres.py:92-95) then calls `_apply_migrations()` (postgres.py:96). `_apply_migrations` (postgres.py:160-224) reads the `schema_migrations` ledger, then for every unrecorded filename calls `_run_one_migration`. There is NO `pg_advisory_lock`, no `LOCK TABLE schema_migrations`, and no `SELECT ... FOR UPDATE` anywhere in the file — I grepped the whole backend for `advisory` and the only hits are document_repo, table_migration_service, account_service, publication_service, sparse_encoder and pgvector; postgres.py has none. Two boots therefore both compute the same `applied` set and both run the same migration bodies concurrently. The ledger INSERT uses `ON CONFLICT (filename) DO NOTHING` (postgres.py:143-147), which makes the *record* idempotent but does nothing to prevent the *body* from running twice. The comment in init.sql:16-18 ("init.sql itself is still re-run every boot — it is pure CREATE … IF NOT EXISTS and takes no conflicting locks") is contradicted by the project's own code: pgvector.py:124-129 says "PG's CREATE SCHEMA IF NOT EXISTS / CREATE TABLE IF NOT EXISTS are not race-safe at the catalog level — concurrent sessions can still trip 'duplicate key value violates pg_namespace_nspname_index'", which is why the vector store guards its identical DDL with `pg_advisory_xact_lock` (pgvector.py:275). init.sql also contains `CREATE OR REPLACE FUNCTION akb_set_updated_at()` (init.sql:479), which raises `tuple concurrently updated` (XX000) under concurrent execution.

*실패 시나리오*: Two backend pods (or `uvicorn --workers 2`) start within the same second on a fresh/upgraded DB. Both execute init.sql; one loses the catalog race and gets `duplicate key value violates unique constraint "pg_type_typname_nsp_index"` (or `tuple concurrently updated` on the CREATE OR REPLACE FUNCTION). asyncpg raises a `PostgresError`, which is NOT in init_db's retry tuple `(ConnectionRefusedError, asyncpg.CannotConnectNowError, OSError)` at postgres.py:98 — so it propagates out of the lifespan and the pod CrashLoopBackOffs. Separately, migration 011 (backend/app/db/migrations/011_external_doc_collections.py:63-78) does a bare `SELECT id FROM collections WHERE vault_id=$1 AND path=$2` then an unguarded `INSERT INTO collections` with no ON CONFLICT and no enclosing transaction; two processes both see NULL, both INSERT, the loser gets 23505 on UNIQUE(vault_id, path) and the whole boot dies.

*수정 스케치*: Wrap the entire init_db body in `SELECT pg_advisory_lock(<fixed_bigint>)` on a dedicated connection held for the duration (session-scoped, released on close), or better: move migrations out of the API process entirely into a k8s Job / initContainer that runs once per deploy, and have the API process only *verify* the ledger matches the expected tail and refuse to serve otherwise.

**Migration body and its ledger row are not in one transaction — partial application survives a crash or statement_timeout** — `backend/app/db/postgres.py:140` [high/BREAKS_CORRECTNESS]

`_run_one_migration` acquires a pooled connection (postgres.py:140), sets `lock_timeout` (141), calls `module.migrate(conn=conn)` (142), then INSERTs the ledger row (143-147). There is no `async with conn.transaction():` around this block, so under asyncpg every statement autocommits independently. 21 of the 45 migrations additionally do not open a transaction of their own — verified by `grep -L transaction() migrations/*.py`: 001, 002, 003, 004, 005, 007, 010, 011, 012, 013, 015, 016, 017, 018, 019, 027, 029, 030, 031, 032, 036. For those, each individual statement commits as it executes. Worse, the retry handler at postgres.py:149-157 catches `asyncpg.QueryCanceledError` and retries up to 10 times — but QueryCanceledError is ALSO what `statement_timeout = 30000` (set globally at postgres.py:60-61) raises for a migration that legitimately takes longer than 30s. So a slow data migration is cancelled mid-way, its already-committed statements persist, and it is re-run from the top 10 times before finally raising.

*실패 시나리오*: A 60-second backfill migration (e.g. 011 or 026 on a large corpus) is cancelled by statement_timeout at 30s. Half its per-bucket `INSERT INTO collections` / `UPDATE documents` statements have already autocommitted. `_run_one_migration` treats the cancellation as a lock conflict, sleeps 4s, and re-runs the body against the half-migrated state — for 011 that means the SELECT-then-INSERT now hits rows it created itself. After 10 attempts it raises and the boot fails, leaving the DB in a partially-migrated state with no ledger row, so the next boot starts the same loop. With N processes this happens N times in parallel on the same rows.

*수정 스케치*: Wrap `module.migrate()` + the ledger INSERT in a single `async with conn.transaction():` and set a per-migration `SET LOCAL statement_timeout = 0` (or a generous explicit value) so lock waits and genuine long-running work are distinguishable; catch `LockNotAvailableError` only, not `QueryCanceledError`.

**Connection budget: 30 conns/process against max_connections=200 with no PgBouncer — hard wall at N=7** — `backend/app/config.py:92` [blocker/BREAKS_CORRECTNESS]

`pg_pool_min_size: int = 2` / `pg_pool_max_size: int = 30` (config.py:91-92), resolved by `_pool_sizes()` (postgres.py:33-34) with AKB_PG_POOL_* env override. The deployed Postgres is `max_connections=200` (deploy/k8s/postgres.yaml:51); PG's default `superuser_reserved_connections=3` is not overridden, so 197 are usable. In the shipped k8s config `vector_store_dsn: ""` (deploy/k8s/backend.yaml:43, deploy/k8s/internal/backend-config-patch.yaml:49), so `PgvectorStore._pool()` returns the MAIN pool (pgvector.py:172-176) and adds nothing — 30/process. If an operator sets a separate `vector_store_dsn` (a documented, supported mode, config.py:431), the driver opens its own `max_size=8` pool (pgvector.py:161-163) → 38/process. There is no PgBouncer anywhere in deploy/ — I grepped the whole repo and the only hit is a docstring at user_sql_executor.py:12. Arithmetic against 197 usable, shared-pool mode (30/proc): N=1 → 30 (15%); N=2 → 60 (30%); N=4 → 120 (61%); N=6 → 180 (91%); N=7 → 210 (EXCEEDS); N=8 → 240 (EXCEEDS by 43). Separate-DSN mode (38/proc): N=5 → 190 (96%); N=6 → 228 (EXCEEDS). For self-host / all-in-one on a vanilla PG the config's own comment assumes max_connections=100 (config.py:87): N=3 → 90; N=4 → 120 (EXCEEDS). Note `write_lane_concurrency: int = 8` (config.py:497) is also process-local, so N processes admit 8N concurrent git-committing writers, each holding one pooled connection inside an open transaction for the whole critical section (document_service.py:338-343) — the pool is the intended backpressure queue and that assumption is per-process only.

*실패 시나리오*: Scale to 8 replicas (or set `--workers 8` in the Dockerfile CMD). Under a write burst all 8 processes grow their pools toward 30. Around the 197th connection PG starts returning `FATAL: sorry, too many clients already`. asyncpg surfaces this as `TooManyConnectionsError`, a `PostgresError` — which is NOT caught by get_pool's retry loop (postgres.py:65 catches only `ConnectionRefusedError, OSError`), so a pod that boots into a saturated cluster crashes instead of backing off; already-running pods get the error out of `pool.acquire()` and return 500s on random requests, including /health, which then trips the liveness probe.

*수정 스케치*: Derive an explicit global budget: put PgBouncer (transaction pooling — user_sql_executor.py:9-12 already documents SET LOCAL ROLE compatibility) in front, or set AKB_PG_POOL_MAX_SIZE = floor((max_connections - reserved - admin_headroom) / replicas) via the Deployment env and fail the boot if replicas × max_size exceeds a configured ceiling. Also add `TooManyConnectionsError` to get_pool's retry tuple so a cold pod backs off instead of crash-looping.

**RoleSync.reconcile_from_catalog is a lock-free non-transactional read-modify-write — drops live users'/vaults'/tokens' PG roles** — `backend/app/services/role_sync.py:667` [high/BREAKS_CORRECTNESS]

`reconcile_from_catalog` acquires a connection (role_sync.py:667) but never opens a transaction, so each `conn.fetch` runs in its own READ COMMITTED snapshot. `_reconcile_user_roles` reads `SELECT id FROM users` (role_sync.py:690), then in a SEPARATE statement reads `pg_roles LIKE 'akb_user\_%'` (role_sync.py:694), then drops `existing - wanted` (role_sync.py:711-716). The identical two-read-then-drop shape recurs at 730/735/766-771 (vault group roles) and 941/963/973-978 (token roles). Meanwhile `auth_service.register` commits the users row (auth_service.py:243-249) and only afterwards calls `get_role_sync().on_user_create(user_id)` (auth_service.py:258), which creates the role — so there is a real window where the role exists and the users row is not yet in a peer's snapshot. It runs at startup (lifecycle.py:109) and on a 3600s timer (lifecycle.py:183-186, config.py:531), so N processes give N independent reconcilers with unsynchronised phases. A variant of this race exists at N=1 (the timer task and a registration interleave on the same event loop), but at N=1 the hook and the reconciler at least share a process; with N processes the two are in different address spaces with no ordering relationship at all, and the number of drop windows scales linearly with N.

*실패 시나리오*: Process B's hourly reconcile fetches `SELECT id FROM users` at T. At T+2ms a user registers on process A: the users row commits and `on_user_create` creates `akb_user_<uid>`. At T+5ms process B fetches pg_roles, sees `akb_user_<uid>` in `existing` but not in its stale `wanted`, and executes `DROP OWNED BY` + `DROP ROLE` (role_sync.py:1267-1275). The brand-new user's every `akb_sql` call now fails at `SET LOCAL ROLE "akb_user_<uid>"` (user_sql_executor.py:204) with `role does not exist` — for up to one hour. The same sequence against `_reconcile_vault_roles` drops all three group roles of a vault created seconds earlier, revoking every member's akb_sql access to it; against `_reconcile_token_roles` it drops a live scoped PAT's role, which is fail-closed but still a total akb_sql outage for that token.

*수정 스케치*: Take `pg_advisory_xact_lock(<rolesync_key>)` at the top of reconcile_from_catalog so only one process reconciles at a time, AND run the whole reconcile inside a single REPEATABLE READ transaction (or at minimum read `users`/`vaults`/`tokens` and `pg_roles` in one snapshot) so orphan detection can never see a half-committed create. A grace period (only drop roles whose catalog row has been absent for > one reconcile interval) is a cheap belt-and-braces.

**Reconcile re-issues 3 ACCESS EXCLUSIVE GRANTs on EVERY vt_* table unconditionally, every pass, in every process** — `backend/app/services/role_sync.py:831` [high/WASTEFUL]

`_reconcile_table_grants` (role_sync.py:818-840) selects every row of `vault_tables` joined to `vaults` and calls `self._grant_table(...)` for each one with no diff whatsoever (role_sync.py:836-840). `_grant_table` issues three statements per table (role_sync.py:1313-1317): `GRANT SELECT`, `GRANT SELECT,INSERT,UPDATE,DELETE`, `GRANT ALL` on `public."vt_..."`. In PostgreSQL GRANT/REVOKE on a relation takes an AccessExclusiveLock on that relation, which conflicts with plain SELECT. The class already knows how to compute the drift set — `_diff_table_grants` (role_sync.py:1156-1216) does exactly one catalog-wide query against `information_schema.role_table_grants` and produces `missing_table_grants` — but the reconcile path does not use it. The same unconditional pattern applies to `_reconcile_memberships` (role_sync.py:779-786, one GRANT per vault_access row, counted as `grants_added` regardless of whether anything changed), `_reconcile_vault_roles` hierarchy/owner grants (role_sync.py:753-764, 3 per vault), and `_reconcile_public_access` (role_sync.py:799-812, 2-3 REVOKEs + up to 1 GRANT per vault). Note the reconcile connection does NOT set `lock_timeout` (unlike migrations, postgres.py:141), so each GRANT waits up to the 30s `statement_timeout`.

*실패 시나리오*: A deployment with 400 vault tables, 8 replicas. Each replica's startup reconcile plus its hourly timer fires 1200 GRANT statements, each taking AccessExclusiveLock on a vt_* table. With 8 unsynchronised reconcilers that is 9600 ACCESS EXCLUSIVE acquisitions per hour, all contending with each other and with live `akb_sql` SELECTs running under `SET LOCAL ROLE` (user_sql_executor.py:184-231). A user query holding a table open blocks the GRANT, the GRANT queues behind it and blocks every subsequent query on that table (PG lock queue is FIFO), producing head-of-line stalls up to 30s on the single event loop — the exact 503 shape of the prior Kiwi incident. Additionally, `_drop_role_if_present` issues `DROP OWNED BY "role"` (role_sync.py:1267), which internally REVOKEs across every vt_* table the role touches, taking ACCESS EXCLUSIVE on all of them in nondeterministic Python-set iteration order (role_sync.py:711, 766, 973) — different orders in different processes, which is the classic ingredient for a cross-process deadlock. I did NOT reproduce the deadlock; treat the deadlock half of this as plausible-unverified, the lock-storm half as verified from the code.

*수정 스케치*: Make `_reconcile_table_grants` call the existing `_diff_table_grants` logic and only GRANT where `missing_privileges` is non-empty (same for memberships/public-access, which can be diffed off the same `pg_auth_members` bulk query the diff path already runs). Combined with the advisory lock from the previous finding, steady-state reconcile then emits zero DDL.

**create_vault rollback rm -rf's the winner's git repo — safety is explicitly documented as depending on a process-local asyncio.Lock** — `backend/app/services/document_service.py:1874` [blocker/BREAKS_CORRECTNESS]

`create_vault` serialises same-name creates with `_create_lock(name)` (document_service.py:1722), a plain `asyncio.Lock` held in a module-level dict `_CREATE_LOCKS` (document_service.py:153-161). The docstring at document_service.py:1706-1713 states the ownership probe is unsound without it: "A and B race the same name, A's init wins, B's fails, and B's rollback would see the dir 'appear during its attempt' and delete A's repo." `_rollback_vault_disk` implements exactly that probe: `if existed_before or (git_path is None and not self.git.vault_exists(name)): return` (document_service.py:1874), and its docstring at 1871 says the extra probe is "sound only because `_create_lock(name)` excludes concurrent same-name creates." *실패 시나리오*: Two processes receive `akb_create_vault(name='research')` concurrently. Both take their own local `_create_lock('research')` (different objects in different address spaces). Both evaluate `existed_before = self.git.vault_exists('research')` → False. Process A's `init_vault` creates the bare repo and A proceeds to commit + INSERT. The guard evaluates `False or (True and not self.git.vault_exists('research'))` — but A has now created the directory, so `vault_exists` is True and the guard is False. **Concurrent reconcilers permanently inflate /health rbac error counters, masking real drift** — `backend/app/services/role_sync.py:700` [medium/WASTEFUL]

**BM25 stats cache is process-local — N processes serve up to 60s of divergent IDF after a recompute** — `backend/app/services/sparse_encoder.py:387` [low/WASTEFUL]

`_stats_cache: tuple[float, dict] | None` (sparse_encoder.py:387) is a module global with a 60s TTL (`_STATS_TTL_SECS = 60.0`, sparse_encoder.py:386), read on every scoring call via `load_stats()` (sparse_encoder.py:390-406). `_invalidate_stats_cache()` (sparse_encoder.py:409-411) is called only from inside `recompute_stats` (sparse_encoder.py:676) — i.e. it invalidates the cache of the process that *won* the `pg_try_advisory_lock` (sparse_encoder.py:587). **register() bootstrap-admin check-then-insert can mint two admins (pre-existing at N=1, not newly caused by multi-process)** — `backend/app/services/auth_service.py:245` [medium/BREAKS_CORRECTNESS]

`register` does a `SELECT id FROM users WHERE username = $1 OR email = $2` duplicate probe (auth_service.py:230-235) and then `INSERT INTO users (...) ## event-loop blocking — why ONE event loop is a liability

AKB has clearly been through at least two rounds of event-loop hardening: git reads/writes, bcrypt, audit-log disk I/O, publication CSV/HTML/snapshot rendering, the akb_sql row coercion, and Kiwi tokenization are all correctly offloaded (to_thread, the dedicated commit ThreadPoolExecutor in write_lane, the audit writer thread, and the Kiwi ProcessPool). The remaining blockers cluster in three places the hardening passes missed. (1) **boto3 is still called synchronously from coroutines** — `access_service.delete_vault` issues one blocking S3 DELETE per file in a bare `for` loop on the loop thread (access_service.py:1541, again at :1565), `s3_delete_worker` does 16 blocking DELETEs per tick inside the API process (s3_delete_worker.py:115), and `file_service.confirm_upload`/`initiate_upload` do a blocking `head_object`/`head_bucket` per request (file_service.py:336, :254). (2) **`SearchService.grep` fetches an uncapped `chunks` result set and then runs a pure-Python per-line regex/substring scan on the loop** (search_service.py:906–957) — the SQL `LIMIT` was deliberately removed and the Python `re.search` on user-supplied patterns is a live ReDoS hole. (3) **Unbounded document/response bodies are parsed and serialized inline**: no request-body size cap anywhere, so `chunk_markdown` + `frontmatter` + sha256 + link-extraction all run on the loop per write (document_service.py:486–547), zip compress/decompress for export/import runs on the loop (routes/knowledge_io.py:53, :74), and every MCP response — including `akb_export`, which inlines an entire vault — goes through a single `json.dumps` on the loop (mcp_server/server.py:1406). With `replicas: 1`, `readinessProbe` 15s/8s/×3 (~45s to be pulled from the Service) and `livenessProbe` 30s/8s/×6 (~3min to SIGKILL), any of these turns a single request into a full-service outage. The single worst remaining blocker is `grep`: one authenticated `akb_grep(regex=true, ...)` with a backtracking pattern freezes the only loop indefinitely until liveness kills the pod. The worst *operationally likely* one is the blocking-boto3 family, which converts any S3/MinIO slowdown into a multi-minute loop freeze with zero attacker involvement.

**grep runs an uncapped SQL fetch plus a per-line Python regex scan directly on the event loop (ReDoS → indefinite freeze)** — `backend/app/services/search_service.py:906` [blocker/WASTEFUL]

The chunk query at search_service.py:906-918 intentionally has NO `LIMIT` (see the comment at :889-905, "Drop the cap"), so every chunk matching the ILIKE/`~*` predicate is materialized by asyncpg. There is no pg_trgm index on `chunks.content` (backend/app/db/init.sql:239 is the only chunks index), so this is a full seq scan bounded only by the 30s `statement_timeout` (app/db/postgres.py:60). The result is then processed at :943-957 in a synchronous loop: `strip_chunk_metadata_header` (a regex sub), `chunk_body.split("\n")`, and per line either `_re.search(pattern, line, IGNORECASE)` or `pattern.lower() in line.lower()`. None of this is awaited or offloaded. Python's `re` is a backtracking engine while PostgreSQL's is a hybrid DFA — so a pattern PG matches cheaply can be exponential in Python. `regex` is a first-class user parameter on both surfaces (mcp_server/tools.py:433, app/api/routes/search.py:89) and `limit` only truncates the OUTPUT (:998), never the scan.

*실패 시나리오*: An authenticated writer stores one document whose chunk contains a line like `"a"*40 + "b"` (so PG's `~*` matches the chunk and returns the row) followed by a line of `"a"*40` with no `b`. They then call `akb_grep(pattern="(a+)+$", regex=true)`. PG returns the row in milliseconds; the Python loop at :947 calls `re.search(r"(a+)+$", "aaaa…a")` on the non-matching line, which backtracks ~2^40 times. The single event loop is frozen with no timeout and no cancellation point. /livez and /readyz can no longer be scheduled, so readinessProbe (8s timeout, ×3 at 15s) pulls the pod from the Service after ~45s — with replicas:1 that is a 100% outage — and livenessProbe SIGKILLs it after ~3min. Volume alone reproduces a milder version: `akb_grep(pattern="the")` over a 500k-chunk corpus fetches ~750MB of text (also an OOM risk against the 4Gi limit in deploy/k8s/backend.yaml) and spends tens of seconds in the line loop.

*수정 스케치*: Restore a hard SQL `LIMIT` (or stream with a server-side cursor) and move the whole grouping/line-scan block (:920-957) into `asyncio.to_thread`. Additionally bound the Python-side regex: pre-compile once, reject patterns over a length/complexity threshold, or drop the Python re-scan entirely and let PG do the line extraction (`regexp_matches` / `unnest(string_to_array(content, E'\n'))`), which is not exponential.

**delete_vault issues one blocking boto3 DELETE per file, in a bare for-loop, on the event loop** — `backend/app/services/access_service.py:1541` [blocker/WASTEFUL]

`delete_vault` is `async def` (access_service.py:1496). At :1535 it fetches every `vault_files` row, then at :1539-1541 iterates them calling `s3_adapter.delete(fr["s3_key"])` — a synchronous boto3 `delete_object` (app/services/adapters/s3_adapter.py:178-182) with no `to_thread`, no batching, and no cap on N. *실패 시나리오*: An admin deletes a vault holding 10,000 files. ## Process & deployment topology

One AKB backend container today runs 5 long-lived OS processes (1 uvicorn parent + 4 spawned Kiwi tokenizer children from `sparse_encoder.py:284`), roughly 29-43 Python threads in the parent (1 event loop + the lazily-created `asyncio.to_thread` pool at `min(32, cpu+4)` + 8 dedicated git-commit threads + ProcessPool management threads), 4 × os.cpu_count() native Kiwi threads across the children, and 7 transient `git` subprocess forks per document commit. `replicas: 1` is not a conservative default — it is a load-bearing correctness invariant. The single hardest constraint is `git_service.py`: the per-vault serialization is a process-local `threading.Lock` (`git_service.py:43-53`), every write does `git reset --hard HEAD` on a SHARED persistent worktree on the RWO PVC (`git_service.py:589`), and the ref move is a non-CAS `update_ref` (`git_service.py:128`) — two processes writing different paths in the same vault silently destroy each other's content and lose commits. Two more state stores are explicitly process-local and documented as such: the MCP session registry (`mcp_server/http_app.py:52-55`, with no sticky-session annotation on the Ingress) and the publication password brute-force throttle (`publication_rate_limit.py:1-8`, whose own docstring says "the backend runs single-replica … so a module-global dict is authoritative"). The advertised escape hatch does not exist: `lifecycle.py:3` claims `AKB_DISABLE_WORKERS` and an `app.worker_main` entrypoint, but neither is implemented anywhere in the repo — `main.py:41` calls `start_workers()` unconditionally, so every process gets the full worker set. Naively setting `--workers 4` would not reach the git corruption; it would OOMKill during startup first, because Kiwi measures ~550 MB resident per loaded process and 16 children exceed the 4Gi limit by more than 2×.

**Shared git worktree is serialized only by a process-local threading.Lock; `reset --hard HEAD` destroys a peer process's staged write** — `backend/app/services/git_service.py:589` [blocker/BREAKS_CORRECTNESS]

`commit_file` (line 579), `delete_file` (613) and `move_file` (652) all take `_vault_lock(vault_name)` — a `threading.Lock` from the module-global `_VAULT_LOCKS` dict (git_service.py:43-53). That dict lives in ONE interpreter. The persistent worktree it protects lives on the shared `akb-vaultdata` PVC at `/data/vaults/_worktrees/<vault>` (backend.yaml:110-111, config.py:103). The first statement inside the lock is `work_repo.git.reset('--hard', 'HEAD')` (line 589), which wipes any uncommitted working-tree content. The DB-level guard does NOT cover this: `document_service._path_lock` takes `pg_advisory_xact_lock(vault_id, path)` (document_service.py:338-343, document_repo.py:33) — keyed on the PATH, not the vault — so two writers to DIFFERENT paths in the SAME vault are, by design, concurrent. Today that is safe because they land in the same process and contend on `_vault_lock`. Across processes there is nothing.

*실패 시나리오*: With 2 backend processes (either replicas=2 co-scheduled on one node, or `--workers 2`), user A PUTs `notes/a.md` on process 1 and user B PUTs `specs/b.md` on process 2 in the same vault at the same time. P1 passes its advisory lock and its local `_vault_lock`, runs `reset --hard`, writes `a.md`, and calls `git add`. Before P1 reaches `write_tree` (line 113), P2 — holding a DIFFERENT path advisory lock and its OWN local `_vault_lock` — runs `reset --hard HEAD` at line 589 and deletes P1's staged `a.md` from the working tree. P1's `write_tree` then produces a tree missing `a.md`, but P1 still records `documents.current_commit` for `a.md` in Postgres. The document exists in PG and in search, and 404s on every git read. No error is raised anywhere.

*수정 스케치*: Replace `_vault_lock` with a Postgres session-scoped `pg_advisory_lock(hashtext('akb_git_vault'), hashtext(vault_name))` held for the whole worktree critical section, or give each process its own worktree directory (`_worktrees/<vault>/<pid-or-pod>`) so the `reset --hard` blast radius is process-private. The bare repo's ref move still needs #2's fix.

**`git update_ref HEAD <sha>` has no old-value CAS — a concurrent commit is silently lost** — `backend/app/services/git_service.py:128` [blocker/BREAKS_CORRECTNESS]

`_stage_and_commit` reads the parent with `rev_parse --verify HEAD` (line 116), builds the commit with `commit_tree ... -p HEAD` (line 120), then moves the branch with `work_repo.git.update_ref('HEAD', commit_sha)` (line 128). `git update-ref` accepts an optional `<oldvalue>` argument that makes the move a compare-and-swap; it is not passed. This is a textbook read-modify-write with no optimistic-concurrency check. It is currently safe only because `_vault_lock` (git_service.py:579) makes the read-build-write sequence atomic within one process.

*실패 시나리오*: Two processes commit to the same vault. Both resolve HEAD to commit X. P1 builds commit X→Y and moves the ref to Y. P2, which already captured X as its parent, builds X→Z and calls `update_ref HEAD Z` — with no oldvalue, git accepts the non-fast-forward move unconditionally. Commit Y is now unreachable from the branch; the document P1 wrote is gone from git history, while `documents.current_commit = Y` in Postgres still points at an orphaned object. `akb_get` returns the row, `git.read_file` at the recorded commit may still work (the object survives until gc), but `akb_history` / `vault_log` no longer show it and the next `reset --hard HEAD` reverts the file on disk.

*수정 스케치*: Pass the observed parent as oldvalue: `update_ref('HEAD', commit_sha, parent_sha)`. git then fails the move with 'ref … is at X but expected Y' and the caller can retry the whole build. Cheap, and it turns silent loss into a retryable 409.

**MCP session registry is three process-local dicts, and an unknown session silently mints a new one instead of 404ing** — `backend/mcp_server/http_app.py:141` [high/BREAKS_CORRECTNESS]

`_transports`, `_server_tasks` and `_session_users` (http_app.py:52-55) are module-global dicts holding live `StreamableHTTPServerTransport` objects and asyncio tasks — inherently un-shareable across processes. The POST path at line 141 checks `if session_id and session_id in _transports`; on a miss it falls into the `else` at 143 and **mints a brand-new session id** (144) plus a fresh, never-`initialize`d transport (145-151), then hands the request to it (155). The GET/SSE path at 159 correctly 404s on an unknown session, so the two paths disagree. There is no session-affinity annotation on either Ingress — `nginx.ingress.kubernetes.io/affinity` is absent from ingress.yaml (the `/mcp` rule is at ingress.yaml:33-39) and from internal/ingress-patch.yaml (line 29-35) — so a multi-replica Service round-robins MCP requests.

*실패 시나리오*: With replicas=2, an agent completes `initialize` against pod A and receives session S. Its next `tools/call` round-robins to pod B. `S not in _transports` on B, so B mints session S' and dispatches `tools/call` into a transport that has never seen `initialize` — the MCP server loop rejects it (or hangs on the 0.05s startup race at line 82). *수정 스케치*: Two independent fixes: (a) make the POST path 404 on an unknown non-null `mcp-session-id` instead of silently minting a new one — the client already knows how to re-initialize; (b) add `nginx.ingress.kubernetes.io/affinity: cookie` + `affinity-mode: persistent` (or `upstream-hash-by: $http_mcp_session_id`) on the `/mcp` Ingress rule before replicas ever exceeds 1.

**Publication password brute-force throttle is a module-global dict with an explicit "single-replica is authoritative" assumption** — `backend/app/services/publication_rate_limit.py:40` [high/BREAKS_CORRECTNESS]

`_by_ip` and `_by_slug` (lines 40-41) are plain dicts. The module docstring states it outright at lines 3-4: "The backend runs single-replica (one process, one event loop), so a module-global dict is authoritative without cross-process coordination." The budgets are `_FREE_IP = 5` and `_FREE_SLUG = 30` (lines 26-27) — the per-slug backstop at line 27 exists specifically because X-Forwarded-For is spoofable, so it is the only real ceiling on an online guessing attack against a password-gated publication. *실패 시나리오*: With N processes fronted by a round-robining Service, an attacker's guesses distribute across N independent counters. `start_tokenizer_pool` sizes the pool at `max(2, min(4, os.cpu_count() or 2))` — 4 on any production node — with `spawn` and an initializer that eagerly loads the Kiwi model in each child (`_init_tokenizer_worker`, line 267-270). **Kiwi's internal thread pool defaults to os.cpu_count() per child — 4 × node-CPU native threads against a 1-CPU request with no CPU limit** — `backend/app/services/sparse_encoder.py:218` [medium/WASTEFUL]

`_get_kiwi()` constructs `Kiwi()` with no arguments (line 218). `kiwipiepy.Kiwi.__init__` takes `num_workers: Optional[int] = None`, and the resulting instance reports `k.num_workers == os.cpu_count()` — verified locally: 14 on a 14-core box. Neither `os.cpu_count()` nor `os.process_cpu_count()` honors a cgroup CPU quota, and backend.yaml sets no CPU limit at all (the comment at backend.yaml:116-118 removed it deliberately because throttling caused /livez timeouts) with `requests.cpu: "1"` (line 115).

*실패 시나리오*: On a 32-core node, each of the 4 tokenizer children creates a 32-thread Kiwi pool = 128 native threads, for a pod that declared it needs 1 CPU. *수정 스케치*: Pass an explicit `num_workers` to `Kiwi()` derived from the pod's CPU request (e.g. `Kiwi(num_workers=1)` — the parallelism already comes from the 4-process pool, so per-instance threading is redundant work-splitting inside an already-parallel design).

**`_apply_migrations()` runs schema + data migrations on every process boot with no cross-process lock** — `backend/app/db/postgres.py:160` [medium/WASTEFUL]

`init_storage()` (lifecycle.py:73) → `init_db()` (postgres.py:80) executes the full `init.sql` (line 95) and then `_apply_migrations()` (line 96) on EVERY process start. `_apply_migrations` reads the applied set (postgres.py:170-173) then iterates 40+ migration modules, several of which are data rewrites, not DDL (026_uri_collection_prefix rewrites edges/publications/events URIs; 035_fix_wikilink_alias_edges; 011_external_doc_collections backfills). There is no `pg_advisory_lock` around the sequence — the only serialization is `SET lock_timeout = '5s'` plus a 10×4s retry inside `_run_one_migration` (postgres.py:141, 149-157), which is a table-lock backoff, not mutual exclusion.

*실패 시나리오*: On a `--workers 4` boot, or a first-ever deploy at replicas=2, all processes read the same empty `schema_migrations` set within milliseconds of each other and all run the same migration list. The DDL ones serialize on ACCESS EXCLUSIVE and burn retry budget — 4 processes × a 5s lock_timeout on `ALTER TABLE chunks` can exhaust the 10-attempt / 40s budget and raise out of `init_db`, crashing startup. The data rewrites run 4× concurrently; each claims idempotence individually (e.g. 026's docstring, lines 18-20) but that has never been tested under concurrent execution.

*수정 스케치*: Wrap the whole `_apply_migrations()` body in a session-scoped `pg_advisory_lock(<migrations key>)` acquired on a dedicated connection, released in a finally. Losers then observe the completed ledger and skip. ~10 lines, and it is the same pattern already used correctly at sparse_encoder.py:586.

**`cleanup_stale_locks()` runs at every process startup across ALL vaults on the shared PVC** — `backend/app/services/git_service.py:206` [medium/BREAKS_CORRECTNESS]

`init_storage()` calls `GitService().cleanup_stale_locks()` unconditionally at lifecycle.py:79. It iterates every `<storage>/<name>.git` on the shared PVC and unlinks `index.lock` files older than `max_age_seconds=60.0` (line 206, 263-266). The docstring's safety argument at lines 229-234 is explicitly single-process: "the only write paths that touch a worktree's index hold `_vault_lock(vault_name)` per-vault, so startup self-heal — which runs before workers — cannot remove a lock held by a live operation." That reasoning evaporates the moment a second process exists, because `_vault_lock` is process-local (line 43-53).

*실패 시나리오*: During a Recreate rollout or any second-process start, an in-flight commit on the OLD process is holding `index.lock` for vault V. If that commit has been running longer than 60s — plausible on a large `reset --hard` stat sweep, since `git_write_timeout_secs` is 30s per COMMAND (config.py:512) not per commit, and `commit_file` issues 7 git commands — the new process unlinks the live lock at line 266. The old process's git then proceeds against an index another git may now also be writing, producing a corrupt index or a torn commit. The 60s threshold is defense-in-depth (line 232-234), not a guarantee.

*수정 스케치*: Gate the self-heal on the same cross-process vault lock proposed in finding #1, or make it a separate operator-invoked command rather than an unconditional startup step once replicas can exceed 1.

**RoleSync reconcile runs concurrently from every process with unguarded role DDL, inflating the security-drift counter on /health** — `backend/app/services/role_sync.py:642` [medium/WASTEFUL]

`reconcile_from_catalog()` runs once at startup (lifecycle.py:109) and then every `role_sync_reconcile_interval_secs` = 3600 (config.py:531, lifecycle.py:183-186). `_vault_gates` (line 75), `_global_slots` (line 80) and `_commit_pool` (line 94) are module globals. The module's entire premise — 'the global write-lane semaphore caps writes as a CLASS, so the connections and commit threads they can occupy are bounded no matter how many vaults are active' (lines 77-79) — holds only per process. `write_lane_concurrency` is 8 (config.py:498) and config.py:496-497 explicitly reasons about it relative to `pg_pool_max_size` = 30 (config.py:92): 'keep well under pg_pool_max_size (30) so reads always have headroom'. *수정 스케치*: Divide `write_lane_concurrency` and `AKB_PG_POOL_MAX_SIZE` by the replica count at deploy time (both are already tunable — the pool via the deliberate env-var exception at postgres.py:33-34), and treat the per-vault gate as advisory-only once the git layer has a real cross-process lock.

**/livez measures only event-loop schedulability and /readyz caches success for 30s — correct per-pod, wrong behind `--workers N`** — `backend/app/main.py:235` [medium/BREAKS_CORRECTNESS]

`/livez` (line 235-237) is `return {'status': 'alive'}` — no I/O. It measures exactly one thing: can the event loop schedule a trivial coroutine and can the socket accept a connection. That is the deliberate post-Kiwi-incident design and is right for its purpose, but it does NOT observe DB, git, worker liveness, or disk. `/readyz` (308-319) probes PG with a 2s timeout (265) and reports vector-store health non-fatally (277-281), then caches SUCCESSES for `_READY_TTL_SECONDS = 30` (240, 296-305) — failures are deliberately not cached (298-300). Both are per-process module state (`_ready_state`, line 250). Behind a multi-replica Service this is CORRECT: kubelet probes each pod's own container, so each pod reports its own loop and its own pool, and a stalled pod is shed after ~3×15s (backend.yaml:133-139).

*실패 시나리오*: Behind `uvicorn --workers 4`, all 4 worker processes share one listening socket on :8000. The kubelet's probe connection is accepted by an arbitrary worker. Worker 2 can be fully wedged — event loop blocked, PG pool exhausted — while workers 1, 3, 4 answer every /livez and /readyz. Liveness never fires, readiness never sheds the pod, and 25% of real traffic hangs indefinitely. The probes become statistically meaningless rather than merely lagging. The 30s success cache (line 304) also means a worker that lost PG keeps answering 'ready, cached: true' for up to 30s after the failure.

*수정 스케치*: If `--workers` is ever adopted, probes must move to a per-worker mechanism (separate admin port per worker, or a supervisor that aggregates worker health). For the multi-replica case the current design is sound and needs no change — this is a `--workers` hazard specifically.

**No terminationGracePeriodSeconds, but stop_workers() budgets up to 120s per worker — the graceful-shutdown path is unreachable** — `backend/app/services/lifecycle.py:191` [medium/WASTEFUL]

`stop_workers()` (lines 191-203) sequentially awaits 8 `BackfillRunner.stop()` calls plus the pool teardowns. Each `stop()` gives the in-flight iteration up to 120s (`_backfill.py:85-88`) before cancelling, with the comment at _backfill.py:77-83 explaining that a shorter timeout left rows half-claimed. `main.py:43-47` then drains the audit queue. No `terminationGracePeriodSeconds` is set anywhere in deploy/k8s (grep returns nothing), so Kubernetes uses the 30s default.

*실패 시나리오*: On any rollout, SIGTERM starts the lifespan shutdown; if a single embed_worker iteration is mid-embedding-API-call, `stop_workers()` blocks in the first `await` for up to 120s. At t=30s the kubelet SIGKILLs the container. The audit drain at main.py:47 never runs (dropping the tail of the audit trail — the exact loss its comment says it prevents), and any in-flight git commit dies holding `index.lock`, which is why `cleanup_stale_locks()` (lifecycle.py:79) has to exist at all. Combined with `strategy: Recreate` + `replicas: 1` (backend.yaml:78, 85-86), every single deploy is a hard outage window with a non-zero chance of leaving a stale lock behind.

*수정 스케치*: Set `terminationGracePeriodSeconds` on the backend pod spec to exceed the worst-case shutdown budget (or cut the `_backfill.py:87` timeout to fit inside 30s — the two numbers must be reconciled in one direction or the other).

**Audit hash chain state is per-process in-memory but appends to one shared file** — `backend/app/services/audit_log.py:83` [low/BREAKS_CORRECTNESS]

`_seq`, `_prev` and `_cur_date` (audit_log.py:83-86) are module globals, mutated only by the single writer thread (line 303) and used to build the hash chain written to `audit-<date>.jsonl` via a plain append `open('a')` at line 282. The file path is `settings.audit.log_dir` (config.py:42). Two processes each maintain an independent `(_seq, _prev)` chain and interleave appends into the same file, so the chain is unverifiable — the whole point of a hash-chained audit stream. Currently INERT in production: `audit.enabled` defaults to False (config.py:39) and the internal overlay (deploy/k8s/internal/backend-config-patch.yaml) sets no `audit:` block, so this does not fire today.

*실패 시나리오*: If an operator turns on `audit.enabled` while running more than one process, every consumer that verifies `h[n] == hash(prev, record)` sees a broken chain on the first interleaved write, and cannot distinguish that from tampering. Separately, `log_dir` defaults to `/data/audit` while backend.yaml:110-111 mounts only `/data/vaults` — with no PVC at that path the lines land on the container's writable layer and are lost on every restart, which config.py:40-41 explicitly warns about but the manifest does not implement.

*수정 스케치*: Before enabling audit: give each process its own file (`audit-<date>-<pid>.jsonl`) so each chain is self-consistent, and add a `/data/audit` volumeMount to backend.yaml.

**What actually forces replicas=1 — the complete constraint set** — `deploy/k8s/backend.yaml:78` [info/ALREADY_SAFE]

Enumerated, strongest first. (1) CORRECTNESS, hard: the process-local git worktree lock and non-CAS ref move (git_service.py:43-53, 128, 589) — findings #1/#2. (2) CORRECTNESS, hard: process-local MCP session dicts with no Ingress affinity (http_app.py:52-55; ingress.yaml:33 has no affinity annotation). (3) SECURITY, hard: the publication throttle's stated single-replica assumption (publication_rate_limit.py:1-8). (4) INFRASTRUCTURE: `akb-vaultdata` is `ReadWriteOnce` (backend.yaml:172-173) — a second pod on a DIFFERENT node stays Pending on Multi-Attach; note this does NOT protect you when both pods land on the SAME node, where CSI happily satisfies RWO for both. (5) `strategy: Recreate` (backend.yaml:85-86) — chosen for the RWO Multi-Attach race per the comment at 79-84, which is a consequence of (4), not an independent constraint. (6) In-process workers with no disable gate (main.py:41, lifecycle.py:115, and the non-existent AKB_DISABLE_WORKERS at lifecycle.py:3) — finding #5. (7) Probe comments that encode the assumption: backend.yaml:140-141 justifies the liveness tolerance with 'with replicas=1 that is a total outage'. (8) Resource sizing: a 1Gi request against a ~2.5 GB actual footprint (backend.yaml:114) — finding #6.

*실패 시나리오*: Sequence if an operator sets replicas=2 today: FIRST, scheduling decides everything — a different node gives a Pending pod and no outage (RWO Multi-Attach); the SAME node gives a running second pod and all of the below. SECOND, both pods run lifespan concurrently: `cleanup_stale_locks` over the shared PVC (lifecycle.py:79), concurrent `_apply_migrations` (postgres.py:160), concurrent `RoleSync.reconcile` (lifecycle.py:109) — the last immediately starts logging CREATE ROLE duplicate errors into the /health rbac drift counter. THIRD, on the first pair of concurrent same-vault writes to different paths, git_service.py:589 silently destroys a document. MCP session churn (http_app.py:144) begins on the first round-robined tool call. Sequence for `--workers 4`: FIRST, OOMKill at startup from 16 Kiwi children vs a 4Gi limit (sparse_encoder.py:284 + backend.yaml:120) — it never reaches the git layer. SECOND, if memory were raised: 4 concurrent migration runs (postgres.py:160). THIRD: 120 PG connections vs max_connections=200 (config.py:92 × 4, postgres.yaml:51), then the same git corruption plus meaningless probes (finding #12).

*수정 스케치*: Add an explicit comment at backend.yaml:78 naming the three CORRECTNESS blockers (git worktree lock, MCP sessions, publication throttle) so `replicas` is not read as a capacity knob. The Recreate comment at 79-84 documents the PVC constraint well but reads as if that were the only reason.

**미해결 질문**

- Kiwi memory (~351 MB at construct, ~199 MB more after first tokenize) was measured on darwin/arm64 CPython 3.11 with the pinned kiwipiepy==0.23.1. Production is linux/amd64 CPython 3.14 (backend/Dockerfile:1). The per-process multiplier is structural, but the absolute numbers need an in-cluster `kubectl top pod` / cgroup memory.current read before sizing requests/limits off them.
- `min(32, cpu+4)` for the asyncio default `to_thread` executor was verified on CPython 3.11 (measured 18 on a 14-core box) and matches the comment at write_lane.py:12. I did not verify that CPython 3.14 keeps the same default formula — worth confirming against the 3.14 stdlib before quoting the parent-process thread count precisely.
- Whether the four ⚠ vector-store drivers flagged at vector_store/base.py:186-195 (Qdrant, SeahorseCloud, SeahorseDb) actually converge under concurrent `ensure_collection` from N processes is untested. Only PgvectorStore is confirmed cross-process safe (base.py:185, pgvector.py:235). The production overlay uses pgvector (internal/backend-config-patch.yaml:48), so this is latent, not live.
- Whether the individual data migrations that claim idempotence (026_uri_collection_prefix, 035_fix_wikilink_alias_edges, 011_external_doc_collections) are idempotent under CONCURRENT execution — not just under repeated sequential execution — was not verified. Their docstrings only claim the latter.
- Whether the cluster's CSI driver would in practice bind the RWO akb-vaultdata PVC to two pods co-scheduled on one node. RWO is node-scoped for most CSI drivers, which would make the co-scheduled case the dangerous one, but this depends on the specific storage class in the internal cluster (no storageClassName is set at backend.yaml:171-176).
