### 심사 코멘트

**A — in-pod supervisor: N API processes + 1 worker process, flock-serialized git**

Explicitly keeps replicas:1 + Recreate + RWO (backend.yaml:78,85-86,172-173), so node loss is still total loss and every deploy is still an outage window — it never buys availability, by design. Write throughput is unchanged too: per-vault writes still serialize on one flock. Its central technical argument is weaker than it presents: it rejects a PG advisory lock because git commits run in write_lane's ThreadPoolExecutor (write_lane.py:94), but run_git_write (write_lane.py:188) is itself an async funnel, and I confirmed only FOUR mutation sites bypass it (external_git_service.py:125,133,134,138) — an enumerable fix, not grounds for a second lock substrate. flock is also the one coordination primitive the repo has zero precedent for, and its correctness depends on mount semantics the repo cannot declare (no storageClassName anywhere in deploy/, verified). Adds a bespoke XL PID-1 supervisor with signal forwarding, zombie reaping and probe fan-out to replicate supervision k8s gives free at pod level, and replaces an honest per-process /livez (main.py:235) with the supervisor's opinion about N children. Reversible (revert Dockerfile:17, flock layers under the existing threading.Lock) — that is its best property.

**B — split tiers: N stateless API replicas + one gitd writer/worker Deployment over internal RPC**

Does not remove the single-writer git constraint — it shrinks what is subject to it from 'all of AKB' to 'git I/O + workers', and gitd rollout is still a write-outage window. But it removes the constraint that actually caused the production incidents (one event loop shared with every worker) and buys API HA plus RollingUpdate — today strategy:Recreate makes every single deploy a hard outage. Crucially it touches NOTHING about the storage substrate: RWO stays, no RWX, no CephFS, no flock-on-unknown-mount. Given a documented CephFS/MDS outage in this cluster, that is the decisive safety property. Fit is the standout: the seams already exist (run_git_write is the single async mutation funnel; only 13 GitService() construction sites; document_service.py:266 and external_git_service.py:76 already accept `git or GitService()` injection), and because gitd is one interpreter the process-local threading.Lock at git_service.py:43-53, the shared worktree, the prune-retry and cleanup_stale_locks all keep their EXISTING safety arguments verbatim — this is the option that requires the least rewriting of the most dangerous file. Worker singleton-ness comes free from replicas:1 on gitd, so the audit hash chain, role_sync DDL and the four monotonic sweep gates become correct with zero new coordination code. Phase 1 ships with gitd_url empty = byte-identical runtime, which is the safest rollout of the three.

**C — symmetric replicas on shared RWX CephFS + PG advisory locks everywhere**

The only option that genuinely removes all of it: symmetric pods, any replica writes any vault, true HA, concurrent writes across vaults. It also fits the repo's advisory-lock idiom most elegantly and avoids the tokenizer-serving-dependency hazard entirely by keeping start_workers unconditional. And then it bets AKB's availability on the one component that has already taken AKB down. RWX in this cluster means CephFS; during an MDS stall stat()/open() block in D-state, git_write_timeout_secs (config.py:512) sends a signal a D-state process cannot receive, so all N event loops park together, all N probes fail together, kubelet SIGKILLs the fleet, and every restarting pod re-walks the stalled mount in cleanup_stale_locks (lifecycle.py:79) — a restart herd that automates the exact 'do NOT restart stateful pods' anti-pattern from the recorded incident. It converts an independent failure into an N-way correlated one. The repo cannot even confirm RWX CephFS is available (no storageClassName in deploy/, verified). Cost is an XL irreversible rewrite of git_service's write path (detached worktrees, branch-ref CAS, second connection per write, pod-scoped cleanup, hand-rolled worktree GC keyed on pod names that change every rollout), the advisory-lock protocol still has no fencing token, and rolling updates mean old and new code run against the same bare repos simultaneously with nothing in CI enforcing forward-compat. Reverting after the RWX flip means migrating data back to an RWO volume.

## 승자 선정

**Option B — split tiers: N stateless API replicas + one single-replica `akb-gitd` writer/worker Deployment owning the RWO PVC, reached by synchronous internal RPC**

B is the only option that improves availability without changing the storage substrate, and in this environment the storage substrate is the part least under the team's control and the one with a live outage record. A refuses to buy availability at all (replicas:1, Recreate, RWO all untouched by design) while still requiring ~80% of the multi-pod correctness work plus a bespoke XL supervisor. C buys the most and bets it on CephFS/MDS, turning a single-pod storage stall into an N-way correlated fleet kill with a restart herd — the precise anti-pattern the prior incident notes warn against — and pays for it with an irreversible rewrite of the most dangerous file in the repo.

B also fits what is already built, which matters most for a small team on a live service. I verified the seams: `run_git_write` (write_lane.py:188) is already the single async funnel for git mutations, `GitService()` has only 13 construction sites, and two of the important ones already accept injection. Because gitd is exactly one interpreter, the hardest code in the audit needs no rewrite at all — the process-local `threading.Lock` at git_service.py:43-53 is a CORRECT per-vault mutex again by construction, the shared worktree's `reset --hard HEAD` (git_service.py:589) has a single-writer blast radius again, and `cleanup_stale_locks`' safety docstring (git_service.py:229-234) becomes true again rather than aspirational. `write_lane` stops being a per-process lie and becomes the authoritative cluster-wide write budget, which is exactly what its own docstring says it is for. The workers that already claim with `FOR UPDATE SKIP LOCKED` keep working; the three that need singleton-ness (audit hash chain, role_sync reconcile, audit uploader) get it from `replicas: 1` on gitd instead of from new leader-election code.

Payoff ordering is also right: the largest win (every worker off the serving event loop — including the 16 blocking boto3 DELETEs per tick at s3_delete_worker.py:115 and the corpus-wide BM25 tokenize) lands at Phase 3 while the API tier is still replicas:1, so it is delivered before any replica increase and before any new concurrency exposure. And Phase 1 ships dark with `gitd_url` empty, giving a byte-identical runtime path — the safest first step of the three proposals.

The honest caveat the PM should hold B to: it delivers zero write scalability and zero write HA, and it adds a network hop inside an open PG transaction holding an advisory lock. If the real production pain turns out to be git write latency rather than event-loop stalls, B does not address it.

## 패자 안에서 이식할 것

- FROM A AND C — `update-ref` compare-and-swap (git_service.py:128). B omits this; it is non-negotiable. I confirmed the parent sha is ALREADY computed and thrown away: line 116 runs `work_repo.git.rev_parse('--verify','HEAD')` and discards the result, then line 128 calls `update_ref('HEAD', commit_sha)` with no oldvalue. Capture line 116's return and pass it as the third positional arg (empty string when `parent_required` is False, which git treats as 'ref must not exist'). Under gitd's single writer this should never fire — that is the point: it is the assertion that the single-writer invariant actually holds, and it converts a silent orphaned commit into a loud retryable 409.

- FROM C — RoleSync fixes (role_sync.py:642,690,694,700,743,969). This is a LIVE bug at replicas:1 today, not a multi-process one: the two catalog reads are separate autocommit snapshots, so a role created between them is classified as an orphan and DROPped, killing that user's akb_sql for up to an hour. Read `wanted` and `existing` in one REPEATABLE READ transaction, and route the three raw `CREATE ROLE`s through `_create_role_if_missing` (role_sync.py:1254) so duplicate-object stops permanently inflating the /health rbac drift counter (main.py:381-383) that oncall is told to trust.

- FROM C — transaction + advisory lock around `index_table_metadata` (table_service.py:538) and `index_file_metadata` (file_service.py:646). C is the ONLY option that catches this, and it is BREAKS_CORRECTNESS today at one process: both acquire a bare connection with no transaction, so `_drop_source_chunks_with_outbox`'s documented atomicity requirement (index_service.py:476-492) is violated and a half-committed outbox makes delete_worker remove LIVE vector points.

- FROM C — `await asyncio.to_thread` on the two bare `self.git.vault_exists(name)` calls (document_service.py:1734, 1874). These are the only unwrapped filesystem stats on a request coroutine, and during a CephFS MDS stall a stat() blocks in uninterruptible sleep and parks the entire event loop. Given this cluster's incident history this is a two-line, high-value graft.

- FROM C — per-migration transaction and stop treating `QueryCanceledError` as a lock conflict (postgres.py:140-157). B only adds the advisory lock around `_apply_migrations`. C additionally catches that the 30s `statement_timeout` (postgres.py:60) raises the same exception the retry loop treats as lock contention, so a slow data migration is half-applied and then re-run 10 times. - FROM C — leader-election helper generalizing `pg_try_advisory_lock` (the pattern proven at sparse_encoder.py:585-599), applied to role_sync reconcile, the audit uploader and vault_backfill. B gets singleton-ness from gitd `replicas: 1`, so this is defense-in-depth — but it directly covers B's own stated weakness: `run_workers` set wrong on the API tier silently resurrects every duplication finding with no error. Turns 'singleton by deployment config' into 'singleton enforced in code'.

- FROM C — `FOR UPDATE SKIP LOCKED` on vault_backfill's batch CTE (vault_backfill.py:127). It is the only queue worker missing it; cheap, and it stops N drainers re-applying identical 5000-row UPDATEs.

- FROM C — explicit `Kiwi(num_workers=1)` at sparse_encoder.py:218, in addition to B's config-driven pool size at :284. These are two separate defects: the pool count and the per-instance native thread count, which inherits `os.cpu_count()` and honors no cgroup quota against `requests.cpu: "1"` and no CPU limit (backend.yaml:115-118).

A silent fallback to a local GitService on a pod with no volume mount creates an empty /data/vaults and serves 404s for every document body — the worst possible failure direction.

Must be demonstrated RED on current code and GREEN after. Nothing in the suite today would go red if a second writer appeared, so every green e2e run silently bakes in the single-instance assumption.

Apply the memory correction to BOTH tiers, not just gitd; the 1Gi request against a ~2.5GB footprint makes the scheduler over-commit the node.

## 심사역이 지목한 첫 PR

**fix(perf): move blocking S3 and filesystem I/O off the serving event loop**

Wrap the remaining synchronous boto3 and filesystem calls that execute directly on the single event loop in `asyncio.to_thread`. Seven call sites, one mechanical transformation, no architectural commitment — this PR is correct and valuable under Option A, B, or C, and under 'do nothing'.

1. `s3_delete_worker.py:115` — `s3_adapter.delete(row['s3_key'])` runs synchronously inside an async worker loop, once per claimed row, BATCH_SIZE=16. Hoist the batch into one `to_thread`.
2. `access_service.py:1541` — `delete_vault` calls `s3_adapter.delete(fr['s3_key'])` in a bare `for` loop over every `vault_files` row, uncapped, while holding a pool connection.
3. `access_service.py:1565` — identical loop for publication snapshot keys.
4. `file_service.py:336` — `meta = s3_adapter.head(row['s3_key'])` on the loop. The smoking gun: line 347, eleven lines below, already does `await asyncio.to_thread(...)` for the far cheaper hash computation. This is an oversight, not a design choice.
5. `file_service.py:254` — `s3_adapter.ensure_bucket(self._bucket)` on the loop; `_bucket_verified` is only set on success, so while S3 is down EVERY upload re-issues a blocking `head_bucket`.
6. `document_service.py:1734` and 7. `document_service.py:1874` — the two bare `self.git.vault_exists(name)` calls, which are `Path.exists()` stats against the CephFS-backed PVC. Every neighbouring git call in that file already routes through `to_thread` or `run_git_write`; these two are the only unwrapped ones.

Explicitly OUT of scope, to keep the diff reviewable: switching the delete loops to batched `delete_objects`, the outbox refactor for `delete_vault`, and the `ensure_bucket` concurrent-create ClientError fix. File those as follow-ups.

**줄어드는 위험**: This is the highest-probability total-outage path in the audit that needs no attacker, no second process, and no code change to trigger — only a slow dependency. Today, with `replicas: 1`, any MinIO/S3 slowdown or CephFS MDS stall freezes the ONLY event loop: one `s3_delete_worker` tick is 16 blocking deletes at up to ~9-13s each (~144s of frozen loop) and it immediately ticks again; a `delete_vault` over 10k files blocks ~50s even against healthy MinIO. /livez and /readyz become unschedulable, readiness fails 3x8s at 15s intervals (backend.yaml:133-139) and pulls the single replica from the Service at ~45s — a 100% outage — then liveness SIGKILLs the pod at ~3min, producing a self-inflicted restart loop driven by a background worker with nothing to do with request traffic. The `vault_exists` stats are the same class against the storage layer that has already caused an AKB outage, and a SIGKILL during a CephFS stall is precisely the escalation the incident notes say makes things worse. After this PR those events degrade to slow individual requests instead of service-wide unavailability. It also removes a prerequisite hazard for the winner: Option B's own analysis concedes that Phase 3 RELOCATES the 503 to gitd rather than removing it unless these blocking calls are fixed — so this work is on the critical path regardless, and doing it first means the tier split is not the thing that has to prove it.

# 안별 상세

## OPTION A — scale UP inside one pod: a supervisor process running N API processes + exactly 1 worker process, all sharing the one RWO /data/vaults on one node, with git writes serialized by kernel flock instead of a process-local threading.Lock.

**한 줄**: Keep replicas:1 and the RWO PVC exactly as they are, but stop pretending "one process" and "one pod" are the same invariant: put a supervisor at PID 1 that runs one-shot schema/self-heal init before forking, one singleton worker process that owns all "must run exactly once" work, and N API processes whose git writes are made cross-process safe by an flock on the vault (single node ⇒ kernel-local flock is genuinely correct) plus an update-ref compare-and-swap that turns any residual race into a loud 409.

### 목표 토폴로지

ONE pod, ONE node, ONE ReadWriteOnce PVC `akb-vaultdata` at /data/vaults (deploy/k8s/backend.yaml:110-111, :172-173). `replicas: 1` (backend.yaml:78) and `strategy: Recreate` (backend.yaml:85-86) are UNCHANGED and stay load-bearing — the PVC is still single-attach and the deploy is still an outage window.

Inside the container, PID 1 becomes a new `backend/app/supervisor.py` (stdlib asyncio + os.fork/subprocess, no s6/supervisord dependency added to the image). It does three things:

(1) ONE-SHOT PRE-FORK INIT, before any child exists: `init_db()` (backend/app/db/postgres.py:80) → `init.sql` + `_apply_migrations()` (postgres.py:96,160), then `GitService().cleanup_stale_locks()` (git_service.py:206, today unconditionally per-process at lifecycle.py:78-83), then the startup `RoleSync.reconcile_from_catalog()` (today at lifecycle.py:109). Because no child process exists yet, all three become trivially single-writer — no advisory-lock ceremony required for the common path. Children boot with `AKB_SKIP_INIT=1`.

(2) FORK N API PROCESSES. N comes from a new `api_processes` setting (default 1). All N share one listening socket on :8000 — the supervisor binds it once and passes the fd, which is the same mechanism `uvicorn --workers` uses; the kernel round-robins accept(). Each child ADDITIONALLY binds a private admin listener on 127.0.0.1:8100+i serving that child's own `/livez` + `/readyz`, because a probe on the shared :8000 socket is answered by an arbitrary child and is therefore statistically meaningless (main.py:235-237, :308-319 are per-process module state). Each API child runs with workers DISABLED.

(3) FORK EXACTLY ONE WORKER PROCESS (`python -m app.worker_main`, new file): `init_storage()` + `start_workers()` (lifecycle.py:115-188), no HTTP surface. Singleton-by-construction is the whole point — the audit hash chain (`_seq`/`_prev`, audit_log.py:83-86), the audit uploader's fixed bucket key, `role_sync` reconcile DDL (role_sync.py:642), `delete_worker`/`s3_delete_worker`/`events_publisher` monotonic sweep gates, and `vault_backfill`'s un-SKIP-LOCKED batch UPDATE all become correct without inventing leader election, because there is provably one of them.

(4) SUPERVISOR OWNS THE KUBERNETES PROBES on a new port 8081. It polls each child's 127.0.0.1:8100+i admin endpoint on an interval and returns 200 only if EVERY child answers. A child that fails M consecutive polls is SIGKILLed and re-forked in-pod, so a single wedged event loop no longer requires the kubelet to SIGKILL the whole container (backend.yaml:133-141). It forwards SIGTERM to all children and waits out the shutdown budget before exiting.

GIT WRITE SERIALIZATION — the decision: `fcntl.flock(LOCK_EX)` on `/data/vaults/_locks/<vault>.lock`, layered UNDER the existing `threading.Lock` from `_VAULT_LOCKS` (git_service.py:43-53). The threading.Lock stays as the cheap uncontended intra-process fast path; the flock is only ever contended across processes. Rationale for flock over the two alternatives:
  - vs. PG advisory lock: git commits execute in `write_lane._commit_pool` (write_lane.py:94), a SYNCHRONOUS ThreadPoolExecutor. You cannot acquire an asyncpg connection from there, so a PG lock would have to be taken in async space in `write_lane()` — which does NOT cover the ungated worker paths that the module docstring itself calls out (write_lane.py:31-33: "worker paths — external_git poller, vault seeding — commit without passing this lane"), nor `cleanup_stale_locks`, nor `cleanup_vault_dirs`. flock lives inside GitService and therefore covers every caller unconditionally.
  - vs. per-process worktrees (`_worktrees/<vault>/<pid>`): multiplies a full checkout per process per vault on the PVC, multiplies the `reset --hard HEAD` stat sweep (git_service.py:589), and still does NOT fix the ref update — all worktrees share one `refs/heads/<branch>`.
  - flock is kernel-local and dies with the process (no stale-lock class of its own). Single-node is exactly the constraint that makes it sound. The lock files live in `_locks/`, deliberately NOT inside `<vault>.git`, so `cleanup_vault_dirs`' rmtree (git_service.py:307-310) cannot swap the lock inode out from under a holder.

REF UPDATE: `_stage_and_commit` (git_service.py:113-129) captures the parent sha from the existing `rev_parse --verify HEAD` at :116 and passes it as the oldvalue argument to `update_ref('HEAD', commit_sha, parent_sha)` at :128, making the ref move a compare-and-swap. Under flock this should never fire; it is the assertion that flock is working, and it converts any residual race from invisible orphaned-commit loss into a retryable conflict.

BUDGETS: the supervisor injects per-process budgets derived from a pod-wide total — `AKB_PG_POOL_MAX_SIZE` (already honored at postgres.py:33-40) = total / (N+1), and a new `AKB_WRITE_LANE_CONCURRENCY` for `write_lane._global_slots` (write_lane.py:80). Kiwi: `start_tokenizer_pool()` moves off `start_workers()` (lifecycle.py:135) onto the always-run `init_storage()` path — it is a SERVING dependency per its own docstring (sparse_encoder.py:277-279) — and its size becomes a config knob instead of `max(2, min(4, os.cpu_count()))` (sparse_encoder.py:284), set to 1 per API process and 2 in the worker. `Kiwi()` at sparse_encoder.py:218 gets an explicit `num_workers` instead of inheriting `os.cpu_count()`.

### 새로 생기는 실패 양식

- flock semantics depend on the mount, and the repo does not tell us what backs `akb-vaultdata` (no storageClassName at backend.yaml:171-176; prior incident notes reference CephFS/MDS). A kernel CephFS or local-block mount honors flock; a fuse or NFSv3 mount may accept LOCK_EX from two processes without excluding either — silently reintroducing exactly the corruption this design removes, with no error anywhere. Mitigated only by the boot-time self-test and by fail-closed behavior, which must be written and must actually be exercised in-cluster, not just locally.
- The supervisor is a new single point of failure that Kubernetes does not understand. Signal forwarding, zombie reaping, and the SIGTERM→children→grace-budget sequence must be correct or a rollout leaves orphaned git children holding index.lock — which is the exact condition `cleanup_stale_locks` exists to clean up, now made more likely rather than less. A child that crash-loops during startup can also be invisible behind a supervisor that is itself answering 200.
- Aggregated probes are less trustworthy than the honest single-process probe they replace. Today /livez is a true statement about the one event loop that matters. After Phase 4 it is the supervisor's opinion about N children, and any bug in the fan-out (a poll timeout treated as healthy, a child restarted but not re-registered) produces a pod that takes full traffic while 1/N of requests hang — strictly worse than the current behavior.
- Memory becomes the binding constraint and its blast radius grows. N API processes + 1 worker, each with a Kiwi pool, against a limit that must be re-measured on linux/amd64 CPython 3.14 (backend/Dockerfile:1) rather than trusted from the darwin/arm64 numbers in the evidence pack. An OOMKill now takes down the API tier AND the worker tier together, and with `strategy: Recreate` that is a full outage.
- The `update_ref` compare-and-swap introduces a new user-visible write failure path. If the conflict is not wired into `write_lane`'s retry (write_lane.py:105-140) it surfaces as a 5xx on writes that previously queued silently — trading invisible corruption for visible errors is the right trade, but only if the retry actually exists.
- Pre-fork one-shot init means migrations no longer run inside the API process. A developer running `uvicorn app.main:app` directly, or any deployment path that bypasses the supervisor (deploy/all-in-one/), now boots against an unmigrated database unless the `AKB_SKIP_INIT` gate defaults to 'run when unsupervised' — an easy default to get backwards, and the failure is a confusing runtime error rather than a boot failure.
- The worker singleton is enforced only by the supervisor's process table. A `kubectl exec`-launched second worker, or a stale child surviving a failed restart, silently duplicates the audit hash chain (audit_log.py:83-86), the audit uploader's fixed bucket key (audit_log.py:373), and the role-sync DDL — with no detection mechanism anywhere in the code.
- Per-process budget injection is a new class of misconfiguration. `AKB_PG_POOL_MAX_SIZE` and `AKB_WRITE_LANE_CONCURRENCY` must be divided by the process count; get it wrong and N×30 connections hit `max_connections=200` (deploy/k8s/postgres.yaml:51), where `TooManyConnectionsError` is not in `get_pool`'s retry tuple (postgres.py:65) and a cold process crash-loops instead of backing off.

### 스스로 진술한 치명적 약점

Option A never buys availability, and it never will — `replicas: 1`, `strategy: Recreate`, and the ReadWriteOnce PVC (deploy/k8s/backend.yaml:78, 85-86, 172-173) are untouched by design, so node loss is still total loss and every deploy is still an outage window. Yet to get there you must build roughly 80% of the correctness work a genuine multi-pod migration needs anyway — the cross-process vault lock, the update-ref CAS, the worker-tier split, the PG-backed publication throttle, the MCP session fix, the migration serialization — and then ADDITIONALLY build a bespoke in-pod supervisor and probe aggregator (backend/app/supervisor.py, an XL new component with its own signal-handling and health-fan-out failure modes) to replicate supervision that Kubernetes gives you for free at the pod level. And the ceiling you buy is small: per-vault git writes still serialize on one flock, so write throughput for a hot vault improves by exactly zero; Kiwi's ~550MB-per-loaded-process footprint against the memory limit caps you at roughly 2-3 API processes; and the volume, the node, and the single failure domain are unchanged. You pay most of the price of multi-pod, keep multi-pod's single worst limitation, and the payoff is a ~3× ceiling on read/API concurrency plus better isolation of workers from the serving loop. If the honest goal is surviving a node, Phases 1-3 of this plan are the right work and Phase 4 is the wrong destination for it.

## Option B — split tiers: N stateless API replicas + one gitd writer/worker Deployment owning the RWO volume, reached by synchronous internal RPC

**한 줄**: `write_lane.run_git_write` and `GitService()` are already the only two seams that touch git, so the split is a factory swap plus a thin internal HTTP tier — and because the RPC stays synchronous inside the existing PG transaction, `akb_put` still returns a real commit hash and the client contract does not change at all.

### 목표 토폴로지

TWO Deployments, one image, two entrypoints.

TIER 1 — `akb-backend` (API): replicas: N, strategy RollingUpdate, ONE uvicorn process per pod (no `--workers`; per the probe finding, `--workers` makes /livez and /readyz statistically meaningless because all workers share one listening socket, so replicas is the only honest scaling axis). NO `vaultdata` volumeMount. Runs `app.main:app` with `settings.run_workers=false`, so `start_workers()` (main.py:41) is skipped. Still runs the Kiwi tokenizer ProcessPool and the git commit pool, which move out of `start_workers()` into `init_storage()` — sparse_encoder.py:277-279 states outright that the pool is a SERVING dependency of `encode_query`, so leaving it behind a worker gate silently restores the GIL-serialization path that caused the original 503 incident. All `GitService()` construction goes through a new `get_git()` factory returning a `GitClient` RPC stub.

TIER 2 — `akb-gitd` (writer + workers): replicas: 1, strategy Recreate, `terminationGracePeriodSeconds: 180`, sole owner of the `akb-vaultdata` RWO PVC at /data/vaults. ONE uvicorn process running a new `app.gitd_main:app` on a ClusterIP-only Service `akb-gitd:8100` (no Ingress rule, bearer token + NetworkPolicy). Its lifespan runs `init_storage()` + `start_workers()` — all 11 background loops, including the external_git_poller which is the one worker that calls GitService directly and unlaned (external_git_service.py:123-138) and therefore must live where the volume is.

WHICH TIER OWNS THE VOLUME: gitd, exclusively. RWO already forces replicas:1 on whoever holds it; Option B accepts that constraint and shrinks the thing subject to it from "all of AKB" to "git I/O + background jobs".

HOW GIT WRITES ARE SERIALIZED: unchanged from today, and correct again by construction. `git_service._VAULT_LOCKS` (git_service.py:43-53) is a process-local `threading.Lock`, which is a valid per-vault mutex precisely because gitd is exactly one interpreter. The non-CAS `update_ref('HEAD', commit_sha)` (git_service.py:128), the shared-worktree `reset --hard HEAD` (git_service.py:589), the `_ensure_worktree` prune-retry (git_service.py:151-167) and the startup `cleanup_stale_locks()` (lifecycle.py:79) all keep their existing single-process safety arguments verbatim. gitd's own `write_lane` (`_global_slots`, write_lane.py:80) becomes the authoritative cluster-wide write budget; the API tier's lane degrades to client-side admission only.

QUEUE: none — deliberately. `run_git_write` is already an `await` (document_service.py:491) inside the transaction opened by `_path_lock` (document_service.py:338-343), and its result feeds `doc_repo.create(..., commit_hash=...)` at :516 in that same transaction. Replacing a ThreadPoolExecutor dispatch with an HTTP round-trip preserves that exact ordering. A PG outbox would invert it (PG first, git later), which would strip the commit hash out of the `akb_put` response and add a SECOND git/PG divergence direction on top of the one that already exists at :491-vs-:516.

READ-YOUR-WRITES: free. The API replica builds its response from the transaction it committed itself, and every subsequent read is commit-pinned — `document_service.py:597` reads `git.read_file(vault, path, row['current_commit'])`. Git objects are immutable and content-addressed, so any API replica asking gitd for that sha gets the right bytes with no replication lag to reason about. This also makes `(vault, path, commit_sha) -> content` a pure function, so the API tier can cache it in a bounded LRU.

### 새로 생기는 실패 양식

- Hard cross-tier dependency that did not exist before: a NetworkPolicy mistake, DNS blip, or gitd CrashLoop turns every git read and write into a 429/503 where it used to be a local function call. Today git I/O cannot fail for network reasons; after Phase 3 it can.
- Latency amplification into the PG pool. `run_git_write` at document_service.py:491 is called INSIDE the transaction opened by `_path_lock` (document_service.py:338-343), holding a pooled connection and a `pg_advisory_xact_lock`. That hop is now a network round-trip, so a slow gitd converts directly into pool occupancy and `idle_in_transaction_session_timeout` (60s, postgres.py:61) risk on every API replica at once — a coupling the local thread-pool dispatch did not have.
- gitd becomes a shared event loop for N replicas' git I/O AND every background worker — including the still-blocking `s3_delete_worker.py:115` (16 sync boto3 DELETEs per tick) and `access_service.py:1541` (one blocking S3 DELETE per file in a bare loop). Those bugs used to stall one pod's own requests; now a degraded MinIO stalls git reads for the whole cluster. Phase 3 RELOCATES the 503 rather than removing it unless those are fixed alongside.
- A `gitd_url` misconfiguration fails open in the worst direction: `get_git()` falls back to a local GitService on a pod with no volume mounted, which silently creates an empty /data/vaults and serves 404s for every document body. Requires a boot-time assertion, never a default.
- New privileged internal surface. gitd carries unrestricted write authority over every vault and performs NO ACL checks — all authorization stays on the API tier. Anything that can reach `akb-gitd:8100` can rewrite any vault's git history, so ClusterIP + bearer token + NetworkPolicy are correctness requirements, not hardening.
- Two entrypoints and two config surfaces drift. `settings.run_workers` set wrong on the API tier resurrects every duplication finding (N tokenizer pools, N role_sync reconcilers issuing CREATE/DROP ROLE, N audit uploaders racing one bucket key) with no error — just a slowly poisoned /health rbac drift counter (main.py:381-383).

### 스스로 진술한 치명적 약점

Option B keeps a single-writer git tier, so it buys read/API scalability and deploy safety while delivering exactly zero write scalability and zero write HA — and charges a distributed system for it. After all four phases, every write in AKB still funnels through one `threading.Lock` in `_VAULT_LOCKS` (git_service.py:43-53), in one interpreter, on one ReadWriteOnce PVC. Write throughput is identical to today. Write availability during a gitd rollout is a fresh outage window that today's Recreate deploy also had, so that is a wash. What you have added is a ~19-method RPC protocol, a second Deployment and image entrypoint, a new privileged internal attack surface, a network hop inside an open PG transaction holding an advisory lock, and a fail-open misconfiguration mode. If the actual production pain turns out to be git write latency or write availability rather than event-loop stalls, none of this touches it. The uncomfortable comparison: fixing the three underlying defects directly — swap `_VAULT_LOCKS` for a PG advisory lock keyed on vault, pass the observed parent as the oldvalue CAS argument to `update_ref('HEAD', commit_sha, parent_sha)` at git_service.py:128, and give each process a private worktree so `reset --hard HEAD` (git_service.py:589) has a process-local blast radius — is maybe a few hundred lines, needs no new tier, no RPC, and no new failure class, and it lets N symmetric replicas write concurrently instead of serializing them all through one pod. Option B's honest pitch is that it isolates the fragile stuff (workers, blocking boto3, the tokenizer, grep) from the serving loop, which is a real and large win; but it should not be sold as the fix for the git scaling blocker, because it does not fix it — it just moves it somewhere with a smaller audience.

## Option C — symmetric replicas on a shared RWX CephFS volume, with every process-local lock replaced by a Postgres advisory lock so any replica can write any vault

**한 줄**: Keep one Deployment of identical pods; make the git write path multi-writer-safe by giving each pod its own DETACHED worktree, serializing per-vault with a session-scoped pg_advisory_lock on a dedicated connection, and making the branch-ref move a real compare-and-swap — then move /data/vaults to RWX CephFS and raise replicas.

### 목표 토폴로지

N=3 pods of ONE Deployment (deploy/k8s/backend.yaml:78), each running exactly ONE uvicorn process — no `--workers`, ever: backend/app/main.py:235 `/livez` and the 30s-cached `/readyz` (main.py:240,296-305) are per-process, and behind a shared listening socket a wedged worker would be invisible to the kubelet; `--workers 4` also means 16 Kiwi children (sparse_encoder.py:284) against the 4Gi limit (backend.yaml:120). So: 3 pods × (1 uvicorn parent + 4 Kiwi children + 8 commit threads).

`akb-vaultdata` (backend.yaml:171-176) flips ReadWriteOnce → ReadWriteMany with an explicit CephFS `storageClassName`, mounted at /data/vaults on all 3 pods (backend.yaml:110-111). NFS is disqualified — git needs cross-client-atomic `O_CREAT|O_EXCL` on `<ref>.lock`/`packed-refs.lock`, which NFSv3 does not reliably provide; CephFS does.

Ownership split on that shared volume:
- SHARED, cross-pod: `<storage>/<vault>.git` — the bare repo's object store (content-addressed, tmp+rename, append-only) and `refs/heads/<branch>`. This is the source of truth and the ONLY thing pods contend on.
- POD-PRIVATE: worktrees move from `<storage>/_worktrees/<vault>` (git_service.py:79-80) to `<storage>/_worktrees/<vault>__<POD_NAME>`. Every `reset --hard HEAD` (git_service.py:589,619,658,718) then has a pod-private blast radius, and `index.lock` is never contended across nodes. Because `_ensure_worktree` currently checks out the branch (git_service.py:145-151) and git refuses a second worktree on a checked-out branch, pod worktrees are created with `git worktree add --detach`.

Git write serialization, three layers, each doing a distinct job:
1. Per-pod admission (unchanged): `write_lane._vault_gates` / `_global_slots` (write_lane.py:75,80) stay as a LOCAL resource guard — they bound this pod's PG connections and commit threads. Their budget is divided by replica count.
2. Cross-pod mutual exclusion (new): `pg_advisory_lock(hashtext('akb:git'), hashtext(vault))` on a DEDICATED asyncpg connection from a small side pool, acquired inside `write_lane(vault)` after the local gate and BEFORE the caller opens its transaction, released in `finally`. Session-scoped (not `_xact_`) because the git work happens on the commit executor, outside the caller's transaction. Every one of the 8 `_vault_lock` sites (git_service.py:200,307,350,403,579,613,652,711) moves behind it, including the worker paths that bypass the lane today (external_git_service.py:125,133-134,138).
3. Loud failure backstop (new): `_stage_and_commit` (git_service.py:113-129) is rewritten for the detached model — read the branch tip from the bare, `reset --hard <tip>`, `commit-tree -p <tip>`, then `update-ref refs/heads/<branch> <new> <tip>`. That third argument is the compare-and-swap git already supports and AKB never passes. If layer 2 ever fails (partition, lock bug), the ref move fails loudly and the write lane retries the whole sequence, instead of silently orphaning a peer's commit.

Singleton work uses leader election, not a separate tier: a new `app/services/leader.py` generalizes the pattern already proven at sparse_encoder.py:585-599 (`pg_try_advisory_lock` on a held connection, loser returns immediately). Applied to role_sync reconcile (lifecycle.py:109,183-186), the four monotonic sweep gates (delete_worker.py:39,209; s3_delete_worker.py:35; events_publisher.py:47), vault_backfill, and the audit uploader. The six queue workers that already claim with `FOR UPDATE SKIP LOCKED` (embed_worker.py:70, delete_worker.py:56, s3_delete_worker.py:65, metadata_worker.py:71, events_publisher.py:100, external_git_poller.py:49) are left alone — they scale correctly and are the reason a symmetric topology is viable at all. `start_workers()` (lifecycle.py:115) stays unconditional; no `worker_main`, no tier split, so the tokenizer-pool-is-a-serving-dependency hazard (sparse_encoder.py:276-279) never arises.

MCP is pinned rather than shared: `/mcp` gets its own Ingress rule with `nginx.ingress.kubernetes.io/upstream-hash-by: "$http_mcp_session_id"`, AND http_app.py:141-151 stops minting a session for an unknown non-null id (404 instead), so a client that lands wrong recovers by re-initializing rather than getting an orphan.

### 새로 생기는 실패 양식

- Advisory locks have no fencing token. When a node hard-partitions, PG eventually reaps the dead session and releases the vault lock — but the partitioned pod may still be alive and mid-`git add` on the CephFS mount (CephFS and PG are different network paths; losing one does not imply losing the other). A new leader then legitimately enters the same vault's sequence. The branch-ref CAS (git_service.py:128 rewritten) catches the ref collision, and pod-private worktrees keep the index damage local — but `cleanup_vault_dirs`' rmtree (git_service.py:307-310) and `clone_mirror` (349-356) have no equivalent guard. This is the irreducible residual risk of the design and cannot be engineered away with PG locks alone.
- Postgres becomes a hard dependency of the GIT write path. Today a PG hiccup fails the DB half of a write; after this change it blocks the write from starting at all. Worse, each in-flight vault write now pins TWO connections — the lock connection plus the caller's transaction connection — so the write path's connection cost doubles at exactly the moment (a write burst) when the pool is tightest. This is why the lock must come from a dedicated side pool, and it is a new coupling that did not exist before.
- CephFS/MDS becomes a CORRELATED failure domain across every replica. The environment has already had an AKB 503 traced to a CephFS/MDS stall with an I/O-probe-hang signature. Under Option C, /data/vaults is a CephFS mount on all N pods: an MDS stall parks all N event loops in uninterruptible D-state on `stat()`/`open()` simultaneously, `git_write_timeout_secs` (config.py:512) cannot reap a D-state process, all N liveness probes fail together, kubelet SIGKILLs all N, and every restarting pod immediately re-walks the stalled mount in `cleanup_stale_locks` (lifecycle.py:79) — a restart herd against a sick MDS, which is precisely the 'do not restart stateful pods' anti-pattern already recorded for this cluster.
- Worktree storage multiplies by N and leaks per pod name. Each pod holds a full checkout of every vault it has written, under `_worktrees/<vault>__<POD_NAME>`. On a 20Gi PVC (backend.yaml:174-176) three pods triple the working-tree cost, and because Kubernetes mints a new pod name on every rollout, every deploy strands a dead pod's worktree directory AND its `<bare>/worktrees/<vault>__<old-pod>` registration. Left ungarbaged this grows without bound.
- `git worktree prune` becomes actively destructive and there is no scoped form of it. The current retry at git_service.py:159-167 prunes globally, which under shared storage reaps a live peer's registration mid-`worktree add` — the peer then holds a worktree whose administrative directory no longer exists and every write to that vault 500s until an operator intervenes. The replacement is a hand-rolled targeted removal keyed on this pod's own name, which is exactly the kind of bespoke GC that goes wrong quietly.
- Rolling updates now run OLD and NEW code against the same bare repos simultaneously. Any future change to the git layout, the commit-message format, or the worktree naming convention must be forward-compatible for one release, and nothing in the repo or CI enforces that. Recreate previously made this impossible by construction.
- The non-pgvector drivers' `ensure_collection` has no cross-process guard — base.py:184-198 marks Qdrant, SeahorseCloud and SeahorseDb with ⚠ by the file's own audit, versus PgvectorStore's `pg_advisory_xact_lock` (pgvector.py:274-277). Production is pgvector (internal/backend-config-patch.yaml:48) so this is latent, but Option C makes a driver switch a correctness decision rather than a performance one. Also `CREATE EXTENSION IF NOT EXISTS vector` (pgvector.py:269) runs in AUTOCOMMIT before the lock is taken, so even pgvector has a fresh-DB cold-start race at N pods.
- MCP correctness now depends on an nginx annotation. `upstream-hash-by: $http_mcp_session_id` is invisible to the application, untested by any suite (nothing in backend/tests references `_transports` or `MCPApp`), and silently ineffective if someone edits the Ingress, changes ingress controllers, or a client omits the header. The Phase 2 404-on-unknown fix is the real safety net; the affinity is only an optimization, and it must be framed that way or it will be trusted as a guarantee.

### 스스로 진술한 치명적 약점

This design bets AKB's availability on CephFS — and CephFS/MDS is the one component that has already taken AKB down, in a way horizontal replication makes strictly worse rather than better. Today `akb-vaultdata` is a ReadWriteOnce volume (backend.yaml:172-173) with no storageClassName, and an MDS problem is at worst one pod's problem. Option C requires ReadWriteMany, which in this cluster means CephFS, which means every replica shares one metadata server as a mount dependency. During an MDS stall, `stat()` and `open()` on that mount block in uninterruptible D-state; `git_write_timeout_secs`' kill_after_timeout (config.py:512) sends a signal a D-state process cannot receive; so all N event loops park at once, all N `/livez` probes fail at once, and the kubelet SIGKILLs the entire fleet — then every restarting pod immediately walks the stalled mount again in `cleanup_stale_locks` (lifecycle.py:79). You get N-way correlated failure, a restart herd against sick storage, and the explicit "do not restart stateful pods" guidance from the prior incident violated automatically by Kubernetes. And you pay for it with an XL, irreversible rewrite of the git write path — detached worktrees, branch-ref CAS, a second connection per write — whose lock protocol still has no fencing token, so the "a replica died holding the lock" case is only *mostly* safe (the CAS covers the ref; `cleanup_vault_dirs` and `clone_mirror` are still exposed). The honest summary: Option C buys real request-level capacity and removes deploy outages, but it does not improve — and probably degrades — resilience against the specific failure that has actually caused AKB's outages, and the storage substrate is the part of the design least under this team's control.
