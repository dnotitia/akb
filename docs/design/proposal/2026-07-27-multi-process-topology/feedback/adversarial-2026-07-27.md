### [PARTIALLY_WRONG] git_service.py:128 `update_ref` performs no compare-and-swap, so a concurrent commit is silently orphaned — and the fix is to capture the sha already read by the existing `rev_parse --verify HEAD` at git_service.py:116 and pass it as the oldvalue (asserted identically by the evidence pack and by all three proposals, Option A [S] change, Option B rationale, Option C [XL] change (b)).

The CORE claim SURVIVES verbatim: git_service.py:128 is literally `work_repo.git.update_ref("HEAD", commit_sha, **_write_kt())` — two positional args, no oldvalue. But the FIX RECIPE all three proposals share is wrong on the code as written. git_service.py:116 is `work_repo.git.rev_parse("--verify", "HEAD", **_write_kt())` with the return value DISCARDED — nothing is assigned, so there is no sha to 'capture'; a new assignment is required. Worse, that line is inside `if parent_required:` (git_service.py:115-118) and `parent_args` stays empty otherwise. `commit_file` passes `parent_required=True` (git_service.py:586-592) but `_stage_and_commit` is a shared helper with a `parent_required=False` branch (the first commit on a fresh branch, and `_commit_via_clone`'s sibling path at git_service.py:741). For that branch the correct CAS is not `update-ref HEAD <new> <old>` but the must-not-exist form (`update-ref HEAD <new> ""`), which no proposal mentions. Shipping the recipe as written either NameErrors on the no-parent branch or silently keeps the non-CAS write there. Also: `update_ref('HEAD', ...)` moves the symref target (refs/heads/<branch>) only because `_ensure_worktree` attaches the worktree to the branch (git_service.py:151 `worktree("add", str(wt), branch_name)`); Option C's switch to `--detach` breaks that assumption, which Option C does handle but Options A/B do not need to.

Repo-wide grep for `worker_main|DISABLE_WORKERS` excluding .git/node_modules/__pycache__ returns exactly ONE hit: backend/app/services/lifecycle.py:3. `ls backend/app` shows __init__.py, __main__.py, api, cli.py, config.py, db, exceptions.py, main.py, models, openapi_contract.py, repositories, services, util, utils.py — no worker_main.py. backend/Dockerfile:17 is `CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]` with no --workers, confirming exactly one process today. Claim fully confirmed.

backend/mcp_server/http_app.py:141-152: `if session_id and session_id in _transports: transport = _transports[session_id]` / `else: session_id = str(uuid.uuid4()); transport = StreamableHTTPServerTransport(mcp_session_id=session_id, is_json_response_enabled=True); _transports[session_id] = transport; _session_users[session_id] = user; await _ensure_server_running(...)` then `await transport.handle_request(...)`. ### [REFUTED] OPTION A's central design decision: flock inside GitService is the right primitive BECAUSE 'git commits execute in write_lane._commit_pool, a SYNCHRONOUS ThreadPoolExecutor. You cannot acquire an asyncpg connection from there, so a PG lock would have to be taken in async space in write_lane() — which does NOT cover the ungated worker paths'.

The coverage half is right; the ORDERING half is backwards, and it reintroduces the exact bug write_lane was written to eliminate. Call chain verified: document_service.py:338 `async with write_lane(vault_name)` → `_path_lock` acquires a pool connection + `pg_advisory_xact_lock` inside an open transaction → document_service.py:491 `await run_git_write(self.git.commit_file, ...)` → write_lane.py:245-250 `_dispatch_to_pool` → `loop.run_in_executor(_commit_pool, ...)` → git_service.py:579 `with _vault_lock(vault_name)`. Option A puts a BLOCKING cross-process flock at that last step. write_lane.py:5-22 names precisely this as the two starvation paths it exists to fix: '1. Pool poisoning: a writer queued for the per-vault git lock while holding a pool connection inside an open transaction... 2. Executor starvation: that queueing happened INSIDE a thread of the shared executor', and write_lane.py:23-25 states the fix is 'admission in front of resource acquisition, into event-loop space where waiting is a suspended coroutine'. write_lane.py:91-93 sizes `_commit_pool` to write_lane_concurrency 'admitted writers only, so there is never queueing here in the steady state' — an assumption that is false the moment a peer PROCESS holds the flock, because each process's `_vault_gates` (write_lane.py:75) admits its own writer per vault. At N processes, N-1 writers per hot vault block in a commit-pool thread holding a main-pool connection in an open transaction, reachable by `idle_in_transaction_session_timeout` (60s). Option C's placement — acquire the cross-process lock inside `write_lane(vault)` after the local gate and BEFORE the caller opens its transaction — is the correct order, and Option A rejects it for a reason that is actually the argument FOR it.

### [REFUTED] OPTION C's mechanism: 'inside write_lane(vault) acquire vault_git_lock(vault) immediately after the per-vault gate + global slot and before yielding... do the same in run_git_write (~line 195) for the ungated lifecycle/worker callers the module docstring at lines 31-33 explicitly says bypass the lane', with vault_git_lock taking a session-scoped pg_advisory_lock on a dedicated side-pool connection.

Three independent defects, all verifiable. (a) SELF-DEADLOCK: every document write already nests run_git_write INSIDE write_lane — document_service.py:338 `async with write_lane(vault_name)` then document_service.py:491/850/1013/1225 `await run_git_write(...)`; collection_service.py:415-421 does it explicitly (`async with write_lane(vault): await run_git_write(self.git.delete_paths_bulk, ...)`). Because vault_git_lock uses a DEDICATED side-pool connection, the inner acquisition is a DIFFERENT PG session from the outer one, so `pg_advisory_lock` on the same key blocks forever on a lock the same task already holds — a permanent hang on the primary write path, not a rare race. write_lane.py:70/150/225 already ships the exact ContextVar (`_slot_held`) that run_git_write uses to detect this nesting; Option C never mentions reusing it. (b) VAULT NAME IS NOT DERIVABLE: `run_git_write(fn, /, *args, must_complete=False, **kwargs)` (write_lane.py:188) is vault-agnostic and callers are inconsistent — KEYWORD at document_service.py:492 (`vault_name=req.vault`), :851, :1014, :1226 and collection_service.py:417; POSITIONAL at document_service.py:1738 (`run_git_write(self.git.init_vault, name)`), :1879 (`self.git.cleanup_vault_dirs, name`) and access_service.py:1628 (`GitService().cleanup_vault_dirs, vault_name`). No generic extraction exists. (c) COVERAGE HOLE — the most destructive worker path is not on either insertion point: `ensure_local_bare` calls `self.git.clone_mirror` (external_git_service.py:125), `self.git.cleanup_vault_dirs` (:133), `self.git.clone_mirror` (:134) and `self.git.fetch_remote` (:138) SYNCHRONOUSLY, and it is dispatched via `await asyncio.to_thread(self.ensure_local_bare, ...)` at external_git_service.py:174 — NOT via run_git_write. So Option C leaves the rmtree-then-reclone path completely unlocked, which is the one path Option A's in-GitService placement would have covered.

## 2. 누락된 차원

### Observability — you cannot tell which replica served a request or emitted a log line

**왜 중요한가**: backend/app/main.py:29-33 sets `format="%(asctime)s %(levelname)s %(name)s: %(message)s"` — no pid, no hostname, no pod name. A repo-wide grep of backend/app and backend/mcp_server for `X-Request-Id|request_id|correlation|POD_NAME|HOSTNAME|socket.gethostname|instance_id` returns zero relevant hits: there is no correlation-id middleware, no response header carrying replica identity, and nothing stamps process identity into logs. Every single divergence finding in the evidence pack is diagnosed by COMPARING replicas — BM25 `_stats_cache` skew (sparse_encoder.py:387), `vault_backfill._ready` (vault_backfill.py:42), `/health` rbac drift counters (main.py:381-382), `write_lane.snapshot()` waiters, MCP session churn. With N processes interleaving into one stdout stream you cannot attribute any of them. Not one of the three proposals adds a single line of this, yet Option A's supervisor makes it strictly worse (N children on one stdout with no pid) and Option B's aggregated /health hides which tier answered.

**해야 할 것**: Before raising any process count: add pid + POD_NAME (Downward API) to the logging format at main.py:31; add a request-id middleware next to the existing CORS/cache-control middlewares (main.py:178-208) that echoes an `X-AKB-Instance` response header; and stamp the instance id into every per-process value `/health` reports (write_lane.snapshot, rbac metrics_snapshot, vault_backfill.pending_stats.ready) so an operator can tell 'stale replica' from 'real drift'. This is a prerequisite for verifying ANY of the three options in production, not a nice-to-have.

### The Node proxy replays writes on 404 — and all three options ship a change that makes 404 the common case, with no proxy fix

**왜 중요한가**: Verified end to end: `_http` rejects with `new Error(\`HTTP ${res.statusCode}: ...\`)` (packages/akb-mcp-client/lib/proxy.mjs:655-657); `_forward`'s classifier matches `err.message.includes("404")` (proxy.mjs:688-694); on a match it nulls `this.sessionId`, re-runs `initialize`, then `continue`s the loop and calls `this._rpc(msg.method, msg.params || {})` again (proxy.mjs:681) — REPLAYING the original tools/call, up to 2 extra times. Every one of the three proposals lists 'make the POST path 404 on an unknown mcp-session-id' as a change (Option A [L], Option B [M], Option C [M]), and NOT ONE lists a proxy.mjs change. Combined with `akb_put` being create-only with `-shortid` collision suffixing, the recommended hardening converts an MCP protocol error into a silent duplicate document. Options A and C schedule the 404 change in Phase 2/3 with the proxy untouched forever.

**해야 할 것**: Sequence the proxy fix FIRST, not at all-never: narrow proxy.mjs:688-694 so replay is allowed only for read-only methods (tools/list, resources/*, and the read-only akb_* tools) or for pre-write transport errors (ECONNREFUSED before bytes were written); for write tools surface the error. Then ship a proxy version floor and a `packages/akb-mcp-client/CHANGELOG.md` entry per AGENTS.md:66 ('Deploy checklist (proxy changes)'), and only then land the backend 404. Add a test — grep confirms nothing under backend/tests or packages/akb-mcp-client/test references `_transports` or `MCPApp`.

### Backup, restore, and disaster recovery do not exist as tooling

**왜 중요한가**: `grep -rln 'backup|restore|pg_dump' scripts/ deploy/ docs/` returns only two prose mentions in docs/ and ZERO in scripts/ or deploy/. `ls scripts/` is bench_pg_rbac.py, bump-version.sh, check-workspace-account-governance.sh, check.sh, keycloak, run_canonical_e2e.sh, run_regression.sh — no backup, no restore, no consistency-snapshot helper. Yet PG and git must be snapshotted CONSISTENTLY (the evidence's own finding: `documents.current_commit` is written after the git commit at document_service.py:491-vs-:516, so a PG-only or git-only restore is guaranteed divergent). All three options change on-disk layout or ownership: Option A adds `<storage>/_locks/`, Option C adds `_worktrees/<vault>__<pod>` and `<vault>.git.deleting-<uuid>` tombstones, Option B reassigns the PVC to a new Deployment. Restoring into any of these from a pre-change backup is untested and undocumented.

**해야 할 것**: Write and exercise a restore drill BEFORE the first topology change: a script that quiesces writes (the write lane already has a natural chokepoint), snapshots PG and /data/vaults, and a verifier that asserts every `documents.current_commit` is an ancestor of its vault's HEAD (this check does not exist anywhere — resource_integrity.repair_resource_hashes at resource_integrity.py:71-116 recomputes hashes FROM current_commit and structurally cannot detect git-ahead-of-DB). That verifier is also the acceptance test for every option's Phase 1.

### Rolling updates run pre- and post-migration schema simultaneously — the thing `strategy: Recreate` was silently buying

**왜 중요한가**: deploy/k8s/backend.yaml:78-86 is `replicas: 1` + `strategy: Recreate`, and the comment there justifies Recreate ONLY on the RWO Multi-Attach race. But Recreate also structurally guarantees that no old-schema pod is serving while a new pod runs `_apply_migrations()` (backend/app/db/postgres.py:96,160). Option C explicitly moves to `RollingUpdate maxSurge:1 maxUnavailable:0` and Option B moves the API tier to RollingUpdate — in both, a NEW pod applies migrations while OLD pods keep serving against the pre-migration schema. Option C's own 'new failure modes' section reasons about old/new code sharing git repos but never about old/new code sharing a MIGRATED schema. With 21 of 45 migrations opening no transaction of their own (per the evidence, and postgres.py:140-147 shows the migration body and its ledger INSERT are not wrapped either), a DDL that drops or renames a column mid-rollout 500s every request on the old pods.

**해야 할 것**: Decide and document a migration compatibility contract before either option's rolling-update phase: either (a) migrations move to a k8s Job/initContainer gated ahead of the rollout with an expand/contract discipline (add-only in release N, drop in release N+1), or (b) keep Recreate for any release whose migration list is non-empty and only roll when it is empty. Also add the missing `async with conn.transaction():` around `module.migrate()` + the ledger INSERT at postgres.py:140-147 regardless of option — that one is a live defect at N=1.

### The frontend polls per-process /health state on a 15s timer and no option mentions it

**왜 중요한가**: frontend/src/hooks/use-health.ts:16 sets `const ENDPOINT = "/health"` and :45 `const id = setInterval(tick, intervalMs)`; frontend/src/hooks/use-vault-health.ts:5,13,48 polls `/health/vault/{name}` every 15s. `/health` returns per-process values — `write_lane.snapshot()`, `get_role_sync().metrics_snapshot()` (main.py:381-382), `vault_backfill.pending_stats()['ready']` (vault_backfill.py:42-48). Behind a round-robin Service these will visibly OSCILLATE in the UI every 15s (rbac error counts flipping between 0 and 140, backfill readiness flipping true/false) with no user-visible cause. All three proposals discuss /health only from the kubelet's point of view; none mentions the frontend at all, and none checks what a UI does with contradictory consecutive polls.

**해야 할 것**: Split /health's payload into cluster-truth fields (PG COUNT-backed: embed_backfill, vector backfill, events backlog — these are already safe) and per-instance fields, label the latter with the instance id from the observability gap above, and make the frontend either aggregate or clearly render them as per-instance. At minimum, verify the two hooks' rendering against alternating responses before raising any replica count.

### The concurrency test suite exists but nothing would run the proposed multi-process test in CI

**왜 중요한가**: backend/tests/concurrency/ already contains repro_e01_multivault.py, repro_e02_samepath.py, repro_e03_update_race.py, repro_e05_e06_delete_race.py, repro_pub_security.sh, test_invariants.sh, test_invariants_unit.py, test_alter_unique_race_unit.py, test_ensure_collection_race_unit.py — so the harness precedent is there. But every e2e script targets one backend (`BASE_URL="${AKB_URL:-http://localhost:8000}"`, test_e2e.sh:8) and none spawns a second process. Option A proposes one new file (test_git_multiprocess_flock.py) and Option C proposes one (test_git_multiprocess_race.py); NEITHER proposes a CI wiring change, a docker-compose/kind two-backend fixture, or an addition to scripts/run_regression.sh / scripts/check.sh. A test that exists but is never executed is the same as no test, and both options make it the sole gate for their Phase 1. One thing that DOES survive: `wait_for_indexing` (backend/tests/_wait_for_indexing.sh) polls /health for `embed_backfill.pending`, which is a PG `COUNT(*)` in embed_worker.pending_stats — replica-agnostic, so the existing e2e suites will not go spuriously red on that axis.

**해야 할 것**: Land the two-process fixture and its CI invocation in the SAME change as the test: a conftest/compose fixture that boots two backends against one Postgres and one git_storage_path, plus a line in scripts/run_regression.sh (or check.sh) that runs it. Demonstrate it RED on the pre-fix commit — both options claim this but neither says where it runs.

### Option B's gitd tier sits entirely outside the 44-test cross-vault isolation suite, and its wire format is unspecified for binary

**왜 중요한가**: AGENTS.md:86 documents `backend/tests/test_pg_rbac_e2e.sh` as 'PG-native vault isolation: cross-vault probes via SQL surface variations (44 tests, includes system-catalog access, schema-qualified, quoted, UNION/CTE/EXISTS/subquery, filesystem functions, DDL-shaped attempts, reader-scope writes)'. Option B's gitd 'does NO ACL logic — authorization stays entirely on the API tier', which means a single internal endpoint `cat_blob(vault_name, blob_sha)` reads any blob in any vault with no vault check. That is a new read surface that the entire tested isolation model does not cover, and Option B frames the NetworkPolicy as the only control. Separately, the wire format is undefined for at least one method: `cat_blob` returns raw `bytes` (git_service.py:483, `repo.git.cat_file("blob", blob_sha, stdout_as_string=False)`), which cannot go over the proposed JSON POST without base64; `clone_mirror`/`fetch_remote`/`ls_remote_head` take `auth_token` (git_service.py:331,364,412), so any future API-tier caller would ship vault git credentials over the internal hop.

**해야 할 것**: If Option B proceeds: add gitd to the isolation test surface (a gitd-reachability probe in test_pg_rbac_e2e.sh asserting an API-tier token cannot reach gitd directly), specify base64 framing for cat_blob and a size cap for vault_log/file_diff/diff, and record an explicit accepted-risk decision for the no-ACL tier in a docs/design item — CLAUDE.md's review checklist requires 'Auth/access control and publication exposure' to be checked, and a new unauthorized-by-vault tier is exactly that.

### Cost and the memory numbers everything is sized from were measured on the wrong platform

**왜 중요한가**: The whole sizing argument (Kiwi ~550MB per warmed child, 4 children ≈ 2.2GB, therefore --workers 4 OOMKills) is explicitly flagged in the evidence as measured on darwin/arm64 CPython 3.11, while backend/Dockerfile:1 is `FROM python:3.14-slim` on linux/amd64. Option A raises `requests.memory` 1Gi→~3Gi (tripling the pod's scheduling footprint on a node whose backend.yaml:116-118 comment already says 'revisit if other tenants land on the same node'), Option B adds a whole second Deployment plus a network hop on every git READ (document_service.py:597 reads on every akb_get — the hottest path), and Option C requires a CephFS RWX storage class plus N× full worktree checkouts on a 20Gi PVC. None of the three states a node-count or $/month delta, and none makes the in-cluster re-measurement a gating step of the phase that depends on it.

**해야 할 것**: Make an in-cluster `kubectl top pod` + cgroup `memory.current` read on linux/amd64 CPython 3.14 a HARD gate at the top of whichever option is chosen — before any requests/limits edit, before any process-count increase. Then attach a one-page cost delta (nodes, PVC class, replica count) to the design item; Option C's CephFS RWX requirement in particular is a storage-class procurement decision, not a code change.

### Option C changes cleanup_vault_dirs' assumption without changing cleanup_vault_dirs, and no option addresses downgrade

**왜 중요한가**: `cleanup_vault_dirs` rmtree's exactly `(self._bare_path(vault_name), self._worktree_path(vault_name))` (git_service.py:307-310). Option C redefines `_worktree_path` to `_worktrees/<vault>__<POD_NAME>` but its change list only mentions making cleanup_vault_dirs rename-then-delete — so after the change, deleting a vault removes the bare plus THIS pod's worktree and permanently orphans every peer's `_worktrees/<vault>__<other-pod>` directory (dangling gitdir pointers, growing on every rollout since k8s mints a new pod name each time). Option C names 'worktree storage multiplies by N and leaks per pod name' as a new failure mode but never fixes the call that would have cleaned it. Separately, no option specifies a DOWNGRADE path: rolling back the image after a partial Option C rollout puts old `_ensure_worktree` (which looks for `_worktrees/<vault>/.git` at git_service.py:140 and does `worktree add <wt> <branch>` at :151) alongside new detached-worktree pods, at which point old code's non-CAS `update_ref("HEAD", sha)` races new code's `update-ref refs/heads/<b> <new> <tip>`.

**해야 할 것**: For Option C: add cleanup_vault_dirs (and a periodic worktree GC keyed on live ReplicaSet pod names) to the change list, not just to the risk list. For all three: write the downgrade procedure as an explicit artifact — which phases are one-way, what the rollback command is, and what state must be manually reconciled — and put the one-way boundary in the phase table. Option C's git-layout change is one-way and is currently presented as if it were reversible.

### None of the three proposals creates the docs/design item that CLAUDE.md's state machine requires

**왜 중요한가**: CLAUDE.md's Default Work Loop step 2 routes 'Architecture, API contracts, storage, indexing, deployment, auth, or cross-component changes' to `docs/design/`, with item folders containing README.md (frontmatter status/stage/updated), rounds/, and feedback/. All three options are squarely that — they change deployment topology, storage layout, the git write contract, and auth-adjacent controls. `ls docs/design/proposal/` shows exactly one item, `command-lane-write-path` (the write_lane design these options all modify), and `ls docs/design/accepted/` shows three unrelated items. `ls docs/prd/wip docs/prd/backlog` is empty. So the option that gets picked would land as code against a documented invariant with no proposal, no critique round, and no PM decision record.

**해야 할 것**: Open `docs/design/proposal/<yyyy-mm-dd-multi-process-topology>/` with README.md carrying the three options, the refutations above, and the open questions (CephFS vs RBD backing for akb-vaultdata, whether remote /mcp is in production use, whether --workers is ever an option); put this critic pass in feedback/ and the option comparison in rounds/. Per CLAUDE.md, the blocking PM decision to surface directly is: is the goal (a) surviving a node, (b) removing deploy outages, or (c) isolating workers from the serving loop — because Option A cannot deliver (a) or (b) at all, and the phases that deliver (c) are common to all three.

## 3. 리포 경계 위반 점검

- Option C contradicts a documented architecture invariant stated in BOTH governance files, without proposing a doc change. AGENTS.md:191-193 states: '**Persistent linked worktree** per vault at `/data/vaults/_worktrees/{vault_name}` (created once via `git worktree add`). Commits go through the worktree — no clone'. CLAUDE.md's Architecture Reminders state: '`GitService` writes go through the persistent worktree and per-vault lock.' Option C's [XL] change deletes `_VAULT_LOCKS`/`_vault_lock` outright (git_service.py:43-53 plus all 8 hold sites) and repaths the worktree to `_worktrees/{vault}__{pod}` created with `--detach`. That may well be the right call, but it must land as a docs/design item that supersedes those two lines, not as a code change against a stated invariant.

- Option A amends the same CLAUDE.md line ('GitService writes go through the persistent worktree and per-vault lock') by redefining the per-vault lock as threading.Lock + fcntl.flock and adding a new on-PVC directory `<storage>/_locks/`. Narrower than Option C (it keeps `_worktrees/{vault}` and the threading.Lock), but it still changes the documented storage layout and needs the same doc amendment.
