# AKB multi-process / multi-replica architecture review

Reviewed at commit `12d8bc06a6b7`. This was a read-only code review; no repository files were changed.

## Executive conclusion

AKB’s singleton deployment is a correctness boundary, not merely a conservative capacity setting. Changing either of these today is unsafe:

- Adding `--workers N` to [`backend/Dockerfile:17`](/Users/kwoo2/Desktop/storage/akb/backend/Dockerfile:17).
- Raising `replicas` above 1 in [`deploy/k8s/backend.yaml:78-86`](/Users/kwoo2/Desktop/storage/akb/deploy/k8s/backend.yaml:78).

The two highest-impact blockers are:

1. Every process directly mutates the same per-vault Git worktree and branch using process-local locks. Concurrent different-path writes can lose a commit or make PostgreSQL point at a commit no longer reachable from the vault branch.
2. MCP Streamable HTTP transports and server tasks are held in process-local dictionaries. A session request routed to a different process has no usable transport state.

Other non-negotiable work includes distributed publication throttling, audit-chain redesign, startup migration serialization, process-role separation, and per-replica resource sizing.

I recommend architecture B: stateless API/MCP replicas plus a single explicit Git-command/worker tier that owns the RWO volume. This makes the singleton an isolated storage-owner boundary instead of forcing the entire serving application to be singleton. It preserves the required architecture: backend business logic remains in the backend, PostgreSQL and Git remain sources of truth, and vector stores remain derived indexes, as required by [`CLAUDE.md:62-70`](/Users/kwoo2/Desktop/storage/akb/CLAUDE.md:62).

## 1.2 Category (a): duplication breaks correctness or security

Ordered by severity.

### P0 — Shared Git worktrees and branch refs are not cross-process safe

Each vault uses:

- Bare repo: `/data/vaults/{vault}.git`
- Linked worktree: `/data/vaults/_worktrees/{vault}`

The worktree shares objects and refs with the bare repo. [`backend/app/services/git_service.py:1-19`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:1), [`backend/app/services/git_service.py:69-80`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:69)

All mutation serialization is through module-global `threading.Lock` objects, so it protects threads only inside one Python process. [`backend/app/services/git_service.py:39-53`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:39)

A normal commit is a multi-command transaction:

1. `reset --hard HEAD`
2. Write the file
3. `git add`
4. `write-tree`
5. Build a commit with parent `HEAD`
6. `update-ref HEAD <new>` without an expected old OID

[`backend/app/services/git_service.py:97-129`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:97), [`backend/app/services/git_service.py:563-602`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:563)

The PostgreSQL advisory lock is only on `(vault_id, path)`, not the vault branch. It therefore serializes concurrent changes to the same path but permits different paths in the same vault to run concurrently across processes. [`backend/app/repositories/document_repo.py:15-36`](/Users/kwoo2/Desktop/storage/akb/backend/app/repositories/document_repo.py:15), [`backend/app/services/document_service.py:313-343`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:313)

Failure modes:

- `index.lock`/ref-lock errors and request failure.
- One process’s `reset --hard` erasing another process’s uncommitted worktree changes.
- Sibling commits created from the same parent, followed by last-writer-wins `update-ref`.
- PostgreSQL transaction A committing `documents.current_commit=A` while vault HEAD is later replaced by sibling B.
- A commit remaining in the object database but becoming unreachable from the branch: silent PG/Git source-of-truth divergence and apparent lost update.

Git supports compare-and-swap ref updates when the old OID is provided; AKB omits that argument. [Git `update-ref` documentation](https://git-scm.com/docs/git-update-ref).

This blocks both multiple processes in one pod and multiple pods sharing RWX storage.

### P0 — MCP sessions are process-local

MCP transports, server tasks, and session users are stored in three module dictionaries. [`backend/mcp_server/http_app.py:51-55`](/Users/kwoo2/Desktop/storage/akb/backend/mcp_server/http_app.py:51)

Each transport owns a live server loop task. [`backend/mcp_server/http_app.py:63-82`](/Users/kwoo2/Desktop/storage/akb/backend/mcp_server/http_app.py:63)

For a POST whose session ID is unknown locally, the server creates a new transport instead of locating the original one. GET returns 404 for a non-local session. [`backend/mcp_server/http_app.py:125-165`](/Users/kwoo2/Desktop/storage/akb/backend/mcp_server/http_app.py:125)

The Kubernetes Service and Ingress have no session-affinity configuration; `/mcp` goes to the ordinary backend Service. [`deploy/k8s/backend.yaml:179-189`](/Users/kwoo2/Desktop/storage/akb/deploy/k8s/backend.yaml:179), [`deploy/k8s/ingress.yaml:24-39`](/Users/kwoo2/Desktop/storage/akb/deploy/k8s/ingress.yaml:24)

The stdio proxy retains a session ID and retries session/404/connection failures by creating a new session and replaying the original call. [`packages/akb-mcp-client/lib/proxy.mjs:679-717`](/Users/kwoo2/Desktop/storage/akb/packages/akb-mcp-client/lib/proxy.mjs:679), [`packages/akb-mcp-client/lib/proxy.mjs:722-759`](/Users/kwoo2/Desktop/storage/akb/packages/akb-mcp-client/lib/proxy.mjs:722)

Its keep-alive connection reduces worker changes in some direct deployments, but it cannot guarantee affinity through reconnects, rollouts, ingress upstream pools, or pod changes. [`packages/akb-mcp-client/lib/proxy.mjs:20-27`](/Users/kwoo2/Desktop/storage/akb/packages/akb-mcp-client/lib/proxy.mjs:20)

Failure modes:

- Intermittent invalid-session/protocol errors.
- Reinitialization storms during rollout.
- Mutating tool replay after an ambiguous connection failure. I found no backend request-id deduplication around MCP dispatch, so exactly-once mutation cannot be assumed.

The pinned MCP SDK has a stateless session-manager mode, but AKB is not using it. [`backend/pyproject.toml:18-24`](/Users/kwoo2/Desktop/storage/akb/backend/pyproject.toml:18)

### P0 — Same-name vault creation can delete another process’s successful repo

AKB explicitly documents why `_CREATE_LOCKS` must cover both creation and rollback: without serialization, loser B can see a directory created by winner A and delete A’s repository during compensation. The lock is an `asyncio.Lock` stored in a module dictionary. [`backend/app/services/document_service.py:146-161`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:146), [`backend/app/services/document_service.py:1695-1728`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:1695)

Creation performs filesystem initialization and the first commit before inserting the vault row into PostgreSQL. [`backend/app/services/document_service.py:1734-1753`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:1734)

Rollback ownership is sound only because the process-local creation lock excludes concurrent same-name creates. [`backend/app/services/document_service.py:1864-1879`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:1864)

Failure mode: destructive deletion of a winning vault’s bare repo/worktree, leaving a live PostgreSQL vault whose Git source is gone.

### P0 — Vault deletion/rollback can race another process’s writer or poller

Vault deletion commits the PostgreSQL cascade first and then removes the bare repo and linked worktree. [`backend/app/services/access_service.py:1569-1629`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/access_service.py:1569)

`cleanup_vault_dirs()` relies exclusively on the process-local `_vault_lock` before recursively deleting both paths. [`backend/app/services/git_service.py:277-310`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:277)

Failure modes:

- Another process writes or fetches while the repo is being removed.
- A same-named recreation observes partial leftover state.
- A PostgreSQL row can survive while its Git data has been removed, or vice versa, depending on which process fails.

### P1 — Publication password throttling is explicitly single-process

The limiter states that its module dictionaries are authoritative because the backend is one process. [`backend/app/services/publication_rate_limit.py:1-19`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/publication_rate_limit.py:1)

The counters are `_by_ip` and `_by_slug` dictionaries. [`backend/app/services/publication_rate_limit.py:26-41`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/publication_rate_limit.py:26)

The public authentication route reserves against those counters before bcrypt verification. [`backend/app/api/routes/public.py:433-485`](/Users/kwoo2/Desktop/storage/akb/backend/app/api/routes/public.py:433)

Failure mode: with N workers, the effective allowance becomes approximately N times larger, and requests can bypass a lockout by reaching a different worker. With multiple pods, load-balancer hopping makes that easier. This is a security-control failure, not just stale cache behavior.

### P1 — Audit hash-chain integrity breaks across processes

When enabled, each process has its own sequence, previous hash, lock, bounded queue, dropped count, and writer thread. [`backend/app/services/audit_log.py:80-98`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/audit_log.py:80)

Every process appends to the same date-derived filename when sharing a log directory. [`backend/app/services/audit_log.py:105-135`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/audit_log.py:105)

Each process independently reseeds its local chain and then appends using only its own thread lock. [`backend/app/services/audit_log.py:157-205`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/audit_log.py:157), [`backend/app/services/audit_log.py:254-304`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/audit_log.py:254)

Failure modes:

- Shared directory: duplicate sequence numbers and forked `prev` hashes interleaved in one file, causing verification failure.
- Separate pod-local directories: fragmented chains and lost lines on restart.
- Separate files with the same name: uploaders target the same `audit/{day}/{filename}` S3 key and can overwrite/race. [`backend/app/services/audit_log.py:370-379`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/audit_log.py:370), [`backend/app/services/audit_log.py:421-440`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/audit_log.py:421)
- Multiple uploaders race marker creation, upload, and pruning without a PostgreSQL or filesystem lock. [`backend/app/services/audit_log.py:459-495`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/audit_log.py:459)

Audit is disabled by default, and the base backend manifest does not mount the documented `/data/audit` PVC. [`backend/app/config.py:26-51`](/Users/kwoo2/Desktop/storage/akb/backend/app/config.py:26), [`deploy/k8s/backend.yaml:101-111`](/Users/kwoo2/Desktop/storage/akb/deploy/k8s/backend.yaml:101) Private overlays may differ; I could not verify them.

### P1 — Startup migrations are not globally serialized

Every process runs `init_db()` before serving. [`backend/app/db/postgres.py:80-97`](/Users/kwoo2/Desktop/storage/akb/backend/app/db/postgres.py:80)

Migration application:

1. Reads the entire applied ledger into a local set.
2. Runs every locally missing migration.
3. Inserts the ledger row only after the migration function returns.

There is no migration-wide advisory lock or atomic claim. [`backend/app/db/postgres.py:123-174`](/Users/kwoo2/Desktop/storage/akb/backend/app/db/postgres.py:123), [`backend/app/db/postgres.py:219-224`](/Users/kwoo2/Desktop/storage/akb/backend/app/db/postgres.py:219)

Many migrations use idempotent DDL, but not every check-then-DDL sequence is concurrency-proof. Migration 045 checks `pg_constraint` and then adds a constraint; two starters can both pass the check before one receives a duplicate-object error. [`backend/app/db/migrations/045_vault_write_grant_actions.py:32-60`](/Users/kwoo2/Desktop/storage/akb/backend/app/db/migrations/045_vault_write_grant_actions.py:32)

Failure mode: one or more workers fail startup or repeatedly contend on DDL. I did not find evidence of schema corruption in current migrations, but startup success under simultaneous cold starts is not guaranteed.

### P1 — The write lane’s global and per-vault limits are local

The per-vault admission gate, global semaphore, waiter counters, and commit pool are all module state. [`backend/app/services/write_lane.py:64-109`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/write_lane.py:64)

The intended invariant is one writer per vault and eight globally, before taking a PostgreSQL connection. [`backend/app/services/write_lane.py:112-159`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/write_lane.py:112), [`backend/app/config.py:486-512`](/Users/kwoo2/Desktop/storage/akb/backend/app/config.py:486)

With N processes:

- Per-vault Git concurrency becomes N.
- The global cap becomes `N × write_lane_concurrency`.
- The waiter backstop becomes `N × write_lane_max_waiters`.
- Each process creates its own commit thread pool. [`backend/app/services/write_lane.py:161-185`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/write_lane.py:161)

The correctness aspect is covered by the Git finding above. Independently, admission control ceases to protect the shared PostgreSQL and storage system from aggregate overload.

### P1 — RWO prevents ordinary multi-node replicas

The base PVC requests RWO and provides no `storageClassName`, so the actual storage implementation cannot be identified from this repository. [`deploy/k8s/backend.yaml:167-176`](/Users/kwoo2/Desktop/storage/akb/deploy/k8s/backend.yaml:167)

Kubernetes RWO means one node, not one pod; multiple pods on the same node may mount it. It does not guarantee co-scheduling, however, and a second pod on another node may remain Pending or fail attachment. [Kubernetes Persistent Volume access modes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes).

The manifest’s own comment records an AWS Multi-Attach rollout failure and explains why `Recreate` is required. [`deploy/k8s/backend.yaml:79-86`](/Users/kwoo2/Desktop/storage/akb/deploy/k8s/backend.yaml:79)

Failure mode: unavailable replicas or rollout downtime before any application-level concurrency is reached.

### P2 — External Git’s claim is a time lease, not full-duration exclusion

The poller claims one vault with `FOR UPDATE SKIP LOCKED`, then commits the claim and sets `next_attempt_at` one hour forward. [`backend/app/services/external_git_poller.py:32-59`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/external_git_poller.py:32), [`backend/app/config.py:105-114`](/Users/kwoo2/Desktop/storage/akb/backend/app/config.py:105)

If reconciliation exceeds one hour, another worker may claim the same vault. The Git fetch path uses a fixed temporary ref and only a process-local lock around the final ref update. [`backend/app/services/git_service.py:364-410`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:364)

Failure mode: duplicate indexing and concurrent clone/fetch/cleanup against one repo. This is conditional; I did not verify a current production reconcile exceeding one hour.

### P2 — Non-pgvector collection creation is not proven cross-process safe

- Seahorse Cloud: check-then-create with no distributed guard.

### P2 — Stale Git lock cleanup’s safety proof becomes invalid

Startup deletes `index.lock` files older than 60 seconds. Its concurrency argument assumes all writers share `_vault_lock` and startup cannot overlap a live writer. [`backend/app/services/git_service.py:206-275`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:206)

Multiple processes violate both assumptions because each has a different `_vault_lock` and starts its own cleanup. [`backend/app/services/lifecycle.py:70-83`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/lifecycle.py:70)

Failure mode: an active lock older than the threshold can be removed underneath Git. I did not establish that the normal write path holds `index.lock` longer than 60 seconds—individual write commands are configured for a 30-second timeout—so this is a real safety gap but not a demonstrated current incident. [`backend/app/config.py:508-512`](/Users/kwoo2/Desktop/storage/akb/backend/app/config.py:508)

# 4. Storage constraint

## Required layout

For every vault, AKB requires one bare repo and one persistent linked worktree:

```text
/data/vaults/
├── {vault}.git/
└── _worktrees/
    └── {vault}/
        └── .git   # linked-worktree pointer into the bare repo
```

The layout and direct ref sharing are defined in [`backend/app/services/git_service.py:1-19`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:1) and [`backend/app/services/git_service.py:69-80`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/git_service.py:69). Git linked worktrees have their own index/HEAD metadata but share normal refs and the object store. [Git worktree documentation](https://git-scm.com/docs/git-worktree.html).

The linked-worktree administrative metadata records a path back to the worktree. Mounting the volume at the same `/data/vaults` path in every pod is therefore important. [Git repository-layout documentation](https://git-scm.com/docs/gitrepository-layout).

## Can two processes on the same node share it?

**Not with the current code.**

They physically can see the same RWO-mounted files, but `_VAULT_LOCKS` and the write lane are process-local. The current PostgreSQL lock is path-grained while the Git branch and worktree are vault-grained.

It can be made safe only if one exclusive, cross-process vault lock covers the complete compound operation:

```text
reset → filesystem changes → index changes → commit object → ref CAS
```

It must also cover:

- Vault init and first commit.
- Clone/reclone.
- Fetch temporary-ref handling and canonical-ref update.
- Worktree add/prune.
- Bulk deletion and moves.
- Vault cleanup and rollback.
- Stale-lock cleanup.

A POSIX `flock` could coordinate same-node processes if the underlying filesystem implements it correctly and every mutation honors the same lock file. There is no `flock`/`fcntl` use in the repository. More importantly, Git’s `git worktree lock` is not that mutex: it prevents administrative pruning/moving of a worktree; it does not serialize ordinary writers. [Git worktree documentation](https://git-scm.com/docs/git-worktree.html).

A PostgreSQL advisory lock keyed by vault ID/name is more portable and works across nodes. It must use a dedicated or carefully managed connection, have one documented lock order, and release correctly on cancellation/process death. Git ref compare-and-swap should remain as a second line of defense, not as a replacement for the worktree mutex.

## Can two pods share it through RWX?

Physically, yes—if an RWX-capable storage class is provisioned and both pods mount it at the same path. The repository does not specify such a class, so I cannot verify:

- Whether the production filesystem supports correct cross-client file locking.
- Cache-coherency behavior for ref/index files.
- Atomic rename guarantees.
- Git latency and failure behavior on that filesystem.

RWX alone does not make AKB safe. The first likely failure is one of:

1. Two processes pass their local write gates.
2. Both operate on the same index/worktree.
3. One gets an `index.lock` failure, or one reset overwrites the other’s work.
4. If individual Git lockfiles happen to serialize commands, the higher-level multi-command transaction still races.
5. Both create sibling commits and the non-CAS ref update loses one.

A distributed PostgreSQL vault lock avoids relying on provider-specific network-filesystem locking. RWX would solve volume attachment, not concurrency correctness.

## Interaction with RWO and `Recreate`

- Multiple Uvicorn workers in one pod can share the current RWO volume physically.
- Multiple pods may share it only when co-located on the same node; RWO does not require Kubernetes to co-locate them. [Kubernetes RWO semantics](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes).
- `Recreate` deliberately prevents old/new pod overlap but causes rollout downtime. [`deploy/k8s/backend.yaml:79-86`](/Users/kwoo2/Desktop/storage/akb/deploy/k8s/backend.yaml:79)
- Switching to `RollingUpdate` without first separating the volume owner or adding distributed locking reintroduces simultaneous writers.

# 5. Migration options

## A. Multiple Uvicorn workers in one pod

**Shape:** `uvicorn --workers N`, one pod, one node, one RWO volume.

**Required code changes**

- Replace/customize the MCP transport with stateless handling or another process-independent model.
- Add vault-wide distributed locking around every Git mutation and CAS ref updates.
- Serialize migrations.
- Move publication throttling to PG/Redis.
- Redesign audit production.
- Decide whether only one worker runs background tasks or allow the coordinated workers to duplicate.
- Scale per-process PG pools, tokenizer children, and thread pools down.

**Smallest first step**

Add the cross-process Git lock/CAS and multi-process invariant tests while keeping `--workers=1`. Then switch MCP to stateless mode. Only after both pass should the image be tested with two workers.

**New failure modes**

- N× pool connections, tokenizer children, caches, and threads.
- One pod/node/volume remains a single failure domain.
- Per-process event-loop failure can be hidden by another process answering pod probes.
- A missed Git mutation path becomes a rare data-loss race.
- No pod-level rolling availability because the RWO volume and `Recreate` strategy remain.

**Assessment**

Useful as a capacity stopgap, not a high-availability architecture.

## B. Stateless API replicas plus a single Git-command/worker tier

**Shape:** N API/MCP replicas with no vault PVC; one command/worker replica mounts `/data/vaults`.

**Required code changes**

- Implement a real process-role model and actual worker entrypoint; the lifecycle’s claimed `worker_main` does not exist. [`backend/app/services/lifecycle.py:1-5`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/lifecycle.py:1)
- Keep the tokenizer pool in every serving API process because query-time BM25 uses it. [`backend/app/services/sparse_encoder.py:273-279`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/sparse_encoder.py:273)
- Introduce an authenticated internal backend command interface for complete Git-dependent use cases—not local filesystem work in the Node proxy.
- Route all Git reads as well as writes through the owner. `DocumentService.get()` reads the body from Git at the PG row’s recorded commit, so simply unmounting the PVC from API pods would break reads. [`backend/app/services/document_service.py:577-603`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:577)
- Keep the whole current Git-before-PG use case in the command tier rather than splitting the transaction across an API process and a Git micro-call. Current creation commits Git before inserting the document row. [`backend/app/services/document_service.py:489-523`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:489)
- Run external-Git filesystem operations in the owner tier or through the same command interface.
- Pure PG/vector outbox workers can be moved to a separate scalable worker Deployment later.
- Make MCP stateless so its request handling can live on the API tier.

**Smallest first step**

Add an explicit role setting such as `all | api | worker`, defaulting to current `all`, and implement `app.worker_main`. This can ship without changing deployment behavior.

**New failure modes**

- The Git-command tier becomes an explicit read/write availability bottleneck.
- Internal RPC timeout, authentication, cancellation, and version-skew risks.
- Missing one Git-dependent endpoint from the command boundary can cause production-only filesystem failures.
- If API holds a PG transaction while waiting for command RPC, failure recovery becomes worse; complete business commands should execute in the command tier.

**RWO/strategy interaction**

- API Deployment: no PVC, `replicas > 1`, `RollingUpdate`.
- Git-command/worker Deployment: one replica, current RWO PVC, `Recreate`.
- API/auth/search/table availability can survive an API pod rollout; Git-dependent operations still depend on the storage owner.

## C. RWX shared filesystem plus distributed locking, N symmetric replicas

**Shape:** every replica mounts the same RWX Git tree and runs the same application.

**Required code changes**

Everything required by option A, plus:

- Provision and migrate to an RWX storage class.
- Distributed vault lock around all Git lifecycle and mutation operations.
- Unique fetch temp refs or full fetch locking.
- Ref CAS.
- Distributed publication limiter and audit sink.
- Migration serialization.
- Stateless MCP.
- Per-replica worker and pool sizing.

**Smallest first step**

Implement and stress-test the PostgreSQL vault lock on the existing single-node/RWO system. Do not change the volume class first.

**New failure modes**

- Network-filesystem latency in the synchronous Git write path.
- Filesystem cache/locking semantics that differ by provider.
- Lock convoys during large vault operations.
- Split-brain if any mutation bypasses the distributed lock.
- N copies of every background subsystem unless worker roles are also separated.

**RWO/strategy interaction**

The existing PVC must be replaced or migrated; access mode is not a harmless Deployment edit. Once RWX and cross-pod correctness are established, `RollingUpdate` becomes possible.

**Assessment**

Operationally the riskiest option. It makes a filesystem’s distributed semantics part of the database correctness model.

## D. Durable PostgreSQL command queue followed by a Git committer

**Shape:** API transaction writes a durable, ordered per-vault command; a committer owns Git and finalizes the command.

**Required code changes**

- Add a PG command table with idempotency key, vault sequence, payload/blob reference, state, result commit, retry fields, and dead-letter state.
- One active consumer per vault, using `SKIP LOCKED` plus strict per-vault order.
- Define `pending`, `Git committed`, and `PG finalized` states explicitly.
- Make retries idempotent and reconcile Git commits that succeeded before process death.
- Initially preserve the synchronous API contract by waiting for command completion; asynchronous `202 Accepted` can be a later contract.
- Keep Git as source of truth for committed content. PG is the durable command/control plane; vectors remain derived.
- Git reads still require a Git-owner service or separately managed read replicas.

**Smallest first step**

Write shadow command records for current synchronous mutations without changing execution or responses. Compare the recorded order/results against actual Git commits before enabling consumption.

**New failure modes**

- Queue backlog and write latency during committer outage.
- Poison commands blocking a vault if ordering is strict.
- Duplicate execution unless idempotency is complete.
- New eventual-consistency states.
- Unbounded command retention unless GC is designed.
- More complex recovery when Git succeeds but PG finalization fails.

**RWO/strategy interaction**

Only the committer needs the current RWO volume. API pods can roll independently. Multiple committers still require volume sharding, RWX, or an external Git storage service.

**Assessment**

Best long-term write-path architecture, but substantially larger than the immediate replica fix.

# 6. Recommendation

Choose **B: stateless API/MCP replicas plus a single explicit Git-command/worker tier**.

```text
                       ┌──────────────────────────┐
Ingress ──────────────►│ API / stateless MCP, N  │
                       │ no /data/vaults mount    │
                       └───────┬─────────┬────────┘
                               │         │
                               │         └────────► PostgreSQL / derived vectors
                               │
                               ▼
                       ┌──────────────────────────┐
                       │ Git-command/worker, 1    │
                       │ owns complete Git-backed │
                       │ business commands        │
                       └────────────┬─────────────┘
                                    ▼
                         RWO /data/vaults PVC
```

Why:

- It preserves the current persistent-worktree design instead of betting correctness on RWX filesystem behavior.
- It localizes the true singleton—the physical Git workspace—without forcing auth, SQL, search, tables, and ordinary API capacity to be singleton.
- It keeps backend business logic in the backend and does not move server-side Git behavior into the Node proxy. [`CLAUDE.md:64-68`](/Users/kwoo2/Desktop/storage/akb/CLAUDE.md:64)
- It keeps PostgreSQL plus Git as the source-of-truth pair and leaves pgvector/Qdrant/Seahorse as rebuildable indexes. [`CLAUDE.md:68-70`](/Users/kwoo2/Desktop/storage/akb/CLAUDE.md:68)
- It is compatible with a later move to D: the internal command interface becomes the natural insertion point for a durable queue.

The limitation must be explicit: B gives scalable/rolling API availability, but the Git-command tier remains a single point for document body/history and mutation availability. If the actual requirement is zero Git-write downtime, B is an intermediate architecture and D is the eventual target.

# 7. Five sharpest migration risks

1. **An unwrapped Git mutation path.** One missed call to init, fetch, cleanup, bulk delete, or ref update defeats the distributed lock and can cause rare lost commits or repo deletion. Git mutations are currently spread across document, collection, access, and external-Git services. [`backend/app/services/document_service.py:489-496`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:489), [`backend/app/services/collection_service.py:402-437`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/collection_service.py:402), [`backend/app/services/access_service.py:1610-1629`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/access_service.py:1610), [`backend/app/services/external_git_service.py:123-138`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/external_git_service.py:123)

2. **MCP retries turning an availability fault into a duplicate mutation.** The proxy reconnects and retries the original request on session/404/connection errors. [`packages/akb-mcp-client/lib/proxy.mjs:679-717`](/Users/kwoo2/Desktop/storage/akb/packages/akb-mcp-client/lib/proxy.mjs:679) Stateless transport must be paired with mutation idempotency or a clear at-least-once contract.

3. **Distributed-lock deadlock or pool exhaustion.** Current document writes already hold one PG transaction/connection while waiting for Git. [`backend/app/services/document_service.py:313-343`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/document_service.py:313) Adding a session lock, path lock, lifecycle lock, and long external clone without one lock order or a separate small control pool can make the migration less available than the singleton.

4. **Multiplying resources before resizing them.** Defaults are 30 PG connections, 2–4 Kiwi child processes, and up to eight commit threads per API process. [`backend/app/config.py:85-92`](/Users/kwoo2/Desktop/storage/akb/backend/app/config.py:85), [`backend/app/services/sparse_encoder.py:273-290`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/sparse_encoder.py:273), [`backend/app/services/write_lane.py:161-170`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/write_lane.py:161) Under the current 4 GiB pod limit, adding workers before budgeting these can produce OOM/restart flapping. [`deploy/k8s/backend.yaml:112-120`](/Users/kwoo2/Desktop/storage/akb/deploy/k8s/backend.yaml:112)

5. **Treating storage or “safe worker claims” as stronger than they are.** RWO is not a mutex, RWX is not a distributed transaction, and worker leases are at-least-once rather than exactly-once. Events have an explicit Redis/PG crash gap, while external Git can be reclaimed after one hour. [`backend/app/services/events_publisher.py:177-227`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/events_publisher.py:177), [`backend/app/services/external_git_poller.py:32-59`](/Users/kwoo2/Desktop/storage/akb/backend/app/services/external_git_poller.py:32)
