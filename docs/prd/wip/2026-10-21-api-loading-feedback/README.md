## 1. 결론

문제는 로딩 컴포넌트가 없다는 데 있지 않다. `LoadingState`, `InlineLoadingState`, `Skeleton`, 버튼의 loading 처리와 다수 페이지의 초기 스켈레톤은 이미 구현되어 있다. 반면 **최초 조회와 재조회, 아직 모르는 값과 실제 빈 값, 저장 완료와 후속 조회 실패를 구분하는 방식이 페이지마다 다르다.**

사용자가 체감할 주요 문제는 다음과 같다.

1. Vault Overview는 초기 요청 중 실질적인 본문 구조가 숨겨진다.
2. 문서 관계·그래프 개수·Vault 템플릿은 조회 전에도 빈 값처럼 보일 수 있다.
3. 검색·홈 집계·일부 목록은 일시적인 재조회 실패로 이미 보던 내용을 잃는다.
4. Members·설정 목록은 재시도/재조회가 진행 중인지 불분명하고, 일부는 응답 역전 가능성도 있다.
5. 부가 정보 요청이 핵심 목록의 표시를 지연시키거나 파일 미리보기를 통째로 교체한다.

기존 [디자인 시스템의 Loading-state contract](../../../../frontend/DESIGN_SYSTEM.md#loading-state-contract)를 실제 페이지의 상태 전이에 적용하는 작업이 우선이다. 전면적인 데이터 계층 교체나 새로운 전역 스피너 도입은 필요하지 않다.

## 3. 구체적인 개선 항목

우선순위: **P1** 사용자 흐름 단절 또는 잘못된 리소스/상태 표시, **P2** 복구·연속성·부분 로딩 개선, **P3** 표현 및 일관성 개선. 아래 줄 번호는 분석 커밋 기준이다. ‘코드 확인’과 로컬 재현 여부는 검증 기록에서 구분한다.

### A01 · P1 · Vault Overview의 초기 본문 구조 유지

- 근거: `frontend/src/pages/vault.tsx:375–377,501`. `/info` 완료 전 안내 문구만 보이고 Overview가 숨겨진 `Activity` 안에 있다. 내부에 있는 스켈레톤도 함께 숨겨진다.
- 제안: 접근이 검증된 셸 안에서 제목·패널 외곽·행 높이를 가진 `OverviewSkeleton`을 직접 표시한다. 미검증 데이터나 편집 액션까지 먼저 노출하지 않는다. `/info`, 최근 항목, 활동의 로딩을 패널별로 분리한다.
- 완료 조건: `/info`를 2초 지연시켜도 주요 패널 자리가 유지되고, 실제 수치 대신 스켈레톤이 보인다. 계정/권한 변경 시 이전 Vault 내용은 노출하지 않는다.

### A02 · P1 · 문서 Relations의 ‘미조회’를 ‘관계 없음’과 구분

- 근거: `pages/document.tsx:712–723,2022–2029`, `components/relations/relations-panel.tsx:76–90` (`frontend/src/` 기준). 조회 기본값 `[]`와 pending 전달 누락으로 완료 전 0/No relations yet 표시가 가능하다. 오류 영역에 Retry가 없다.
- 제안: 패널에 최초 로딩, 갱신, 오류, 재시도 콜백을 전달한다. 최초에는 관계 행 스켈레톤 3개와 알 수 없는 개수 표시, 성공한 빈 응답일 때만 빈 상태를 표시한다. 재조회는 기존 관계를 유지한다.
- 완료 조건: 2초 후 관계가 반환되는 동안 0/빈 상태가 나타나지 않는다. 최초 500은 Retry로 복구되고, 갱신 500은 기존 관계를 보존한다.

### A03 · P2 · 그래프 개수와 Vault 템플릿의 미확정 상태 분리

- 근거: `pages/graph.tsx:164,212`는 초기/초기 오류에도 0 resources·0 relationships 표시 가능. `components/vault-create-form.tsx:40–52,179–192`는 템플릿 초기값/실패를 빈 배열로 처리하고 None — empty vault 선택을 활성화한다.
- 제안: 그래프 개수는 최초 성공 전 스켈레톤 또는 ‘확인 중’으로 표시한다. 템플릿 필드는 조회 중 안내, 실패+Retry, 성공한 선택 목록을 구분한다. 선택 사항인 템플릿 조회 때문에 사용자가 명시적으로 선택한 ‘빈 Vault 생성’까지 차단하지 않는다.
- 완료 조건: 초기 지연/500을 실제 데이터 0개나 사용 가능한 템플릿 없음으로 오인하지 않는다. 성공한 빈 응답은 정상 빈 상태로 표시한다.

### A04 · P1 검색 / P2 홈 · 재조회 실패에도 직전 성공 데이터 유지

- 근거: `pages/search.tsx:306–316,334–341`은 재조회 실패 시 결과·개수를 비운다. `components/home-workspace-summary.tsx:23–45,63–74`는 `query.isSuccess` 조건 때문에 백그라운드 오류 시 캐시가 있어도 수치를 숨긴다.
- 제안: 동일한 권한·검색 조건에서 마지막 성공 스냅샷을 유지하고 ‘업데이트 실패 — 이전 결과 표시’와 Retry를 인접 배치한다. 홈의 주기적 성공 갱신은 매번 라이브 안내하지 않는다. 검색 조건을 바꾼 경우 이전 결과의 **실제 적용 조건**을 표시하며 새로운 조건의 결과인 것처럼 보여주지 않는다.
- 완료 조건: 성공 → 재조회 503에서 행·개수·스크롤 유지, busy 종료, Retry 성공 시 교체. 401/403/계정 전환은 별도의 접근 정책에 따라 보호 데이터를 제거한다.

### A05 · P2 · Overview 패널과 Global Search의 재조회 연속성

- 근거: `pages/vault.tsx:281–315,455–459,596–609,750–763`은 가져오기 후 목록을 스켈레톤/오류로 교체하고 활동 오류 때 이전 배열을 비운다. `components/global-search-dialog.tsx:162,252–278,679–706`은 요청마다 결과를 비우고 로딩/오류에도 결과를 숨긴다.
- 제안: 최초 조회와 동일 범위 갱신을 분리한다. Overview는 패널별 기존 행+작은 갱신 상태+인라인 오류를 사용한다. Global Search는 새 검색어 초기화와 기존 결과의 소스 필터 변경을 구분하고, 유지한 결과의 조건을 명시한다. 오래된 결과를 새 소스의 결과처럼 키보드로 선택하게 만들지 않는다.
- 완료 조건: 가져오기 후 지연/실패가 다른 패널을 지우지 않는다. 검색 필터 연속 변경 및 응답 역전에도 최신 조건만 적용되고 키보드 선택 인덱스가 안전하게 초기화된다.

### A06 · P1 · 공개 문서의 요청 대상 변경 보호와 재시도

- 근거: `pages/public-publication.tsx:32–62`의 비동기 완료 상태 갱신에 요청 세대/정리 보호가 없다. `:300–347`의 일시 조회 오류는 Back to AKB만 제공한다.
- 제안: slug 및 관련 조회 조건별 요청 ID 또는 취소 신호를 적용하여 A 요청이 B 화면을 덮어쓰지 못하게 한다. 일시 통신 오류에 명시적인 Retry를 제공하고 404·만료·조회 제한·비밀번호 오류를 별도 안내한다.
- 주의: `lib/api.ts:2606–2610` 공개 문서 열기는 조회 횟수·grant/session 의미가 있으므로 일반 GET처럼 무조건 자동 반복하지 않는다. 실제 요청 의미에 맞는 명시적 재시도를 설계한다.
- 완료 조건: A 느림 → B 빠름 → A 완료 순서에서도 B의 본문/오류/비밀번호 상태가 유지된다.

### A07 · P1 · Members 재조회와 권한 조회 상태 명시

- 근거: `pages/vault-members.tsx:150–167,192–203,303,391–407`. 재조회 시작 피드백이 없고 오류 Retry가 반복 활성화된다. 실패 시 기존 정보·목록을 비우며 권한 조회 실패는 `null`로 흡수한다.
- 제안: 최초/재조회 상태를 분리하고 Retry 진행 표시·중복 실행 방지를 추가한다. 일반 조회 실패는 기존 명단과 인라인 오류를 유지한다. 권한 조회 실패는 ‘권한 확인 불가’로 표시하고 쓰기 액션을 안전하게 제한한다. 실제 reader 권한과 통신 실패를 같은 상태로 취급하지 않는다.
- 완료 조건: 변경 성공 후 명단 조회 실패를 ‘변경 실패’로 표현하지 않는다. 권한 503은 원인과 Retry를 제공하고, 실제 403은 보호 데이터를 유지하지 않는다.

### A08 · P2 · 설정의 삭제 완료와 목록 동기화 분리

- 근거: `pages/settings/settings-dialog.tsx:87–101`은 재조회 pending과 요청별 최신 응답 보호가 부족하다. `tokens-section.tsx:50–68`, `admin-section.tsx:87–96,143–180`은 삭제 후 목록 갱신을 기다리지 않고 작업 busy를 끝낸다.
- 제안: 토큰/사용자 리소스별 요청 세대 또는 Query 키를 사용한다. 삭제 성공 시 해당 행을 제거/완료 상태로 전환하고 목록 갱신 중 상태를 표시한다. 후속 조회 실패는 ‘삭제 완료, 목록 갱신 실패’로 알린다. Query 전환은 선택 사항이며 작은 수정으로도 해결 가능하다.
- 완료 조건: 느린 구 응답이 새 목록을 되돌리지 않는다. 삭제한 토큰이 설명 없이 활성 상태로 남지 않고, 조회 실패 때문에 삭제 명령을 다시 실행하도록 유도하지 않는다.

### A09 · P2 · Publications의 제목 보완 요청을 목록 표시에서 분리

- 근거: `pages/publications.tsx:140–175`. 제목이 없는 항목의 `getDocument` 요청을 `Promise.all`로 모두 기다린 후 목록을 설정하며 실패 때 이전 목록을 제거한다.
- 제안: 기본 목록을 먼저 표시하고 누락된 제목만 행 단위로 조회한다. 제목 영역은 스켈레톤/안전한 문서 식별자로 대체하고 오류도 그 행에 한정한다. 본 목록 재조회 실패는 기존 행+Retry로 처리한다.
- 완료 조건: 제목 요청 하나가 10초 지연되어도 나머지 목록과 정상 항목 액션을 사용할 수 있다.

### A10 · P2 · 문서 읽기·히스토리 오류의 지역 복구

- 근거: `pages/document.tsx:540–560,1440–1453,2033–2065`. 최초 읽기 오류에 직접 Retry가 없고, 본문 재조회 피드백이 부족하다. 히스토리는 캐시가 있어도 오류가 전체 내용을 대체한다.
- 제안: 최초 읽기 오류는 문서 셸 내 Alert+Retry, 재조회 오류는 기존 본문·스크롤·초안을 유지하는 인라인 상태로 표시한다. 히스토리도 기존 버전 목록을 유지하고 재시도 버튼에 진행 상태를 연결한다.
- 완료 조건: 최초 실패에서 뒤로 이동하지 않고 복구 가능. 편집 중 재조회 실패가 초안/커서/스크롤을 초기화하지 않는다. 권한 상실 예외는 유지한다.

### A11 · P2 · 파일 URL 갱신과 뷰어 로딩을 분리

- 근거: `pages/file.tsx:164–172,353–385`는 갱신마다 접근 값을 비우고 URL/version 키로 뷰어를 다시 마운트한다. `components/file-viewer.tsx:209–224` PDF iframe은 onLoad 중심이며 장기 대기 복구가 부족하다.
- 제안: 동일 파일 재검증은 유효한 미리보기를 유지하며 URL 갱신 상태를 별도로 표시한다. PDF 페이지·미디어 위치 등 보존 가능한 상태를 유지한다. 만료된 다운로드 링크는 비활성화하고, 파일/계정/권한 변경은 즉시 분리한다. iframe은 느린 상태 안내 및 링크 갱신/다운로드 대안을 제공한다.
- 완료 조건: 일시 갱신 실패가 열람 위치를 불필요하게 초기화하지 않는다. PDF 로드 정지/오프라인에서 복구 행동이 보인다. iframe onLoad만으로 PDF 정상 표시를 단정하지 않는다.

### A12 · P2 · Table 컬럼 메타데이터의 부분 로딩

- 근거: `pages/table.tsx:148–153,257–262,397,709–711`. 스키마 대기가 전체 테이블 초기 로딩과 결합되고 컬럼 조회 실패와 미제공 상태가 비슷한 문구로 표현된다.
- 제안: 행이 있으면 본문을 표시하고 스키마 의존 영역만 로딩/오류/Retry로 나눈다. 스키마가 필요한 편집만 비활성화하며 원인을 설명한다. Refresh가 갱신하는 행과 스키마의 진행 상태를 각각 반영한다.
- 완료 조건: 행 성공+스키마 503에서도 읽기 가능한 행은 유지되고 컬럼 정보만 재시도할 수 있다.

### A13 · P2 · 그래프 상세 관계의 캐시 유지

- 근거: `components/graph/GraphDetailPanel.tsx:184–201`의 오류 분기는 기존 관계 데이터보다 먼저 선택된다.
- 제안: 메인 그래프의 좋은 패턴처럼 관계 목록이 있으면 유지하고 해당 영역에 갱신 실패+Retry를 표시한다.
- 완료 조건: 상세 관계 재조회 503이 기존 연결을 지우지 않는다. 선택 노드가 바뀌면 이전 노드의 관계를 새 노드 관계로 표시하지 않는다.

### A14 · P2 · Activity 오류 후 busy 종료와 Retry

- 근거: `pages/vault-activity.tsx:72–77,105,160–172`. 최초 실패 뒤 `entries=null`이 남아 `aria-busy={entries === null || refreshing}`가 계속 true이다. 재조회 오류에는 직접 Retry가 없다.
- 제안: 데이터 존재 여부 대신 실제 요청 진행 상태로 busy를 계산한다. 재조회 오류에도 Retry를 제공하고 적용된 작성자 조건을 계속 표시한다.
- 완료 조건: 최초 500 후 busy=false, Retry 중 true, 완료 후 false. 기존 행이 있는 실패는 행·조건과 복구 버튼을 함께 유지한다.

### A15 · P2 · Admin SSO 카탈로그 재조회 오류의 지역 처리

- 근거: `pages/admin.tsx:232–236,315–343`. 조회 오류 분기가 캐시가 있는 카탈로그/폼도 대체하며 Retry가 없다. 토글 성공 후 refetch 결과의 의미가 분리되지 않는다.
- 제안: 초기 오류만 전체 영역 Alert로 처리한다. 재조회 실패는 폼 초안/카탈로그 유지+Retry로 표현한다. 설정 변경 성공과 상태 확인 실패를 별도로 알린다.
- 완료 조건: 일시 재조회 실패로 입력이 사라지지 않고, 서버에 적용된 토글을 실패한 명령으로 오인하지 않는다.

### A16 · P3 · 설정과 알림의 표현 일관성

- 근거: `pages/settings/tokens-section.tsx:67–68`, `notifications-section.tsx:32–36`의 초기 표시는 최종 목록과 형상이 다르다. `security-section.tsx:195–213`의 소유 Vault 조회가 전역 busy에 연결되어 `settings-dialog.tsx:170`에서 Saving changes로 표현된다. 알림 필터 키 변경은 새 스켈레톤으로 전환된다.
- 제안: 목록 크기에 맞춘 스켈레톤을 사용하고 ‘소유 Vault 확인 중’과 실제 저장을 분리한다. 읽기 조회는 관련 섹션만 잠근다. 알림 필터의 기존 행 유지 여부는 선택적인 개선이며, 유지할 때 이전 필터 안내와 일괄 액션 제어를 반드시 동반한다.
- 완료 조건: 읽기 요청을 저장으로 안내하지 않는다. 조회만으로 설정 전체 닫기/탭 이동을 불필요하게 막지 않는다. 실제 파괴적 변경의 잠금은 유지한다.

## 4. 공통 UX·구현 규칙

| 상태 | 화면과 인터랙션 |
|---|---|
| 최초 조회, 아직 데이터 없음 | 최종 레이아웃의 셸+영역별 스켈레톤, 짧고 구체적인 상태 문구. 관련 없는 탐색은 유지 |
| 최초 오류 | 스켈레톤 종료, 원인에 맞는 Alert+Retry. 권한 없음/없어진 리소스는 별도 처리 |
| 성공한 빈 값 | 조회 성공이 확인된 뒤에만 0/없음 표시, 가능한 다음 행동 안내 |
| 기존 데이터 재조회 | 같은 신원·권한·리소스의 마지막 성공 내용 유지, 영역 busy와 컨트롤 근처 작은 갱신 표시 |
| 기존 데이터 재조회 실패 | 기존 내용+업데이트 실패+Retry. busy는 종료하고 유지된 내용의 적용 조건을 표시 |
| 저장/삭제 요청 | 동사에 맞는 버튼 loading, 중복 제출 방지. 필요한 범위만 잠금 |
| 변경 성공, 후속 조회 실패 | 명령 성공을 유지하고 ‘목록 갱신 실패’ 안내. 조회만 재시도 |
| 계정·권한·리소스 전환 | 이전 보호 데이터를 무조건 유지하지 않음. 신원/권한 revision/vault/resource/query 식별자로 경계 설정 |
| 오래 걸림/오프라인 | 실제 요청 상태에 맞는 설명·복구 제공. 알 수 없는 작업을 가짜 퍼센트로 표시하지 않음 |

구현은 기존 프리미티브를 재사용한다. 필요한 곳에 `initialPending`, `refreshing`, `hasSnapshot`, `initialError`, `refreshError`, `appliedKey`를 명시하거나 동등한 Query 상태로 매핑한다. 모든 화면을 거대한 공통 래퍼에 넣기보다 동일한 상태 규칙과 테스트를 공유한다.

TanStack Query에서는 초기 pending과 `isFetching`의 의미가 다르다. `enabled`가 꺼져 있거나 오프라인으로 `fetchStatus='paused'`인 상태도 고려하여 pending만으로 영구 스피너를 만들지 않는다. 캐시 유지 여부는 단순 `isSuccess`보다 데이터 유효성과 접근 경계로 판단한다. [공식 background fetching 문서](https://tanstack.com/query/latest/docs/framework/react/guides/background-fetching-indicators)

접근성은 로딩 개수보다 **정확한 시작과 종료**가 중요하다. 영역 `aria-busy`는 요청 종료 시 false로 돌아와야 하며, 상태 변화는 초점을 강제로 옮기지 않고 인지할 수 있어야 한다. 반복 폴링마다 여러 라이브 영역이 동시에 읽지 않도록 한 영역이 상태 안내를 소유한다. 스켈레톤은 장식 요소로 처리하고 reduced-motion을 유지한다. [W3C 상태 메시지 해설](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

`LoadingState`/`InlineLoadingState` 자체의 `role=status`와 `aria-busy=true` 조합이 실제 보조기술에서 어떻게 읽히는지는 VoiceOver/NVDA로 추가 검증한다. 이번 소스 감사만으로 안내 누락을 확정하지 않는다.

로딩 표시 지연 150–250ms, 장기 대기 안내 8–10초는 검토 가능한 시작값이지 제품 전체의 확정 기준이 아니다. 빠른 응답에 불필요한 최소 대기 시간을 강제하지 않는다. 공통 API에 일괄 timeout/자동 재시도를 추가하기 전에 조회와 변경을 구분한다. 변경 요청의 클라이언트 대기 종료는 서버 변경 취소를 의미하지 않는다.

## 5. 실행 순서와 검증

| 단계 | 작업 범위 | 완료 기준 |
|---|---|---|
| 1 · 핵심 흐름 | A01, A02, A04 검색, A06, A07, A14 | 빈 화면/잘못된 빈 상태/응답 역전/영구 busy 해소. 상태 전이 회귀 테스트 |
| 2 · 데이터 연속성 | A04 홈, A05, A08, A09, A10, A13, A15 | 재조회 실패에도 올바른 이전 내용 유지. 명령 성공과 조회 실패 분리 |
| 3 · 부분 로딩·마감 | A03, A11, A12, A16 및 공통 접근성 검증 | 독립 요청의 지역화, 읽기 위치 보존, 모바일/보조기술 일관성 |

각 단계는 기능 묶음별 작은 변경으로 진행한다. 기존 `docs/prd/wip/2026-10-14-ui-ux-remediation/`의 완료 항목을 일괄 재개하지 않고, 여기 명시한 남은 상태 전이를 회귀 테스트로 추가한다.

공통 검증 시나리오:

1. 즉시 성공 / 300ms / 2초 지연 / 장기 대기에서 형태와 안내 확인.
2. 최초 500 → Retry 성공, 성공한 빈 응답과 최초 실패의 차이 확인.
3. 기존 데이터 → 느린 재조회 → 503 → Retry 성공에서 내용·스크롤·초안 보존 확인.
4. 빠른 필터/리소스 전환과 역순 응답에서 최신 요청만 반영되는지 확인.
5. 계정 변경·401/403·권한 회수에서 보호 데이터가 잔존하지 않는지 확인.
6. 변경 성공+후속 조회 실패에서 중복 명령을 유도하지 않는지 확인.
7. 375px/1440px, light/dark, reduced-motion, 키보드·VoiceOver/NVDA에서 초점 및 busy 종료 확인.

구현 시 필수 프런트엔드 게이트는 `npm run design:check && npm run typecheck && npm run lint && npm run test`이다. 관련 Playwright 지연/실패 회귀 사례를 추가한다. 최초 감사는 문서 작업으로 수행했으며, 후속 구현 및 테스트 결과는 [구현 기록](implementation.md)에 별도로 기록한다.
